# Council review of the post-R-68 plan: common rules

You are one member of a five-member council. Each member reviews the same plan from a different angle. The members do not talk to each other. The repository owner reads all five reports and decides. Your role brief names your angle.

## The plan under review

- Draft PR #634 in young-kobe/civic-lens, branch docs/post-r68-evidence-plan.
- Setup: git fetch origin docs/post-r68-evidence-plan main && git checkout --detach origin/docs/post-r68-evidence-plan
- Entry point: docs/post-r68/README.md. Then the phase docs it links: claims.md, evaluation.md, graph.md, reader.md, delivery.md, evidence-interface.md, and docs/post-r68/experiments/.
- Context for shipped behavior: README.md, AGENTS.md, docs/architecture.md (its lookup table), and only the feature docs in docs/architecture/ that your angle needs. docs/roadmap.md holds accepted plans.

## Your job

Review the plan adversarially. Assume it has defects until the evidence shows otherwise. Look for weak evidence, small or biased samples, claims the experiments do not support, hidden costs, ownership conflicts with AGENTS.md, missing failure modes, and work that does not change a product decision. Also propose insights or features that the plan misses, and say whether more experiments should run before the build starts.

Rules:
- Give evidence for each claim: a file and line, a number from the repo, a command you ran and its output, or a public source with a URL. Mark each item as VERIFIED (you checked it) or INFERRED (your judgment).
- Do not invent numbers. If you cannot check a thing, say so.
- Keep your angle. Do not repeat a full review of the other angles.
- Be concrete. "Add more tests" is not a finding. "Phase 1 has 4 positives that share one bill, so the 4 of 4 rate has no transfer evidence; add 10 fresh cases from 3 bill families" is a finding.
- For each proposed experiment: the question, the product decision it changes, the smallest design that answers it (sample size and why), the inputs, the cost in hours and dollars, and what result would change the plan. Say "do not run" when the result would not change a decision.
- Rank findings P1, P2, P3. A P1 would make the pilot or a phase produce a wrong or misleading result, harm a named official through a false attribution, or break an AGENTS.md rule. A P2 is a material weakness in evidence, scope, cost, or ownership. A P3 is a smaller improvement.

## Hard limits

- READ-ONLY on Git and GitHub, with one exception: post your report as ONE comment on PR #634. Never commit, push, edit a PR body or a file in the repo, resolve or reply to a thread, or change draft state. Temporary files under /tmp are fine.
- Never call a paid AI API, production, or the live site in bulk. Public government sources (congress.gov web pages, govinfo.gov, the VA site, USAspending) are fine for a few spot checks. Pace requests at least 2 seconds apart.
- Never ask a question and wait. Nobody will answer. If you are blocked, write what blocked you in the report and finish.
- Do not assign shell variables from command output (no V=$(...)). Give literal values. Run each setup step as its own Bash call.
- Prose in ASD-STE100 Simplified Technical English: short sentences, active voice, one idea in each sentence. No em dashes and no en dashes.
- No Co-Authored-By, Claude-Session, session link, claude.ai link, or "Generated by" footer anywhere.

## Report

Post the full report as one comment on PR #634 with the mcp__github__add_issue_comment tool (owner young-kobe, repo civic-lens, issue_number 634). If that tool is not available, use gh pr comment 634 --body-file /tmp/report.md. Keep the comment under 60,000 characters.

Structure:
1. First line: "Council review: <your role name>, plan head <short SHA>".
2. Verdict in three sentences or fewer.
3. Counts: P1, P2, P3.
4. Findings, labeled P1-1, P2-1, P3-1 and so on. Each has: the claim, VERIFIED or INFERRED, the evidence, why it matters, and a fix.
5. Proposed insights or features, ranked. Each has: the reader question it answers, the data it needs (existing or new), the main risk, and a rough size.
6. Experiments: a table with Run now, Run later (with its trigger), or Do not run, for each one you propose and for each "next decision" row in the README research table.
7. Questions for the owner, if any. Keep these few and concrete.

After posting, run: gh api repos/young-kobe/civic-lens/issues/634/comments -q '.[-1].body' | grep -ciE 'generated by|co-authored-by|claude.ai'. If the count is not 0, say so in your final message. Do not edit or delete the comment.

Your final message must be under 900 characters. Give the comment URL, the P1/P2/P3 counts, each P1 title, and your experiment advice in one sentence.
