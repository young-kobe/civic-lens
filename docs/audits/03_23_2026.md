# Civic Lens Code Audit Report

This report outlines findings from analyzing the Go ingestion layer, Python ETL/API layer, Data layer, and React UI layer. The review focused on data robustness, concurrency, IO, database operations, and code modularity. No refactoring has been performed yet, as requested.

## 1. Ingestion Layer (Go)

### Findings & Discrepancies
*   **Concurrency vs. DB Bottlenecks:** The Go crawler uses a weighted semaphore to control worker concurrency (`sem := semaphore.NewWeighted(int64(cfg.Crawl.MaxConcurrency))`). However, the SQLite database connection uses `conn.SetMaxOpenConns(1)` and `conn.SetMaxIdleConns(1)`. Even though SQLite WAL mode (`_journal=WAL&_busy_timeout=5000&_foreign_keys=on`) is used which supports concurrent readers alongside a single writer, restricting the connection pool to exactly 1 ensures that the Go layer cannot take full advantage of concurrent reads or overlapped execution.
*   **Direct DB Calls in Crawl Loop:** In `processPage`, DB updates (`insertArticle`) are executed synchronously via `conn.ExecContext(ctx, ...)` instead of batching or leveraging `BeginImmediate()`. If the Python ETL is querying the DB heavily, or if MaxConcurrency is high, this may frequently block crawlers at the DB insertion phase due to locks or the `5000ms` busy timeout.
*   **Static Migrations:** In `db.go`, the migrations array is hardcoded to a struct listing the SQL files (`001_initial.sql`, `002_x_tables.sql`, etc.), despite looking up a `migrations/` directory on the filesystem. Adding a new migration file to `data/migrations` won't run unless the Go struct array is explicitly modified, which is a discrepancy between a file-based migration system and a hard-coded struct.
*   **Separation of Concerns:** The runners cleanly separate fetching from UI logic, but `processPage` in `crawl.go` is somewhat monolithic, handling robot checks, downloading, checking status codes, storing raw hash payloads, metadata extraction, canonical URL updates, outlink pushing, and database row insertion. 

### Recommendations
*   Increase `SetMaxOpenConns` to allow parallel readers given WAL mode is active.
*   Extract the database insertion logic from `processPage` into a separate worker queue or bulk inserter to prevent IO blocking.
*   Dynamically parse the `data/migrations` directory in `db.go` instead of hardcoding migrations in an array.

## 2. Analysis & ETL Layer (Python)

### Findings & Discrepancies
*   **ETL Unbatched Processing:** In `loader.py`, `load_new_raw_content` iterates over raw records and processes HTML synchronously using `trafilatura` before doing row-by-row `cursor.execute(...)` inserts. This takes a single SQLite connection lock and holds the entire process up without periodic commits until the function exits. If thousands of rows are fetched, memory pressure and long database write-transaction locks can cause contention.
*   **Synchronous Queue Blocking:** In `server.py`, `process_analysis_queue` executes sequential analysis (Bot Detection -> Sentiment -> Favorability) synchronously for every document in a standard `for var in docs` loop. The function is fired into a FastAPI `BackgroundTasks`, running in a single background thread. While it executes, it will not scale up to use multi-core parallelism. The data extraction could heavily benefit from `asyncio` or `ProcessPoolExecutor` for CPU-bound tasks (Sentiment calculations and NLP parsing).
*   **Database connection management:** The Python code lacks centralized connection pooling or pragmatic usage of `_busy_timeout` pragmas on checkout. Standard `sqlite3.connect` generates standard connections that default to no busy timeout or WAL setup during initialization. It works passively due to Go already activating WAL mode, but Python's `sqlite3` without explicit `check_same_thread=False` or tuning could conflict if multi-threading is introduced.

### Recommendations
*   Introduce `asyncio` to the Analysis endpoints and background processors, dispatching CPU heavy processing to process pools and network IO to concurrent tasks.
*   Implement explicit context managers for sqlite3 handles that set the `busy_timeout` property PRAGMA, ensuring cross-language queries don't instantly throw "database is locked" errors on collisions.
*   For the ETL `load_new_raw_content`, use bulk insertions (`executemany`) and read batches to prevent large, unwieldy uncommitted blockings.

## 3. Data Persistence (SQLite + Filesystem)

### Findings & Discrepancies
*   **Raw File System:** The file system hashing strategy (`data/raw/sha256/`) elegantly bypasses SQLite blob size limits, keeping the database lean.
*   **Schema Consistency:** The `docs` schema unifies Reddit, News, and X/Twitter into a single table with a polymorphic `ident` and `source_type`. This is a clean design pattern that prevents complex polymorphic join constraints over diverse tables, adhering to SOLID principles by ensuring the analysis pipeline acts on a generic `docs` interface.

### Recommendations
*   Regular backup procedures for both SQLite db and the Raw data directory should be clearly documented or scripted, as a loss of `data/raw` renders the DB useless for analysis.

## 4. UI Layer (React)

### Findings & Discrepancies
*   **Modularity:** The UI correctly separates API calls (`services/api.ts`) and functional components (`components/common`, `pages/`). It uses React hooks, and the `App.tsx` routes between `StoryClusters`, `PublicSentiment`, `BotActivityProfiler`, and `GlobalHeatmap` pages seamlessly using a simple tab-state representation.
*   **Data Aggregation Fetching:** The UI explicitly retrieves generated cache metadata and pre-calculated statistics rather than raw unaggregated objects. This correctly forces heavy calculation out of the browser / API runtime footprint.

### Recommendations
*   Implement a standard router (e.g., `react-router-dom`) instead of ad-hoc conditional `renderPage()` logic in `App.tsx` to ensure deep linking to specific pages/tabs works appropriately.
*   Add explicit error handling and Loading Boundary suspenses at the page level.

---
**Summary:** The application successfully implements a multi-language pipeline where Go handles network IO and crawling, and Python handles CPU-heavy textual analysis. The biggest areas for improvement involve concurrency patterns around the SQLite database and breaking the single-thread bottlenecks present in the Python ETL background tasks.
