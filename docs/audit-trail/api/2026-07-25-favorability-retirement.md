# 2026-07-25 — Every `analysis.favorability_stances` reader repointed to `analysis.target_mentions`

`analysis.favorability_stances` has no writer as of this change (see `docs/audit-trail/analysis/2026-07-25-text-sentiment-only.md` — the text engine is sentiment-only now). The six live read sites in the API layer are repointed to `analysis.target_mentions`, which already covered the same "stance toward a mentioned entity" signal — party-neutral and topic-tagged, where `favorability_stances` was Republican-entities-only by the old text prompt's explicit instruction. Every existing `favorability_stances` row in the database is Republican-only: any aggregate that somehow spans the cutover (a cache, a long custom date range crossing the deploy) mixes a GOP-scoped population with a party-neutral one and must not be presented as one continuous series.

## CRITICAL DEPLOY CONSTRAINT

This entry's changes are all in the new Postgres-native API layer (`analysis/src/api/**`), which does not share code with the retired stack. The constraint that matters here is upstream of this layer: `analysis/src/engine/analyzer.py`/`engine/bot.py` (RETIRED, still running in production via `scheduler/job_runner.py`'s systemd timer) import the same `llm/{prompts,schemas}.py` objects the text-engine change edited. **The owner must disable the analysis timer before that branch reaches production** — see the analysis-layer entry for the full explanation. This API-layer change is safe to deploy independently since it only reads `analysis.*` tables that already exist; it does not touch the shared prompt/schema surface.

## What shipped

- **`analysis/src/api/queries/sentiment.py`**: `_FAVORABILITY_ROWS_SQL` deleted; `get_sentiment_panel()` no longer fetches favorability rows. `_build_entity_stances()` now takes `target_rows` alone (was `(favorability_rows, target_rows)`) and builds one `target_stance` cell per entity instead of merging `favorability` + `target_stance` cells. `_normalize_favorability()` (the `favorable`->`positive` mapping shim) deleted — target_mentions was always in the `positive`/`negative`/`neutral`/`mixed` vocabulary, so there was never anything to normalize once favorability_stances left the merge.
- **`analysis/src/api/models/sentiment.py`**: `EntityStanceAggregate` drops the `favorability: StanceCounts` field. It previously duplicated `target_stance` — both were "stance toward this entity," just from two engines with different scope — so removing the redundant half is a straight simplification, not a design collapse. Docstring rewritten to describe the single source.
- **`analysis/src/api/queries/movers.py`**: `_fetch_favorability_rows()` rewritten to query `analysis.target_mentions` (`task='targets'`, `tm.entity_id IS NOT NULL` since target_mentions permits unresolved mentions unlike favorability_stances' `NOT NULL` FK) instead of `analysis.favorability_stances` (`task='text'`). `_tally_favorability()`'s internal accumulator keys renamed `fav`/`unfav` -> `pos`/`neg` and now read `stance == "positive"`/`"negative"` instead of `"favorable"`/`"unfavorable"` — the `FavorabilityMover` feature and its API shape are UNCHANGED, only the underlying table swapped. This is a genuinely distinct metric from `ToneMover` (which measures the *entity's own* posts' overall sentiment) — `FavorabilityMover` measures stance *toward* the entity, so it survives as its own concept, just sourced from the party-neutral table now instead of the GOP-only one.
- **`analysis/src/api/models/movers.py`**: `FavorabilityMover`'s docstring updated to name `analysis.target_mentions` as the source (was `analysis.favorability_stances`); field shape unchanged.
- **`analysis/src/api/queries/entities.py`**: `_STANCE_EXPRESSED_SQL` rewritten to query `analysis.target_mentions` (`task='targets'`) instead of `analysis.favorability_stances` (`task='text'`), keeping the same "authored by this entity, any target's stance" join shape (`corpus.author_profiles`/`news_articles`/`reddit_posts` LEFT JOINs filtered on the entity). This is genuinely distinct from `stance_received` (target_mentions where the entity IS the target) — expressed vs. received is an axis `favorability_stances` never distinguished on its own; only the *join* (authored-by vs. mentioned) made that distinction, and that join shape is preserved. `_stance_distribution()` drops its `sentiment_labels: bool` parameter and the `_normalize_favorability()` shim — both `stance_received` and `stance_expressed` now read the `sentiment_label` vocabulary directly, since both are `target_mentions` rows.
- **`analysis/src/api/models/entities.py`**: `StanceDistribution`'s docstring rewritten — no longer describes a favorable/unfavorable-normalizing merge; both `stance_received` and `stance_expressed` are `target_mentions` (`sentiment_label`) now.
- **`analysis/src/api/queries/docs.py`**: `_text_fields()` drops the `analysis.favorability_stances` query and the `favorability_stances` key from the per-doc drill-down response entirely (not kept as an always-empty placeholder). `ui/src/types.ts`'s `AnalysisResult.fields` is `Record<string, unknown>` (deliberately untyped, varies by task) so no UI type change was needed for this key's removal.
- **Tests**: `analysis/tests/test_api_queries_sentiment.py` — `NormalizeFavorabilityTests` deleted; the favorability+target_stance merge test rewritten as `test_entity_stance_surfaces_from_target_mentions_alone` (an entity with ONLY target evidence, no favorability row possible, still surfaces — the regression this whole change is for). `test_api_queries_entities.py` — `StanceDistributionTests` drops the `sentiment_labels` kwarg; `test_stance_received_vs_expressed_are_distinct` reseeded through two `target_mentions` rows (one on the entity's own authored doc, one on someone else's doc naming the entity) instead of a `favorability_stances` + `target_mentions` pair. `test_api_queries_movers.py` — `_seed_favorability_docs` reseeded through a `targets`-task run + `target_mentions` insert instead of a `text`-task run + `favorability_stances` insert; stance literals changed `favorable`/`unfavorable` -> `positive`/`negative`. `analysis/tests/contract/test_sentiment_contract.py` + its `sentiment_panel_basic.json` snapshot: seed rewritten to insert a `target_mentions` row instead of `favorability_stances`; the snapshot's `entityStances[0]` drops the `favorability` key and `targetStance` now carries the seeded row (`positive: 1, volume: 1`) instead of the previous all-zero placeholder.

## Why

- **`favorability_stances` was a strict subset.** Both it and `target_mentions` measured "stance toward a mentioned entity" — the only difference was scope (GOP-only, no topic) vs. (all parties, topic-tagged). Once the text engine stopped writing it, every reader that merged the two was merging one real signal with a permanently-frozen historical one; repointing to the surviving, superset source is the correct fix, not a workaround.
- **No response model should still advertise the favorability vocabulary.** `EntityStanceAggregate.favorability` and the `favorable`/`unfavorable` string literals throughout the merge helpers existed only because two differently-vocabularied tables needed reconciling. With one source and one vocabulary (`positive`/`negative`/`neutral`/`mixed`), keeping the mapping shims as permanent no-ops would misrepresent the data model to every future reader of this code.
