# 2026-07-22 — Postgres redesign Phase 1: dual-backend Go migration runner

`ingest/internal/storage/db/db.go` now opens either SQLite or Postgres from the same `Open(dsn)` entry point, selected by DSN scheme, and the `civic-ingest migrate` subcommand applies whichever backend's migration set is pending. This is the Go half of the Postgres redesign's Phase 1 (see plan `has-our-aggregate-method-async-frog`, checklist `docs/todos/pg-redesign.md`); cross-linked with `docs/audit-trail/infra/2026-07-22-pg-phase1-infrastructure.md` and `docs/audit-trail/analysis/2026-07-22-pg-connection-pool.md`.

## What shipped

- **`Open(dsn)` branches by scheme**: `isPostgresDSN` matches `postgres://` / `postgresql://` and dispatches to `openPostgres` (via `jackc/pgx/v5/stdlib`, `sql.Open("pgx", dsn)`, `Ping()`-verified so a bad DSN fails at `Open` rather than on first query, pool capped `SetMaxOpenConns(5)`/`SetMaxIdleConns(2)` — modest, sized for a box shared with the API and job workers); anything else still goes through `openSQLite` unchanged (WAL mode, busy_timeout, foreign_keys pragma — untouched). One `DB` struct (`isPostgres bool` field) and one `Migrate(ctx)` method dispatch to `migrateSQLite` or `migratePostgresDir` accordingly — callers (`app.NewDBOnly`, `civic-ingest migrate`) do not branch themselves.
- **`CIVIC_DATABASE_URL` as the default `--db`**: `cmd/civic-ingest/main.go`'s `defaultDBPath()` reads `CIVIC_DATABASE_URL` first (matching the env var name already used on the Python side) and falls back to `data/civic_lens.db` only if unset; an explicit `--db` flag still overrides either. Covered by `main_test.go` (`TestDefaultDBPath`).
- **`data/pg-migrations/` as a fixed convention**: unlike the SQLite path (derived from the DB file's own directory), Postgres migrations always resolve from `data/pg-migrations/` relative to the process working directory (`pgMigrationsDir` constant) — the same cwd-relative assumption the SQLite default path already made. `discoverMigrations` (numeric-prefix `NNNN_name.sql` parsing) is shared code between both backends.
- **`ops.schema_migrations` bootstrap, and why it exists**: `bootstrapSchemaMigrations` runs `CREATE SCHEMA IF NOT EXISTS ops` and `CREATE TABLE IF NOT EXISTS ops.schema_migrations (version INT PRIMARY KEY, applied_at TIMESTAMPTZ NOT NULL DEFAULT now())` *before* `migratePostgresDir` looks at any migration file. This is a genuine chicken-and-egg: migration 1 (`0001_north_star.sql`) is itself what defines `ops.schema_migrations` for posterity, but the runner needs a place to record that migration 1 has been applied *before* migration 1 has necessarily finished running — so the runner, not any migration file, owns creating this one specific table ahead of everything else. Every later migration then finds the table already present and its own (unconditional) DDL is irrelevant to it; only migration 1's DDL needs to tolerate the collision, which is why the fix (see the infra entry) was scoped to `0001_north_star.sql` alone. `applyPostgresMigration` runs each file's SQL and its own `INSERT INTO ops.schema_migrations (version) VALUES ($1)` inside one transaction — a crash or failing statement anywhere rolls both back together (the same D-6 atomicity guarantee the SQLite path already had), so a corrected re-run always applies cleanly. This is why migration files must never self-insert their own version row (see the infra entry's note on the redundant `INSERT` that was removed from `0001_north_star.sql`): the runner already owns that insert, uniformly, for every future migration file.
- **pgx v5.8.0 pin**: `ingest/go.mod` now declares `go 1.24.0` and requires `github.com/jackc/pgx/v5 v5.8.0` (`go.sum` updated accordingly). The dev machine's installed toolchain (1.23.5) auto-fetched Go 1.24.0 via `GOTOOLCHAIN=auto` on first build — confirmed via `go version -m` on the built binary. Rationale: v5.8.0 is pgx's current stable release at pin time, and the `go 1.24.0` module line intentionally tracks it rather than pinning to an older pgx release compatible with 1.23 — Phase 1 wanted the current, actively-maintained pgx line rather than an artificially held-back version for a toolchain constraint that resolves itself via `GOTOOLCHAIN=auto` (no manual Go upgrade required on any machine with network access to proxy.golang.org).
- **Test coverage**: `ingest/internal/storage/db/db_test.go` gained SQLite-path regression coverage for the branch-by-scheme change; `db_postgres_test.go` is a real-server integration test gated on `CIVIC_TEST_POSTGRES_DSN` (distinct from the runtime `CIVIC_DATABASE_URL` so running `go test` never accidentally writes into a configured Postgres) — it exercises bootstrap, ordered apply, idempotent re-run, and atomic rollback-on-failure against fixture migrations in a temp directory (never against the real `data/pg-migrations/`). `cmd/civic-ingest/main_test.go` covers the `--db` default precedence.

## Why

- The plan calls for one Go binary handling both backends during the parallel-build period (`storage` branched by DSN scheme), rejecting a hard fork or a second binary — Phase 2 (full `raw.*` port) lands inside this same branch point.
- golang-migrate was explicitly rejected in the plan (adds dirty-state semantics the existing ~150-line hand-rolled runner does not need); porting the existing runner's shape (discover -> apply -> record, atomic per-file) to Postgres keeps one mental model across both backends.
- The chicken-and-egg bootstrap is unavoidable in any from-scratch migration-ledger design where migration 1 is also the ledger's own schema — it is the reason the DDL fix was scoped exactly to the `ops` bootstrap collision and nothing else (see the infra entry for the fix and its live validation).

## Validation performed this task

- `cd ingest && go build -o ../civic-ingest ./cmd/civic-ingest` — clean build, Go 1.24.0 toolchain auto-fetched.
- Real end-to-end `migrate` against a throwaway `postgres:17-alpine` container: clean first apply, idempotent second apply (see infra entry for exact output and table counts).
- `go test ./... -count=1` — all packages pass (`storage/db`, `runner`, `frontier`, `httpclient`, `robots`, `config`, `extract/x`, `util`, `cmd/civic-ingest`; packages with no test files reported as such, none failing).
- `db_postgres_test.go`'s `TestPostgresMigrate` run explicitly against the same throwaway container (`CIVIC_TEST_POSTGRES_DSN` set) as a bonus regression on the runner itself, beyond what `go test ./...` exercises by default (it is skipped without that env var) — passed, confirming ordered apply / idempotent re-run / atomic rollback-on-bad-SQL all hold against a real server, not just `go test`'s default no-Postgres skip path.

## Follow-ups

- What remains SQLite-only until Phase 2/11: `raw.*` writers (`ingest/internal/storage/rawstore` and the frontier/crawler/fetcher write paths) still target the SQLite tables exclusively — this task ported only the migration runner, not the data-writing storage package. `modernc.org/sqlite` and the SQLite storage branch are dropped only at Phase 11 (decommission), after cutover.
- Phase 2 (tracked in `docs/todos/pg-redesign.md`): port `ingest/internal/storage/` proper to Postgres (`$1` placeholders, `ON CONFLICT`, enum casts), add `FOR UPDATE SKIP LOCKED` to the frontier, per-domain balance quotas from `data/seeds.yaml`, and investigate the empty `reddit_posts_raw` capture in production.
- Production deploy does not yet set `CIVIC_DATABASE_URL`; the binary's default remains the SQLite path until that env var is configured, which has not happened (VPS resize is still outstanding — see the infra entry).
