# 2026-07-25 — Text engine drops favorability; `analysis.favorability_stances` retired (writer removed, table kept)

The unified text engine (`engine/text.py`) now produces sentiment only. The favorability half it used to emit alongside sentiment — `entity_stances`, `overall_gop_stance`, `overall_favorability_confidence`, `favorability_reasoning`, written to `analysis.favorability_stances` — is gone from the schema, the prompt, and the engine. Per-entity stance is fully covered by the `targets` engine (`engine/targets.py`, unchanged, not touched by this entry), which is party-neutral, topic-tagged, keeps unresolved targets, and already runs on every doc. `favorability_stances` was a one-party (GOP only, by the old prompt's explicit instruction — "Analyze favorability ONLY toward the explicitly mentioned GOP entities"), topic-less subset of what `target_mentions` already produces. Every existing `favorability_stances` row is Republican-only: any historical aggregate spanning this change mixes two populations (a GOP-scoped sample and a party-neutral one) and must not be treated as one continuous series.

## CRITICAL DEPLOY CONSTRAINT

`analysis/src/engine/analyzer.py` and `engine/bot.py` — the RETIRED SQLite stack, still driven in production by `scheduler/job_runner.py` on a systemd timer — import the SAME prompt and schema objects from `analysis/src/llm/{prompts,schemas}.py` this change edits. They have no private copies. After this lands, `analyzer.py` reads `entity_stances`/`overall_gop_stance`/`overall_favorability_confidence`/`favorability_reasoning` off a `.get()` with a default and will NOT crash — it will silently produce wrong/fabricated-looking favorability output from a schema that no longer instructs the model to return those fields. **The owner must disable the analysis timer before this code reaches the box.** No fork of the shared prompt/schema objects was created; none should be — the retired stack is deleted at Phase 11, not forked.

- **`analysis/src/llm/schemas.py`**: `TEXT_ANALYSIS_SCHEMA` drops `entity_stances`/`overall_gop_stance`/`overall_favorability_confidence`/`favorability_reasoning` from both `properties` and `required`. `ENTITY_STANCE_SCHEMA` (only ever nested under the removed `entity_stances` property) deleted outright as dead code.
- **`analysis/src/llm/prompts.py`**: `TEXT_ANALYSIS_PROMPT_VERSION` bumped `text-analysis-v5` -> `text-analysis-v6`. `TEXT_ANALYSIS_SYSTEM_PROMPT` drops rule 4 (FAVORABILITY) entirely, drops the favorability half of the evidence/reasoning rule and the confidence-format rule, and drops `entity_stances`/`overall_gop_stance`/`overall_favorability_confidence`/`favorability_reasoning` from the OUTPUT SCHEMA block. Rules renumbered 1-7. Header sentence changed from "evaluating both overall sentiment and specific entity favorability" to "evaluating overall sentiment" — no party name appears anywhere in the prompt (verified by test, and required by `.agent/rules/media-analysis.md` rule 7: political lean is never fed into an LLM prompt).
- **`analysis/src/engine/text.py`**: `FavorabilityStanceOutcome` dataclass deleted; `_build_favorability_stances()` deleted; `TextAnalysis` drops `favorability_stances`/`dropped_unresolved`. `analyze()`/`process()` drop the `resolver: EntityResolver` parameter (nothing in this module resolves an entity anymore) — the `EntityResolver` import is gone too. `process()`'s run-level confidence is now simply `result.sentiment.confidence` (previously a mean over sentiment + N favorability stances).
- **`analysis/src/scheduler/pipeline.py`** (necessary cross-file edit, not normally owned by this workstream — see Scope note): `_text_worker()`'s call to `text.process()` drops the `resolver` argument to match the new signature; the wrapper itself still receives `(doc, client, resolver)` from `scheduler/stages.py`'s uniform queue-stage interface and discards `resolver`, the same pattern `_bot_worker`/`_propaganda_worker` already use.
- **`analysis/src/engine/lean_derivation.py`**: `_SELECT_DIRECTIONAL_EVIDENCE_SQL` drops the `analysis.favorability_stances` half of its `UNION ALL` — `analysis.target_mentions` is now the sole evidence source. `_FAVORABLE_STANCES`/`_UNFAVORABLE_STANCES` trimmed from `{"favorable","positive"}`/`{"unfavorable","negative"}` to `{"positive"}`/`{"negative"}` (the `favorable`/`unfavorable` vocabulary can never appear in a query that no longer reads `favorability_stances`). The sample-count/threshold gates (`LEAN_MIN_SAMPLE_COUNT`, `LEAN_SHARE_THRESHOLD`, `LEAN_CONFIDENCE_SATURATION_SAMPLES`) are untouched.
- **`analysis/src/results/store.py`** + **`analysis/src/results/__init__.py`**: `FavorabilityStanceRow` dataclass and `RunHandle.save_favorability_stances()` deleted; the `analysis.favorability_stances` INSERT in `_write_results()` deleted. `store.py` is now the traceability-contract module with no path that can write that table.
- **`data/pg-migrations/`**: no new migration. `analysis.favorability_stances` is deliberately NOT dropped — see Follow-ups.
- **Tests**: `analysis/tests/test_engine_text.py` rewritten (no `resolver`, no favorability fixtures/assertions). New `analysis/tests/test_text_bot_schema_trim.py`: the schema's `required` list excludes the four removed keys and a response without them still yields a valid `TextAnalysis`; no party name appears in `TEXT_ANALYSIS_SYSTEM_PROMPT`. `analysis/tests/test_engine_lean_derivation.py`: `SignalForTests` drops the now-impossible `favorable`/`unfavorable` cases (the `positive`/`negative` cases already covered the same logic); `TallyEvidenceTests` and the whole `RunIntegrationTests` class reseeded through `target_mentions`/`targets`-task runs instead of `favorability_stances`/`text`-task runs. `analysis/tests/test_result_store.py`: `test_sentiment_and_favorability_round_trip` -> `test_sentiment_round_trip`; new `FavorabilityStancesRetiredTests` asserts `store` has no `FavorabilityStanceRow` and `RunHandle` has no `save_favorability_stances`.

## Why

- **Redundant signal, wrong scope.** `favorability_stances` and `target_mentions` measured the same thing — stance toward a mentioned entity — from two engines. One was restricted to Republican entities by prompt instruction; the other is party-neutral and topic-tagged. Keeping both meant every downstream reader had to merge two overlapping, differently-scoped samples into one number, which the API-layer entry (`docs/audit-trail/api/2026-07-25-favorability-retirement.md`) describes in detail.
- **Token cost.** Removing the favorability half of the text prompt (four output fields, one full rule, half of two more) shortens every text-task call — a real, if modest, per-call saving across every doc the pipeline analyzes, on top of removing a structurally redundant judgment.
- **Never fabricate values.** Recomputing this the safe way — build the target_mentions-only path first, verify readers, THEN stop writing — meant the schema/prompt change had to land before any reader migration could be verified end to end, hence editing `llm/{prompts,schemas}.py` as the first concrete step of this workstream.

## Scope note

`analysis/src/scheduler/pipeline.py` is not in this workstream's owned file list (`analysis/src/llm/{prompts,schemas}.py`, `engine/{text,bot_detection,lean_derivation}.py`, `results/store.py`, `api/queries/*.py`, `api/models/*.py`, `scheduler/stages.py` only if the text stage's signature changes, `data/pg-migrations/`, `tests/**`). But `text.process()`'s signature dropping `resolver` breaks `pipeline.py`'s `_text_worker` wrapper, which called `text.process(doc, client, resolver)` — leaving it unedited would raise `TypeError` on the very next `run.sh analyze-pg` invocation. The fix is mechanical and minimal: drop one argument from one call, matching the existing `_bot_worker`/`_propaganda_worker` convention of receiving-but-discarding `resolver`. `scheduler/stages.py` itself needed no change — its `_process_one()` always calls `spec.worker(doc_input, client, resolver)` uniformly regardless of which engine is behind the wrapper.
