# 2026-07-22 — Postgres redesign Phase 1: infrastructure groundwork

The compose stack and dev tooling gain a `postgres:17-alpine` service and the north-star schema DDL, running fully alongside the untouched SQLite stack. Nothing in the running system reads or writes it yet — this entry documents groundwork validated end-to-end, not a cutover. Authority: plan `has-our-aggregate-method-async-frog` (2026-07-22), Phase 1; checklist `docs/todos/pg-redesign.md`. Cross-linked with `docs/audit-trail/ingestion/2026-07-22-pg-migration-runner.md` and `docs/audit-trail/analysis/2026-07-22-pg-connection-pool.md`.

## What shipped

- **`docker-compose.yml`**: a `postgres` service — `pgdata` named volume, bound to `127.0.0.1:5432` only, `mem_limit: 768m`, `shared_buffers=256MB`/`work_mem=16MB`/`max_connections=30` (sized for the current CPX11-class box: see the VPS-resize prerequisite below), a `pg_isready` healthcheck, and `POSTGRES_USER`/`POSTGRES_PASSWORD` wired through `${VAR:?...}` — compose refuses to start the service at all if either is unset, rather than falling back to Postgres's default trust-auth. `docker-compose.override.example.yml` adds a bind-mount variant (`./.compose-data/pgdata`) so `rm -rf .compose-data` resets Postgres the same way it already resets the SQLite data dir.
- **`./run.sh pg`**: brings up the `postgres` service via `docker compose up -d postgres` and polls the container healthcheck (30 x 2s) before returning, so any following step (e.g. `civic-ingest migrate`) never races an unready server.
- **Env contract** (`.env.example`): `POSTGRES_DB` / `POSTGRES_USER` / `POSTGRES_PASSWORD` (no shipped password default — `CHANGE_ME` placeholder, deliberately not usable as-is) drive the compose service; `CIVIC_DATABASE_URL` (`postgresql://user:pass@host:5432/db`) is the single DSN both the Go binary and the Python pool read, matching the naming already used elsewhere in the settings (`CIVIC_` prefix convention).
- **`data/pg-migrations/0001_north_star.sql`**: the entire target schema as one greenfield migration — six namespaced schemas (`raw`, `corpus`, `analysis`, `serving`, `ops`, `archive`), `BIGINT GENERATED ALWAYS AS IDENTITY` surrogate keys (except `raw.*` natural keys and verbatim-imported `archive.*` IDs), `TIMESTAMPTZ` everywhere, JSONB confined to exactly three columns (`analysis.runs.raw_response`, `ops.pipeline_runs.stage_summary`, `archive.*`). `docs/DATABASE_SCHEMA.md` (v3.0) is regenerated from this file and headed "TARGET SCHEMA — not yet live in production"; the v2.0 SQLite reference stays below the fold, unchanged.
- **DDL fix landed in this task**: `0001_north_star.sql` originally could not apply against a fresh database. The Go migration runner (`ingest/internal/storage/db/db.go`) bootstraps `ops` schema + `ops.schema_migrations` *before* applying any migration file — a chicken-and-egg necessity, since the runner needs somewhere to record that migration 1 has been applied, including migration 1 itself (see the ingestion entry for the full rationale). The DDL's own `CREATE SCHEMA ops;` (unconditional) then collided with that bootstrap (`SQLSTATE 42P06`, duplicate_schema) on every fresh apply. Fixed to `CREATE SCHEMA IF NOT EXISTS ops;` and the DDL's `CREATE TABLE ops.schema_migrations` to `CREATE TABLE IF NOT EXISTS` with column definitions kept byte-identical to the bootstrap's (`version INT PRIMARY KEY, applied_at TIMESTAMPTZ NOT NULL DEFAULT now()`). No other object in the file was touched — every other table/type still fails loud on a double-apply, which is the point of the version ledger. A second, related bug surfaced by the same fix: the file also carried its own `INSERT INTO ops.schema_migrations (version, applied_at) VALUES (1, now());` at the end, duplicating what the runner's `applyPostgresMigration` already inserts in the same transaction — this made the runner's insert collide on the primary key and roll the whole migration back. Removed; migration files do not self-track their version under the established runner contract (mirrored by the fixture migrations in `ingest/internal/storage/db/db_postgres_test.go`, none of which self-insert).
- **What validates the DDL**: a throwaway `postgres:17-alpine` container (unique name, random host port, throwaway credentials, no repo volumes touched) was used to run the real `civic-ingest migrate` binary end to end: first apply succeeded cleanly (`Migrations applied successfully`, one "Applying migration 1" line), a second `migrate` invocation was a true no-op (no "Applying migration" line, same exit 0), and a per-schema table count via `psql` matched the DDL author's reported figures exactly — `raw` 5, `corpus` 8, `analysis` 18, `serving` 9, `ops` 4, `archive` 11 — with `ops.schema_migrations` holding exactly one row (`version = 1`). The container was removed afterward; `docker ps -a` / `docker volume ls` confirm no leftovers.

## Why

- Kobe wants to work the data hands-on (pgAdmin) and judged the SQLite schema too tangled to normalize incrementally — full redesign, recompute (not translate) derived data, build in parallel and cut over only after side-by-side verification (see the plan's Context section).
- The DDL fix was forced by testing the plan's own instruction to verify end-to-end rather than trust the file in isolation: the bootstrap-vs-DDL chicken-and-egg was named as a known risk in the task brief; the redundant self-insert was not previously called out and was only caught by actually running `migrate` against a live server.
- Compose sizing (768m / 256MB shared_buffers / 30 connections) matches the plan's explicit RAM budget for the current 2GB-measured box, not a generic default.

## Follow-ups (tracked in `docs/todos/pg-redesign.md`)

- **VPS resize to >=4GB (CPX21/CPX31) remains Kobe's manual action and is NOT done** — the box was measured at ~600Mi free of 1.9Gi total on 2026-07-22; Postgres cannot run alongside the current stack in production until this happens. Everything in this entry was validated against a throwaway container on the dev machine, not the production host.
- Postgres is not yet live anywhere real: no production deploy references this service, no application code opens a pool against it outside its own tests (see the analysis-layer entry), and the Go binary's default DSN still resolves to the SQLite path unless `CIVIC_DATABASE_URL` is explicitly set (see the ingestion entry).
- Phase 2 onward (Go ingestion port, precious-data migration script, ETL rewrite, ...) are unstarted; this entry covers Phase 1 infrastructure only.
