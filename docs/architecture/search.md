# Search

## Purpose

The search service gives readers full-text search over every published record. It is also the public read API. It runs apart from the operational application, with its own Postgres database. It reads published releases and the `public_api` views.

## Decisions

- The kind `executiveAction` indexes the saved Federal Register record as source text and has no summary text. Deploy the search service before the publisher. An older service refuses a release that holds the new kind.
- The service is its own Web SDK project, `CivicLens.PublicApi`. It references `CivicLens.Publication.Contracts`, `CivicLens.PublicWeb`, and the Npgsql package only. PublicWeb holds only public components, so it gives no access to operational storage, credentials, job handlers, or unpublished evidence.
- The service has its own Postgres database, named by `CIVIC_LENS_SEARCH_DATABASE`. It connects to the operational database only through the role `civic_lens_public`, which reads `public_api` views and nothing else. The option `CIVIC_LENS_PUBLIC_VIEWS_DATABASE` names that connection. `/v1/release`, the vote routes, and the bill routes use it. See [public API views](publication.md#public-api-views). The tradeoff is that an operational database outage stops the live API, while the cached pages stay up.
- The operational public-read views have two supporting indexes: a partial bill-identity index on action revisions and a list-key index including vote casts. These preserve the grouped bill lookup and cover vote-list tallies. Together the indexes measured 49.3 MiB in a synthetic write probe, with added WAL and write time. The warm diagnostic does not establish production cold-read latency.
- Party agreement uses a dedicated `public_api.party_agreement` view over active records and their exact vote revisions. It counts only alignment stored by publication, so the public API does not repeat party-majority or cast-tally rules.
- The service reads the public release files over HTTP. The base address is `CIVIC_LENS_RELEASE_BASE_URL`. A dev or test server can serve the release root.
- The ingest polls `release.json` every 30 seconds with a conditional GET. It sends the ETag and the Last-Modified time that the server gave. An unchanged manifest costs one empty reply.
- The ingest reuses the contract rules. `PublicationRelease.Validate` checks the manifest, and the `Validate` method of each record type checks the record. Search copies no contract rule.
- One release is ingested in one transaction. A release that the service stored already only becomes the active release again. A release that is older than the newest stored release and was never stored is refused, logged, and the service keeps serving the active release.
- Each row stores a range of a record revision: its first release and its last release. The last release is null while the range is open. A release that drops, withdraws, or replaces a revision closes its range. A revision that returns later gets a new row, so a pinned search in the gap never sees it.
- A query reads the active release by default. The active release is the number in `release.json`, so the service follows a rollback of the static site. A query can pin another ingested release with `release=N`.
- The schema is a set of numbered SQL files built into the project as embedded resources. The service applies them in order at startup under a Postgres advisory lock. A `schema_migrations` table records them. This departs from the EF migrations of the operational database. The service uses plain Npgsql, so it has no model to migrate.
- Search weighs the text of a record in three levels. The headline has weight A. The summary, the quoted text, the bill title, the relationship reason and quote, and the brief paragraphs have weight B. The first 200,000 characters of the source text have weight C.
- The summary text stops at 50,000 characters, and the source text stops at `PublicationProtocol.SearchSourceTextCharacters`. A Postgres tsvector holds at most 1 MB, and these limits keep the worst case below it. The search page states the source limit.
- Queries use `websearch_to_tsquery('english', q)` and `ts_rank_cd`. A snippet comes from `ts_headline` over the first 50,000 characters of the summary text of the record. A record with no summary text uses its body. The summary text is the published summary of a document change, statement, action, or vote. An action uses its manifest bill line instead, when it has one. A brief, a relationship, and an executive action have no summary text. The summary text is approved public text, so the snippet rules do not change. The snippet marks each match between U+E000 and U+E001, so a reader script never needs HTML from the service.
- Paging uses a keyset cursor, as the review UI does. The cursor carries its release, so all pages of one search read the same release. This service pages forward only, so the cursor has no direction.
- A request may name `sort` (`date`, `published`, `headline`, or `kind`) and `direction` (`asc` or `desc`). Without a sort, results follow the date order, and text ranks them. A sort overrides rank. The key `date` is the sort date, `published` is the first publication time, and `headline` sorts by the lower-case headline in code order (`lower(headline COLLATE pg_c_utf8) COLLATE "C"`). So case does not matter, "H.R. 10" comes before "H.R. 2", and accented letters sort after z. `kind` uses byte order. Dates and publication time default to newest first, and the other keys to ascending. Record ID breaks each tie in the same direction. A direction without a sort is refused.
- A sorted page has the cursor `s.<release>.<recordId>`. The query compares the key and record ID of each row with those of the cursor row, which it reads in the same release. Only the record ID is in the cursor, so the record ID is the only thing a client can forge. The cursor row must be in the release, or the page is empty. The cursors `d.` and `r.` belong to the date order and the ranked order.
- The vote, bill, and statement routes and `/v1/release` use the views data source. They never read base tables or search storage. The pool holds at most 4 connections, because the role allows 5. The role sets its own statement timeout, so the data source sets none. The pool closes a connection after 30 idle seconds. The pool prunes every 10 seconds, and the role ends an idle session after 60 seconds. So the pool always closes a connection first, and the next request never meets a closed one.
- `/v1/release` names the release that the views show, with its publication time from `public_api.active_release`. The search index follows `release.json` by polling, so for up to one poll the search results can name an older release. Search results keep their own `release` field.
- An active empty release keeps its identity, empty record lists, and zero figures. Missing records return 404. No active release returns 503. Record membership still comes from `public_api.active_records`.
- A vote answer holds the release that its own query read. A vote list query reads the active release and the rows in one statement, so they cannot differ.
- The vote cursor is `v.<release>.<date>.<chamber>.<session>.<rollCall>.<recordId>`. It holds the release and the whole sort key, as the dated cursor of search does. So a page needs no lookup of the cursor row. A client can forge any key. A forged key only moves the window over public rows. A cursor of another release gets 409 with the active release number.
- The vote routes send no cache header. The origin serves every request.
- Each vote row includes `bill_record_id` when its Congress, bill type, and bill number match a bill in the active published release. The view selects the lowest matching bill record ID; missing identity or no eligible bill yields null. It reads only the published `public_api.bills` view. The vote view therefore depends on the bill view, and rollback must remove or replace the vote view before changing the bill view.
- The bill routes follow the vote routes. The path of a bill holds its record ID. The congress, the bill type, and the bill number are filters, because the record ID is the key that every release file uses. `BillStore` reads `bills`, `bill_sponsorships`, and `bill_issues`. The bill list order is event date descending, then record ID. The view stores the event date and the cosponsor count, so the route computes neither.
- The bill cursor is `b.<release>.<date>.<recordId>`. The sponsorship cursor is `p.<release>.<position>`, because the path names the bill. `CursorFields` reads the fields of every cursor. `ViewColumns` reads the column types of every view. `VoteStore` and `BillStore` share both.
- `/v1/statements` lists bounded statement metadata from the active release. The `official`, `issue`, and inclusive `from`/`to` filters read published speaker and tracked-issue IDs. Results order by statement date newest first, with undated rows last, then record ID. The cursor holds the active release and nullable date key. Its one statement reads the release and page together; a cursor from another active release gets 409. The `statements` view requires a published revision with headline, summary, and at least one speaker, and excludes legacy revisions with missing metadata. `statement_speakers` joins through that eligible parent view, so it cannot reveal a speaker for an ineligible statement. List rows contain no source text, citations, quotations, authors, or review data.
- `GET /v1/statements/{recordId}` reads one active published statement and its evidence in one read-only statement. The response includes the complete bounded source text once, article URL, date evidence, and ordered quotations. `statement_sources.url` is the collection attempt's requested URL; the candidate article URL stays a separate field. The API derives quotation text with C# UTF-16 offsets. It invokes `PublishedStatement.ValidateContent`, shared with release validation, to reject wrong extraction IDs, invalid ranges, surrogate splits, and quote mismatches. No active release answers 503; an absent or unpublished statement answers 404. It reads only the active revision selected by the published statement view.
- `GET /v1/document-changes/{recordId}` returns one active revision, both complete source versions, ordered changed regions and word edits, and exact citations. Date evidence remains among those citations. The public contract caps complete responses at 2,000 changed regions and 512 word edits per region. One statement reads only the six document-change views and active release identity. A missing active release gives 503; an active empty release gives 404; malformed, unknown, or unpublished IDs give 404. Invalid stored evidence fails closed. The reader checks completion markers, child counts, positions, source identities, and UTF-16 boundaries before returning content. Model text carries the shared document-change AI label; person text has no label.
- The public address will be `api.civic-lens.info`. Every response allows any origin. The service sets no cookie. The search routes check no credential. The report pull route checks one shared bearer token.
- The rate limiter is the ASP.NET built-in fixed window. It keys on `CF-Connecting-IP` only when the connection comes from a configured trusted proxy range. In production that range is loopback, because Caddy and the tunnel run on the same machine. Otherwise it keys on the remote address. An IPv6 client counts as its /64 network.
- A record file holds the full source text. The service indexes it and does not serve it. The API returns index rows and the paths of the record files.
- Publish writes `search.html` in every release. Its canonical address, when `CIVIC_LENS_PUBLIC_BASE_URL` is set, is the bare page without a query. The page fills its filters from the manifest. Issue and policy area names come from the publication catalog. A script calls the service at `CIVIC_LENS_PUBLIC_API_URL`. Without the variable, the page says that search is not available.
- The facet pages are the path for readers without JavaScript.
- Readers send a report with `POST /v1/reports`. The body is form-encoded, so the browser sends a CORS simple request and needs no preflight. The route keeps `Access-Control-Allow-Origin: *` and sets no cookie.
- The service stores nothing about the reporter. It keeps no IP address, no hash of one, and no contact field. The client address only keys the in-memory rate limit. The service logs neither it nor the query text of a search. `PublicApiApp` sets the log level of `Microsoft.AspNetCore` to warning, because the information request logs hold the request address with the query. Test: `SearchEndpointsTests.ASearchWritesNoQueryTextToTheLogsBecauseThePrivacyTableOfTheAboutPagePromisesNothingIsSaved`. A response sets no cookie. Tests: `SearchEndpointsTests.EveryResponseAllowsAnyOriginAndSetsNoCookie` and `ReportEndpointsTests.AReportAnswerSetsNoCookieBecauseTheAboutPageToldReadersThatNoCookieIsSet`.
- The checks run in this order: the shape of the form, the Turnstile check, then the database write. The route reads at most 32 KB of body. An unknown pair of record ID and revision answers 404.
- A report binds to a record revision in the `records` table, in any release range. A report on a replaced revision is accepted, because a reader may hold an old page. The row stores the kind from that table.
- Cloudflare Turnstile checks each report in the service. `TurnstileVerifier` sends the token and the secret to the siteverify API and nothing else. It needs `success` and the configured hostname. A 5 second timeout, a failed call, an unreadable reply, or the code "internal-error" gives 503, so the check fails closed.
- `TurnstileVerifier` is a concrete class at the Cloudflare boundary, as `ReleaseFeed` is at the release boundary. The service registers it only when a secret is set. Tests give `PublicApiApp.Build` a fake `HttpMessageHandler`, as they do for the release feed.
- Without `CIVIC_LENS_TURNSTILE_SECRET` the report route answers 503 "reports are not available".
- Publish writes `report.html` in every release, and every record page links to it; see [publication](publication.md#report-a-problem). The page needs `CIVIC_LENS_PUBLIC_API_URL` and `CIVIC_LENS_TURNSTILE_SITE_KEY`. Without them, it says that reporting is not available.
- Three limits protect the route. The `reports` rate limit policy allows 5 reports each hour for each client, and the global limiter still applies. A durable cap allows 200 reports in 24 hours and is checked inside the insert transaction. A unique index on record ID, revision, and payload hash makes a duplicate a no-op with the same success answer.
- The insert takes the advisory lock `civic-lens-search-reports` and holds it to the commit. Identity values then commit in order, so a pull never skips a late commit. No search transaction holds two keys.
- The operational application pulls the reports with `GET /internal/v1/reports?after=<cursor>&limit=<n>`. The route needs `CIVIC_LENS_REPORT_PULL_TOKEN`, at least 32 characters. Without the variable the route does not exist. The token is compared with `CryptographicOperations.FixedTimeEquals`.
- The cursor is `<epoch>.<sequence>` and moves forward only. The epoch is a uuid that the first migration creates once. A cursor of another epoch starts from the first report, so a reset or restore never skips reports. The puller dedupes by report ID.
- The `after` value acknowledges every report at or below it. The acknowledged sequence in `report_pull_state` never moves back.
- `IngestWorker` also purges reports. It deletes a report only when its sequence is at or below the acknowledged sequence and it is older than 7 days. This keeps one timer loop, so no new hosted service exists.
- The wire types `PulledReport`, `PulledReportBatch`, and `ReaderReportProtocol` are in `CivicLens.Publication.Contracts`. They are not release files, so `PublicationProtocol.SchemaVersion` does not change. The cursor format is owned by `ReportCursor` in the service, because it is opaque to the puller. `ReaderReportProtocol` also owns the retention days that publish shows on `about.html`.
- The operational application pulls the reports with the stage `reportPull`; see [operational pull](#operational-pull).
- The route `/internal/*` is not public. The Caddyfile answers `/internal/*` with 404 on the API host; see [Web server](../operations.md#web-server).

## Invariants

- Document detail binds content and evidence to the active published revision. Date evidence never removes an approved citation. Enforcer: `DocumentChangeStore` and `PublishedDocumentChange.ValidateContent`. Tests: `DocumentChangeEndpointsTests` covers exact sources, date citations, unpublished revisions, release activation, rollback, and malformed persisted content.
- Document detail bounds child payloads before deserialization. Enforcer: guarded SQL markers, sentinel limits, and the bounded issue array in `PublicApiDocumentChangeDetail`. Tests: `DocumentChangeEndpointsTests.DetailFailsClosedWhenPublishedEvidenceIsIncompleteOrInvalid` and the boundary tests in `PublishedDocumentChangeTests`.

- Statement lists bind metadata and ordered speakers to the active published revision. Cursor walks include dated ties and undated rows once. Enforcers: `StatementStore`, `StatementEndpoints`, and the statement views. Tests: `StatementEndpointsTests` and `PublicApiStatementListsMigrationTests`. The official lookup stays correlated through the speaker view, following `PublicApiRecordLinkReason`. No test protects the query plan. A reduced-schema check with 20,000 statements ran combined filters in 147 to 150 ms on one CPU. This is warm local SQL evidence, not a cold production check.
- Statement detail returns only the active published revision and validates every returned citation against its source with the contract's UTF-16 rules. Enforcers: `StatementStore`, `PublishedStatement.ValidateContent`, and the detail views. Tests: `StatementEndpointsTests` and `PublishedStatementTests`.

- A public bill needs at least one sponsorship row on its published revision. A cosponsor alone qualifies. An existence check owns eligibility; the separate sponsor count runs only when a reader needs it. Enforcer: `PublicApiBillLookup`. Tests: `BillEndpointsTests.BillsNeedASponsorshipButDoNotRequireTheSponsorRole` and `HomeEndpointsTests.TheBillLineIsTheLineThatTheStaticBillLinesGiveWhenTheBillRecordsAreInTheActiveRelease`.

## Behavior

`GET /v1/party-agreement?chamber=house&congress=119` returns the active release number and either a chamber agreement or null. Each kind reports stored agreed, split, mixed, and total counts. The result adds their sums and the nomination count. The aggregate reads a dedicated restricted view and the same query checks whether any active vote has unknown Congress. It does not infer Congress from the record date or derive agreement from cast totals.

`GET /v1/boards` returns the active release, the four boards from `OfficialBoardPage.All`, and one agreement for each chamber at its selected Congress. The answer is built in one repeatable-read snapshot. Each member carries the dated seat terms that overlap the board's chamber and Congress. A seat change retains both terms and their dates. The party-pinned `member_votes` groups establish board membership, including members with zero qualifying split casts. `official_party_lines` supplies the stored count and break values. Unknown party pins, unwritten alignments, or an unknown vote Congress make all board results and both agreements null. Incomplete data cannot become an empty board or a zero count. No active release returns 503. Tests: `BoardEndpointsTests`.

Bill detail responses add nullable `crsSummaryText` and `crsSummaryVersion`. They expose the exact stored CRS body and its composite version from the published action revision. Both stay null when the revision has no stored body. Bill list responses omit these full-text fields. Header metadata stays in the cited evidence block. No public read accesses an extraction table. Tests: `BillEndpointsTests.CrsSummaryUsesThePublishedRevisionAndExposesOnlyItsBodyAndSummaryVersion` and `PublicApiCrsSummaryMigrationTests`.

`GET /v1/bills/{recordId}/actions` pages the completed history pinned by the active release. It returns release, optional history metadata, actions, and next cursor. Metadata contains the capture observation time and action count. Actions retain official position, date, optional time, text, type, action code, and source-system fields. The cursor is `ba.<release>.<position>`, with the existing default 20 and maximum 50 rows. A stale cursor returns 409 for a published bill. An absent bill returns 404 first, following sponsorship paging. `BillDetail` adds nullable history metadata, and bill rows add nullable `publicLaw`. Tests: `ActionHistoryEndpointsTests` and `ActionHistoryCursorTests`.

`GET /v1/briefs/{recordId}` returns the active brief, its paragraphs, and its citations in one database statement. It reads public views only. Paragraph citation IDs preserve their order, and citation headlines come from the exact cited revisions. `PublishedBrief.ValidateContent` owns the shared content checks. Missing or invalid IDs and no active release return 404, following the existing bill-detail route. Tests: `BriefEndpointsTests.EndpointReturnsOrderedTextWithPinnedTargetHeadlinesAndRollbackRestoresAWithdrawnBrief` and `PublicApiBriefContentViewsTests`.


### Ingest

`IngestWorker` runs `ReleaseIngest` when the service starts and then every 30 seconds. A failed run logs the error and waits for the next interval. A run that lasts longer than the interval starts the next run at once.

1. `ReleaseFeed` sends a conditional GET for `release.json`. A 304 reply ends the run.
2. It checks the size against `PublicationProtocol.MaximumManifestBytes`. It reads the manifest under `PublicationProtocol.JsonOptions` and calls `PublicationRelease.Validate`.
3. `ReleaseIngest` opens one transaction and takes an advisory lock. If the manifest release is stored already, it only sets the active release and ends the run.
4. It stores the release row. It reads the stored revisions. A revision that the manifest lists and the table holds only as closed gets a new row that copies the stored text. An open revision that the manifest lacks is closed at the newest stored release.
5. For each listed revision that the table lacks, it fetches `records/{id}.json`. `RecordReader` reads the file as the type of its kind and calls its `Validate` method. It builds the weighted texts and the service inserts the row. It then sets the active release.
6. A record that fails to read or validate, for any reason except cancellation, is skipped and reported in the result. The worker logs it. A failed fetch or a database error rolls the transaction back.
7. The feed keeps the ETag and Last-Modified values after the release is stored, so a failed run reads the manifest again.

### Search

`SearchIndex` runs two kinds of query. With text, it matches `websearch_to_tsquery` and orders by `ts_rank_cd`, then by record ID. Without text, it orders by event day, else the UTC day of the first publication, then first publication time newest first, then record ID.

Each filter is one value: `kind`, `official`, `issue`, `policyArea`, `source`, and a `from` and `to` date range on the event date. The filters combine with AND.

Only a search with text returns a snippet. A search without text returns none.

### Server pages

The service renders public components to static HTML with `PageRenderer`, which wraps `HtmlRenderer`. A page has no interactivity, no SignalR, and no WebAssembly. `ServerPageResponder` is the pipeline of every server page. It reads the active release from `public_api.active_release` through `ActiveReleaseReader`, checks the validator for a successful page, answers 304 on a match, and renders otherwise. It sets cache headers after rendering, so a failed render has none. `PageCache` owns semantic freshness and emits the weak ETag `W/"r{release}-{build}-{origin}"`. The build is the git SHA that `SourceRevisionId` bakes into the assembly (`BuildId`). The origin fingerprints the normalized public base URL and browser API URL once at startup. When server pages are enabled, a missing or invalid SHA stops startup. The SHA must be exactly 40 lowercase hex digits, as in the application build rule. Every rendered page response has `Cache-Control: public, s-maxage=60, stale-while-revalidate=600, stale-if-error=86400`. The edge revalidates with `If-None-Match`. Only a successful page can answer 304, which skips rendering. A matching weak or strong tag, or wildcard, matches. A not found page keeps its 404 status and body. A page holds nothing that depends on the reader: no cookie, no query value, and no Vary by cookie. Caddy compresses responses and adds `no-transform` at ingress for `/web` and the ZIP member fragment, including 304 responses that have no content type. It adds `Vary: Accept-Encoding` for identity and compressed responses, preserving upstream cache and variation fields. The cached members strip is an empty slot, `MembersStripSlot`, with only configured public/API URLs. The browser fills it from the ZIP and release marker saved on the device. Home and Compare reuse their full private response; other server pages request `view=strip`. Only a successful unfiltered full lookup advances the marker. `PublicPage` includes the slot when the service registers `MembersStripSlot`. A static Home adds it after a successful lookup.

The prefix of the server pages is `/web`. The home and Compare routes are explicit. Other `/web/{**path}` paths answer with the PublicWeb not found page and status 404, with the same cache headers. With no active release the route answers 503 with no validator. No live route moves yet, so the static pages stay the production path.

`SharedAssetEndpoints` serves the shared files of `PublicAssets.Paths` at the paths of the static release, for example `/assets/css/app.css`. Each file has an ETag of its SHA-256 hash and the value `public, max-age=60` of the static release. No shared file has a hashed or versioned name, so none has a long cache value.

The ZIP member route renders `ZipMemberCards` from one existing `ZipDistrictStore` snapshot through `ZipMemberCardsMapper`. It reuses `PageRenderer` without the full-page cache pipeline. The browser requests HTML, validates the content type and ZIP, release, and Congress metadata, then inserts the fragment. Shared page HTML stays free of personal data. Only the validated five-digit ZIP is remembered on the device after a successful current answer. Loading, retry, stale-response, focus, and Forget behavior remain in `initZipLookup`.

### Search page

`PublishedSearchPage` renders `search.html`. The form stays hidden until `public.js` runs. The kind filter lists the seven kinds. The official and source filters list the distinct values of the release manifest. The issue and policy area filters show catalog names. The script calls `/v1/search`, shows each result with its snippet, and loads more results with the cursor. It builds the snippet with `mark` elements, never with HTML from the service. The page address holds the query as `q` and the filters as `kind`, `official`, `issue`, `policyArea`, `source`, `from`, and `to`, with only the non-empty values. It never holds a cursor, a result page, or a release. The script ignores a `release` parameter. A submit writes history: `pushState` when the parameters change, `replaceState` when they stay the same. Typing does not change the address. Back and forward fill the form from the address and search again, without a history write. An address without parameters, or an empty form, clears the results. It calls no service. The hint reads "Type a topic or a bill number, or choose an official above". A search with no match says "No records match". It then gives next steps. They link to the issue and official pages. The status line counts the results on screen, as "N results so far" while a next cursor exists and "N results" on the last page. One result says "1 result". The line never shows the release number. Each result lists the issue names, not the issue IDs. A `noscript` box before the form tells readers without script where to browse. A page load fills the form from the address, searches when a value is left, and rewrites the address from the form values. A select value that the release does not list becomes Any, and the browser empties a date that is not valid. A new search clears the earlier results and the cursor first. Typing drops a reply that is still in flight, clears the status line, and hides More until the next submit. A jump to a fragment, such as the skip link, does not search again. The service owns the limits, and a 400 shows a message to change the words or filters.

### Operational pull

- The worker runs the stage `reportPull` when `CIVIC_LENS_REPORT_PULL=1`. It ticks at start and then every 5 minutes by the database clock, from `PostgresIntervalWakeup`. The publishing stage uses the same class with a one hour interval. The settings are in [operations](../operations.md#reader-report-queue).
- `StageWorker` runs `PullReaderReports` for each tick. The handler asks for a page with the saved cursor, checks the page, and stores it. It repeats until a page is empty or until the service sends the same cursor again. The queue is in [review](review.md#reader-reports).
- `HttpReportPuller` is a concrete class at the service boundary, like `TurnstileVerifier`. It sends the bearer token and the opaque cursor. The service address may hold a path prefix, with or without a trailing slash. A call has a hard limit of 30 seconds. The client reads at most 4 MB of reply, as the release feed of the service caps its reads. A failed status, an unreadable reply, or a timeout throws, and the stage counts one failure. The token is in no message.
- The application never parses or builds the cursor. It saves `NextCursor` as the service sent it and sends it back as the next `after` value.
- `PulledReportBatch.Validate` runs at the pull, because the service is an outside boundary. It checks the report rules of `ReaderReportProtocol`, the record ID rule of `PublicationProtocol.IsAnyRecordId`, the batch size, and the cursor length. A bad batch is refused as a whole. Its reports and its cursor are not stored.
- `PostgresReaderReportStore.SavePulledAsync` inserts the new reports with `ON CONFLICT (report_id) DO NOTHING` and saves the cursor in the same transaction. A replay after a change of epoch adds no second row and does not change a report that is resolved.
- Unlike the service, the operational application purges nothing. A resolved report stays in the queue.

## Storage and contracts

`public_api.vote_first_publications` exposes each active vote's record, revision, and release with its earliest retained publication release. It groups all retained state ranges for that vote, so revisions and returns preserve original publication identity. Only the restricted view owner reads those base ranges. The public role has SELECT on the view.

- The generated schema reference does not cover this database. The tables are `releases`, `records`, and `schema_migrations`, in `src/CivicLens.PublicApi/Schema/001_search_index.sql`. The tables `reader_reports` and `report_pull_state` are in `002_reader_reports.sql`. File `003_drop_report_release_number.sql` drops the unused release number column of `reader_reports`. File `004_record_bill_line.sql` adds the column `bill_line` to `records`. File `005_record_summary.sql` adds the column `summary` to `records`.
- `releases` holds each ingested release number and its publication time.
- `records` holds one row for each record revision. A row holds the manifest entry fields and the bill line of an action. It holds the summary text for snippets and the body text. It also holds the weighted `search` vector, `first_release`, and `last_release`. GIN indexes cover the vector and the three ID arrays.
- `reader_reports` holds `sequence` (identity), `report_id`, `record_id`, `revision_number`, `kind`, `category`, `body`, `payload_hash`, and `received_at`. CHECK constraints bound the numbers. A unique index covers record ID, revision, and payload hash.
- `report_pull_state` holds one row: the `epoch` uuid, created once, and the `acked_sequence`.
- `PulledReport`, `PulledReportBatch`, and `ReaderReportProtocol` define the pull wire format. `ReaderReportProtocol` also owns the retention days that publish shows on `about.html`.
- The service reads the same contract types as the static site: `PublicationRelease` and the seven record types. `PublicationProtocol.SearchSourceTextCharacters` and `PublicationProtocol.SearchPagePath` are shared with the page.

## Limits and planned work

Planned: `/v1/records/{kind}/{recordId}/corrections` will serve ordinary correction histories for all seven record kinds. It will read the active release's immutable history snapshot through restricted views. Server-rendered pages will reuse its reader within their page snapshot. The endpoint will not add a historical release selector. Publication owns the snapshot preparation and release binding.

- Server pages cover the gated Home preview, the public Compare page, and the not found page. Remaining reader routes move under [R-68](../roadmap.md#active-r-68-redesign). A shared file has no hashed name, so it has no long cache value yet.
- The API exposes stored vote alignment, member party and caucus, vote side and party-majority cast, and official photo paths. A vote member's party comes from the party pinned to its member list. Caucus comes from the active release's matching chamber term on the vote date; when no matching term exists it remains null. Side maps Yea/Aye and Nay/No to their shared side, leaving other casts null. Party-majority cast uses the stored Democrat or Republican majority for the member's pinned party, leaving other parties and ties null. Photo paths come from the release and are already restricted to publication photo paths.
- Issue split and agreed counts, and an agreed or split mark on a home vote are not served yet. The issue count of executive actions is still not built, because release entries for executive actions hold no issue. It waits until executive actions carry issues.
- The official routes still lack party-line vote counts and statement counts by Congress or issue. Publication stores entry Congress and the API exposes photo paths and vote fields, but the remaining aggregates and routes are not built.
- The sponsored bill count of an official counts a bill in the Congress of its bill number. The static page counts it in the Congress of the last event date, and it counts cosponsored bills over the whole release. The two can differ for a bill whose last sponsorship event falls in a later Congress. The API figure equals `billsInCongress`, the base next to it.
- The counts of an official include only records that have an entry row. A record without the row is not counted until `releases entries backfill` writes it. The base `actionsInRelease` counts every active executive action, so it can be larger than the sum of the counts.
- Each page of the list reads every entry row of the release. The order is by name, and the count comes from the entry table. At 540 officials and 40,600 official rows, one page takes about 46 ms. If the entry table grows much larger, the list needs a stored count.
- The ZIP lookup ends a term at the database date of the request. Official pages end it at the publish day of the release. On the day a term ends, the two can disagree until the next publish, which takes about one hour. The ZIP answer cache adds up to one hour. The owner accepted this.
- A release from before the name tables has no name rows. The ZIP route answers 503 until the next publish writes them.
- The timeout answer of a vote or bill read says "the search took too long", because `ApiResults.GuardAsync` has one wording.
- The `issue` and `sponsor` filters of the bill list match an ID as given. An ID that no bill carries gives an empty page, because `PublicApi` holds no issue or official catalog.
- The release manifest stays the data path of the static pages until the pages read `PublicApi`.
- The record page routes give no source quote, no source link, and no source text. Those parts exist only in the release record files. The view `public_api.record_links` needs no file. The owner decided where the quote will live. The revision writer will store the quote text on each citation row, written once by C#, and a view will read that plain column. The full source text stays in the static files until a page needs it. This is planned. No column and no writer change exist yet.
- The bill detail gives the raw latest action and no plain meaning. `BillStatusMeaning` is in `Publication.Contracts`, so `PublicApi` can use it. No route calls it yet. The bill page PR will add the call.
- The executive action route serves one action by ID. A list of executive actions is not served yet.
- The vote list filters the bill by type and number without an index on those columns. A plan reads every vote revision of the active release. This is fast at 1,600 votes. Add an index when the vote count grows.
- One worker pulls. Two workers would pull the same pages. The unique report ID keeps the queue correct.
- The pull address and token are set by hand in the worker environment. [R-24](../roadmap.md#later) sets them in the container configuration.
- The rail and the Review home page link the queue. The operational application sends no notice when a report arrives.
- The per-client report limit lives in memory and resets when the service restarts.
- There is no reporter identity. Abuse handling relies on Turnstile and the caps. A flood can fill the daily cap and close reports for the day.
- A duplicate sent at the daily cap gets 503 like any other report.
- The pull trusts the cursor of the token holder. A cursor above the highest sequence acknowledges reports that the puller never saw.
- A search database restored from a backup keeps its epoch. Reports made after the backup are lost, and the puller can skip new reports that reuse the lost sequences.
- The request log filter in `PublicApiApp` has no provider. A provider-specific `Logging` level, such as `Logging__Console__LogLevel__Default`, overrides it and logs the search text again. The [R-24](../roadmap.md#later) deploy must set none.
- The About page says a search keeps nothing. That stays true only while the Caddy deploy keeps no access logs for search requests. The Caddyfile sets that; see [Web server](../operations.md#web-server).
- Edge blocking of `/internal/*` is deferred to [R-24](../roadmap.md#later).
- The search API answers 200 for a withdrawn record in the pinned releases that hold it. A status 410 needs the ingest to read withdrawals and the API to change its status. This waits until after [R-24](../roadmap.md#later).
- Only the first full ingest is long, because it fetches every record inside one transaction. Later ingests fetch only new revisions. Readers are not blocked, because they read committed rows.
- A release that was never stored and is older than the newest stored release is refused and logged. The service keeps serving the active release. This happens only if the service missed a release and the site rolls back to it.
- One service runs per search database. Two replicas could move the active release back and forth when they read different copies of the site.
- A local proxy or tunnel in front of the API makes every reader share one rate limit bucket. The R-24 deployment must pass the client address as `CF-Connecting-IP` from a trusted range.
- The ingest reads and inserts one record at a time. It does not read every record before the first insert, because a full corpus could use more memory than the host has.
- A record that fails validation stays out of the index. Later releases try it again, because it is not stored.
- The index keeps every revision of every release. Storage grows with published revisions. Review this with the retention rule of [publication](publication.md#limits-and-planned-work).
- A search without text returns no snippet.
- A snippet scans the first 50,000 characters of the summary text, or of the body when the row has no summary text. A match later in that text gives a snippet from its start.
- A row that was indexed before `005_record_summary.sql` holds no summary text, and its snippet comes from the body. The ingest never fetches a stored revision again. So the rows get their summary text only after the operator [resets the search index](../operations.md#reset-the-search-index). A reset also drops the earlier releases, so a pinned search of an older release is not possible until the ingest stores that release again.
- Planned under R-68: the typed ingest takes the summary text from published data. The published views already hold it: `summary` of `public_api.statements` and `public_api.bills`, and `bill_line` of `public_api.bills`. The rule stays the same: the bill line for an action when it exists, else the summary. The ingest then fills the column for each revision on its first read, and the reset is no longer needed.
- The `Dockerfile` target `search` builds the service image. [Container images](../operations.md#container-images) describes it. [R-24](../roadmap.md#later) adds the cloud deployment.
- Planned under R-68: search ingestion moves from public release files to typed published data before static retirement. Then public `release.json` and its unused serving code are removed. Private snapshots remain while verification or recovery use them.
- Planned public MCP ([R-25](../roadmap.md#later)) uses the public API and the same release pinning from a separate deployment.
- A row that was indexed before `004_record_bill_line.sql` holds no bill line, and no code fills it. A new revision gets its line when the ingest stores it. A vote hit holds no line, because the line of a vote comes from the action of its bill in the release build.
