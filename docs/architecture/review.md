# Review

## Purpose

The review feature is the private editorial workspace. People draft, revise, and decide on proposed public records beside their evidence. Every decision binds to an exact immutable revision. This page covers document changes and the decision rules that statements, actions, and votes share. Statement-specific review is in [statements](statements.md#statement-review). Action-specific review is in [actions](actions.md#action-review). Vote-specific review is in [votes](votes.md#vote-review). Brief-specific review is in [briefs](briefs.md#brief-review).

## Decisions

- One authorized operator may both draft and approve a record. A separate approver is not required, and self-approval is allowed.
- The owner can draft, review, and manage editorial access, and can publish with the CLI. The code subject publishes through the worker stage; see [publication](publication.md#automatic-publication). The additional reviewer can draft and review, but cannot publish or manage access.
- Each person signs in with a separate Auth0 identity, and each decision names its actor. Sign-in alone grants no editorial access.
- Authorization is enforced at mutation boundaries, not only by hiding UI controls.
- Server configuration maps exact subject IDs to roles. Client role claims confer no permissions.
- Access changes need a server configuration update and a restart. There is no management UI.
- Approval binds to the exact public wording and evidence versions reviewed. An edit to either needs a new review. Earlier approvals stay as history and do not authorize the new revision.
- Approval and publication are separate actions.
- Code approves an executive action record at admission, and a worker revision of an action or a House vote. Their facts come from Congress.gov and the Clerk XML, and code checks every citation. The actor of that decision is the reserved subject `civic-lens:code`. Code also approves a worker revision of a statement that passes the checks in [statements](statements.md#statement-code-approval). People approve all other statements, relationships, briefs, document changes, and every revision that a person writes.
- Code approves a worker revision only if three rules hold. No concern is open. The revision holds no text that a person wrote. The approval checks pass. If one rule fails, the revision waits for a person. A person who withdraws an approval or requests changes therefore stays effective across worker redrafts. A record that review blocked in this way can be withdrawn from the release; see [publication](publication.md#corrections-and-withdrawal).
- A person can reject a record whose current revision is not approved. A rejection needs one reason code and may carry a note. The codes of each kind are a closed list that `ReviewReasons.For` owns. A statement has `NotAStatement`, `WrongSpeaker`, `IndexPage`, `LowSubstance`, `InaccurateSummary`, and `Duplicate`. A relationship has `NotRelated` and `Duplicate`. A document change and a brief have `InaccurateSummary`, `Duplicate`, and `LowSubstance`. An action, a vote, and an executive action have `InaccurateSummary` and `Duplicate`. There is no "Other" code, so rejections can be counted by cause. A rejected record leaves the Needs a person queue and never publishes. It is not a concern. The worker cannot reopen it: its append steps refuse a rejected record, as the brief and relationship steps already refuse an approved record. A person reopens it by saving a new revision or by Request changes, which is a concern again. A person reverses the rejection by approving it. Both decisions stay in the history. An approved record uses Withdraw approval.
- A person can still edit and withdraw a fact record. A person edit is a revision that waits for a person to approve it.
- Writes use expected versions, not editing locks or last-write-wins. The UI never silently merges editorial wording.
- Decisions are immutable. They cannot be edited or deleted.
- A saved revision never resolves a concern by itself. Only an explicit approval with a resolution note does.
- Shared Application handlers own these rules for the UI, the CLI, and future MCP callers.
- Document changes, statements, actions, votes, and briefs share one decision policy, `ReviewPolicy`. Briefs reach it through `ReviewRecords`.
- A review cycle starts at the latest approval. Reads load the current revision, the last approved revision, and the decisions since that approval. A cycle has no revision cap. The cap of 64 decisions after the opening one bounds its decisions.
- One step appends a revision and computes `review_status` again. Person saves and analysis appends both use it. One step records a decision, and the person path and the code path both use it.
- `review_status` and `has_changes` are stored columns that C# computes. SQL filters read them, so SQL keeps no copy of the policy.
- Autosave and live preview are not part of the first workflow.
- A person saves and approves in one step. The record editor opens with the edit form. The button "Save and approve" has two paths. When the input differs from the current revision, it writes the new revision and its approval together. When the input equals the current revision, it writes no revision and approves the current one. The comparison ignores line break style, the order of chips and cited passages, and an empty optional field; see [Revisions](#revisions).
- One class, `RevisionBackfill`, owns the revision backfill and verify for every kind that has columns. It owns the batch, the savepoint for each row, the refusal mapping, and the verify counts. A kind gives its lock, its legacy test, its page reader, and its column, movable, and comparison rules. The kind store keeps the `IRevisionBackfillStore` boundary.

## Behavior

### What reviewers check

The workspace centers the proposed public record beside its supporting evidence. Document history and comparisons support the investigation. Reviewers assess wording, quotation fidelity, attribution, dates, context, citations, and interpretation.

- For a document change, reviewers separate a substantive source edit from navigation churn or a processing change.
- For a relationship, reviewers verify the claimed connection. The page shows the statement passage beside the facts of the target, and a flag when a cited record changed.
- For a brief, reviewers verify each assertion against the cited revision and read the coverage description. A brief shows a flag when a cited record changed.

An explanation of significance is an editorial judgment that needs review. A text difference never makes it automatic. A comparison alone does not show substantive significance.

### Drafts

A document-change draft starts from an explicitly selected, complete saved comparison with an actual text change. There are three paths:

- The worker writes an AI draft of each complete text change; see [analysis](analysis.md).
- An operator explicitly creates a draft from a saved comparison.
- A reviewer starts a draft by hand.

A change has at most one draft. Starting a draft for a change that already has one opens the existing draft.

The public record holds:

- a headline and a plain-language summary
- optional evidence-supported significance
- limits and uncertainty
- the source institution and supported official links
- configured issue categories
- bindings to the exact comparison, the before and after versions, and the cited passages

The earlier and later observation dates stay distinct from the actual change date. The record includes a change date only when evidence supports it.

### Revisions

Each explicit save keeps an immutable revision of the wording, attribution, issue selection, and evidence bindings. Each record has one current revision. Incomplete drafts can be saved. Approval of a document change needs a headline, a summary, an institution, at least one valid citation, and explicit resolution of all outstanding concerns. An actual change date needs a selected exact citation.

Editing an approved revision creates a new unapproved revision. The historical approval and any published record do not change. The UI warns before a person leaves unsaved edits.

The record editors of document changes, statements, actions, votes, relationships, and briefs open with the edit form. Under the form, "Save and approve" takes a note, the open concerns that the person resolved, and a correction note. It saves the typed wording as the next revision and approves that revision. When the typed input equals the current revision, it writes no revision. It approves the current revision, and the revision keeps its number, its text origin, and its author. When that revision is already approved, it refuses with "Nothing to save." An AI date that a person confirms always needs a new person revision. The approval binds to the new revision number and to the review state version that the page showed. The editor still has the suggestion buttons, which save with no approval. "Request changes", "Reject", and "Withdraw approval" stay in the decision panel and apply to the saved revision. "Reject" shows a required reason list for the kind of the record and takes an optional note. `DraftStatusDisplay` owns the plain label of each reason and of the Rejected status. The panel hides "Reject" for an approved or a rejected revision. The executive action editor has no edit form, so its decision panel keeps "Approve".

Review shows a revision beside the supporting before and after passages. Technical identifiers stay in the evidence details.

Initial citations select positive ranges from the first 32 comparison hunks. The editor offers all hunks for explicit selection within the citation limit.

### Review decisions

A saved revision starts awaiting review. A decision targets an exact revision and keeps the authenticated actor.

| Decision | Effect and requirements |
|---|---|
| Approve | Marks the revision suitable for publication after checking wording, attribution, dates, context, citation fidelity, and substantive significance. One authorized approval suffices. For a worker revision of an action, a vote, or a statement, code approves after its checks pass; see [Code approval](#code-approval). An approval can carry a correction note for readers, 1 to 500 characters. The worker publishes the note as a correction when the approved revision replaces a public record. No other decision takes this note. See [publication](publication.md#corrections-and-withdrawal). |
| Request changes | Blocks publication until explicitly resolved. Needs a note that describes the needed corrections. |
| Withdraw approval | Invalidates the effective approval and blocks future publication. Needs a reason. |
| Reject | Closes a record that is not worth a decision, such as a junk draft. Needs a reason code. The note is optional. Only a current revision that is neither approved nor rejected can be rejected. The record leaves the Needs a person queue and shows in the Rejected list. The rejected revision does not publish. It is not a concern, so a later approval resolves nothing for it. A person can approve the rejected revision later. |

Either reviewer can raise a blocking concern. A later approval must acknowledge the outstanding concerns and include a resolution note. It records the exact outstanding decision IDs it resolves. The original decisions keep their original revision bindings. Unresolved concerns carry forward as publication blockers when a new revision is saved.

### Code approval

`ReviewRecords.AppendCodeApprovedAsync` appends the worker revision of an action, a vote, or a statement. It then writes an Approve decision in the same transaction. The decision names the new revision number and the next review state version, and its actor is `civic-lens:code`. It uses the same approval checks as a person: `ValidateForApproval` with the saved extractions, and `ReviewPolicy.ValidateDecision`. The decision row, the state version, and the status come from the one step, `RecordDecision`, that `DecideAsync` also uses.

The settlement calls `AfterCodeApprovalAsync` after it adds its run row. That call runs the after-decision hooks of the record kind in the order that a person decision uses: relationship staleness, then brief staleness. The hooks save the context, so they must run after the run row exists. The worker already holds the review key of the kind. The hooks then take the later keys in the declared order; see [Advisory locks](../architecture.md#advisory-locks).

A failed check stores no decision. The record stays awaiting review for a person. The draft row keeps the message of the failed check in `held_reason`. A concern that is open, or text that a person wrote, sets no reason. `AppendRevision` and `RecordDecision` clear the reason, so it always describes the newest revision.

Statement code approval runs its checks in `StatementDraftStep`, on the extraction that the claim read. This is safe for four reasons. The extraction and the admitting configuration revision never change. The issue configuration is fixed for each process. A regate requeues only gates with `NoTrackedIssue`. A human draft that appears during the call makes `TryAddAnalysisDraftAsync` return false, so the code approval is dropped with the draft. `StatementAllowedSelections.RequireApprovable` is the single path for these checks. Only the date rule differs: code passes `dateReadByCode` when it read the date from the release.

### Status states

The check constraints on `document_change_drafts`, `statement_drafts`, and `action_drafts` list the stored statuses. Statements add NotDrafted. `ReviewPolicy.GetCurrentStatus` computes it after each write: the latest decision on the current revision sets it, and without one it is awaiting review. `ReviewPolicy.GetInitialStatus` gives the status of a new draft row, which has no decisions.

| From | To | Write |
|---|---|---|
| NotDrafted | AwaitingReview | The first revision, by a person or by analysis |
| Any status | AwaitingReview or AwaitingReviewWithConcerns | A saved or appended revision, with or without open concerns |
| Any drafted status | Approved | Approve, or a code approval. Approve must resolve every open concern |
| Any drafted status | ChangesRequested | Request changes |
| Approved | ApprovalWithdrawn | Withdraw approval |
| Any drafted status except Approved and Rejected | Rejected | Reject |

### Review cycles

A review cycle starts at the latest approval of a record. A record with no approval has one cycle that starts at its first decision. An approval resolves every open concern, so the decisions before it never change the status or the open concerns.

- Reads load the current revision, the last approved revision, and the decisions of the cycle. The AI draft outcome list loads revision 1 through `ReviewRecords.ReadFirstRevisionsAsync` for the model draft. The statement read loads it too, but uses only the run of revision 1. No read loads other revisions or older decisions.
- A read checks the approval at the start of the cycle against its revision, and replays every later decision against the policy.
- The history panel shows the current and the last approved revisions, and the decisions of the cycle. `ReviewHistory.LoadedRevisions` builds that revision list, and each review aggregate carries it as `Revisions`.
- A cycle has no revision cap. The decisions of a cycle are bounded by the open-concern cap; see [Invariants](#invariants).

### Concurrency and replay

- A draft save checks the expected current revision atomically.
- A stale save returns a conflict. It keeps the unsaved text of the operator for comparison with the latest revision.
- A stale "Save and approve" saves and approves nothing. The save step checks the expected revision first. The approval step checks the review state version.
- A review decision checks the expected current revision and the review-state version atomically. A changed revision or an intervening decision needs a refresh before the person decides.
- An idempotent retry of the same successful request returns the original outcome. It creates no duplicate revision or decision.
- Keys are scoped to the authenticated actor and operation and bound to the request payload. Reuse with a conflicting payload is rejected.
- Authorization is checked before a replayed or a new outcome returns.

### Lists and paging

The draft lists, the new-change list, and the recent collection checks use keyset paging. A request holds one opaque cursor with a direction and a (time, id) key. Each page lists the newest rows first. It returns a newer cursor and an older cursor, and a cursor is null at that end.

| List | Order |
|---|---|
| Statement drafts | Event date (newest first), then record ID |
| Needs a person queue | Last revision time, then composite ID `kindcode-recordid` |
| New changes | Observation time of the later version, then comparison ID |
| Checks | Creation time, then job ID |

The statement list adds a rank to the cursor: `o.<rank>.<ticks>.<id>`. The rank is always 1, which keeps the ranked keyset path of `ReviewKeyset.Page`. The ticks are the event date at midnight. `PageCursor.Parse` accepts only the tiers that `ReviewPriority` defines. The two-part form still serves the other lists.

The event date of a statement is its statement date, or else the capture date of its candidate. The tier of an action or a vote is the `priority` of the analysis row for the draft task. It orders the analysis queues, and no review list reads it; see [analysis](analysis.md#storage-and-contracts).

The statement lists also filter on one issue, one official, and an event date range, both ends included. The Host reads `issue`, `official`, `from`, and `to` from the query and checks them against the configured issues and the people of the collection configuration. It keeps them in the tab and pager links. A value that is not valid shows the same error as a bad cursor. A start date after the end date shows its own message. The Application handlers take one `DraftListFilter` with the status and these four values.

A new change is a complete comparison with at least one text hunk and no draft. The statement list filters on status in SQL. Approved means that the newest decision on the current revision approves it. Needs action means every status except Approved and Rejected. A rejected record shows under All only. Its counts reuse the same status filter in `ReviewRecords.Drafts`, so each count equals the total of its list.

The Review home page lists the Needs a person queue, the Rejected list, new changes, source health, and recent activity. The owner also sees the latest root job of each configured source; see [collection](collection.md#sources-page). The recent activity feed reads the newest events of each kind from the review tables. For the owner only, it also reads the job and processing tables. Application merges the events by time. The stat strip counts the open reader reports and, for the owner, the sources that need attention.

Code approves a bill action or a vote when its checks pass. The worker then publishes it; see [actions](actions.md#behavior). A record shows in the Needs a person queue in two cases. Code left it for a person, or a person asked for changes or withdrew approval. A row links to the editor that `RecordRoutes.Editor` names. The rail has no Actions or Votes link, because no list page exists. Each editor also opens from the lookup box; see [Finding a draft](#finding-a-draft). Each editor shows its record ID in the page header, so a reviewer can copy it.

`RecordRoutes.Editor` maps a record kind and a record ID to its review page. It calls the route class of the kind.

### Needs a person queue

The panel "Needs a person" sits first on the Review home page. It lists every record that waits for a person, whatever its kind. The panel header gives the total. The page size is 10. A row shows the headline, the kind, a status badge, the reason, the last revision time, and a link to the editor. The kind and the time hide on a narrow screen. A relationship row shows the title of its editor, `RelationshipLabels.Title`: the link type and the headline of the cited statement. The store reads those headlines with `RelationshipCitedReader.ReadStatementHeadlinesAsync`, for the relationship rows of the page only.

`PostgresReviewQueueStore` reads the keys with one raw `UNION ALL` over the seven draft tables. Each branch keeps the rows with a revision (`current_revision_number >= 1`) whose `review_status` is neither Approved nor Rejected. A key holds a two-letter kind code, the record ID, the composite ID `kindcode-recordid`, and `last_revised_at_utc_ticks`. `ReviewKeyset.Page` pages the keys by time and composite ID, as `PostgresReaderReportStore` pages its reports. The store then reads only the drafts of the page, one kind at a time, with `ReviewRecords.ReadQueueDraftsAsync`. That method goes through `ReadQueueAsync` and `ReadHistoriesOrUnreadableAsync`, so the status and the open concerns come from the decisions and not from the stored status alone. The relationship kind does not use `ReadQueueDraftsAsync`. It calls `ReadQueueAsync` and then reads the cited statement headlines. The total is a count over the same union. The keys, the drafts, and the count all read in one `RepeatableRead` transaction, so a worker revision cannot split a page.

`ReviewQueueItem.Reason` is one sentence. The held reason of the draft wins when it exists. Otherwise the status gives the reason: open concerns, changes requested, or approval withdrawn. Code never checks a revision that a person wrote, so a code-approved kind with a person revision reads "A person edited this record. A person must approve it." A record with no other signal reads "Code did not approve this record. A person must decide." when code can approve its kind (`CodeApproval.CanApprove`). Other kinds read "A person must review this draft." An old record has no held reason, because it waited before the `held_reason` column existed. It shows the derived sentence.

The owner also sees the published records that are stuck at the correction limit. They show first, on the first page only (the page with no newer cursor), with the badge "Cannot publish" and the text of `BlockedPublishedRecord.StuckText`. The record is Approved, so the union cannot list it. The Last revised cell of such a row reads "Approved". Records that review blocked are in the union already, by their status. An approved record is not in the queue. A reviewer opens it with "Find a draft" or "Search approved records". A cursor past the end shows "No more records on this page" and a link to the first page. A link that is not a cursor shows the page link message, and any other failure shows the generic load error and is logged. A stuck record shows once, in the queue only. An approved link that no longer matches shows after the stuck rows, with the badge "Approved". The row text has two parts. The first is `RelationshipLabels.NoLongerMatches`: "This statement and this action or vote no longer share a bill." The link editor shows it too. The second is `RelationshipLabels.CheckApprovedLink`: "Open the link and check it. Withdraw the approval if it is wrong. If it is right, it stays on the site and this row stays here." A stuck link is left out of these rows. One read gives at most 10 such rows. The panel total counts all of them. A hidden row gets a line above the table. The line reads "Showing the newest 10 of 14 approved links that no longer match." These rows have no paging and no dismiss action yet. The pager links of the queue and of the new changes panel keep each other's cursor. They also keep the search text and the search cursor. `ReviewHome.PageHref` builds every such link.

### Finding a draft

The Review home page has a search box, "Find a draft". It sends a GET request with the query `find`, like the list filters, so it needs no antiforgery token. `LookupDraft` reads the text and trims it. "HR 1234", "H.R. 1234", and "HJ Res 5" name a bill of the current Congress. A leading Congress number, as in "118 HR 1234", names another Congress. A record ID of any of the seven kinds opens its editor. A link to an editor or to a public record page gives its record ID, which is the last part of the address. A link without a record ID is invalid input. "Roll 245" names a House roll call of the current Congress and the current session. "Senate roll 245" names a Senate roll call. The vote page links the roll call to clerk.house.gov or senate.gov by chamber (`SourcePages.RollCall`). Test: `VoteReviewWorkspaceTests.ASenateVotePageLinksTheSenateRollCallAndNamesTheSenateInItsHints`. A roll call with a Congress number is not valid, because the session would be unknown.

### Searching approved records

The Review home page has a second search box, "Search approved records". It sends a GET request with the query `q`. `SearchApprovedRecords` trims the text. It refuses blank text and text over 300 characters. The page then shows "Type 1 to 300 characters to search." `PostgresReviewQueueStore.SearchApprovedAsync` runs one raw `UNION ALL`. It covers the draft tables of the kinds that have their own headline: document change, statement, action, vote, weekly brief, and executive action. A branch joins the current revision of each Approved draft. It matches `to_tsvector('english', headline) @@ websearch_to_tsquery('english', text)`. The public search service uses the same text search (see [search](search.md)). The headline comes from the `headline` column for every kind except executive actions. It comes from the `title` column for executive actions. A relationship has no headline of its own, so the box finds its statement and not the link. `ReviewKeyset.Page` pages the matches by last revision time and composite ID. The panel "Search results" shows a link to the editor, the kind in plain words, and an Open button.

The query computes the text vector for each approved row on each search. It has no index, so it scans the approved drafts and their current revisions. This is acceptable while the number of approved records stays small. A stored headline column with a GIN index would remove the scan, but it needs a migration. Tests: `PostgresReviewQueueTests.SearchFindsApprovedRecordsByHeadlineWordsOfEveryKindThatHasOneAndSkipsRecordsThatWaitForAPersonAndOldRevisions`, `PostgresReviewQueueTests.SearchPagesWalkEveryMatchOnce`, `ReviewReadHandlerTests.SearchRejectsBlankTextAndTooLongTextBeforeReading`, and `ActionReviewWorkspaceTests.TheReviewHomeSearchesApprovedRecordsByHeadlineAndLinksEachResultToItsEditorWithItsKindInPlainWordsAsync`.

`CongressCalendar` gives the current Congress and session from the UTC date. `CongressBillListItem.NormalizeCitationType` gives the bill type, so no second type table exists. `IRecordKindStore` gives the kind of a record ID with one query over the primary keys of the draft tables and of `statement_candidates`. The ID sets do not overlap. A bill goes to the action page through `FindRecordIdByBillAsync` of the action store, and a roll call goes to the vote page through `FindRecordIdByRollAsync`. The page redirects to the editor. When no draft exists, the home page shows "No draft for" and the text. When the text names no bill, roll call, record ID, or link, `DraftLookupFormatException` is an invalid input. The page shows its message with status 200 and does not fail. An operational failure shows a retry message.

### Approval check

`ApprovalCheck` holds the result of the checks that Approve runs, as data. It keeps the failure message. A statement check also uses the allowed selections of the admitting configuration revision. Code approval uses it, and the queue shows its failure message as the held reason. `GetStatementReview` runs the statement check on the saved revision. The statement editor shows the failure text in a notice at the top of the page, also when a concern is open. It shows no notice for an approved statement, because code approval reads the date by code and this check does not.

### Workspace forms

The editor shows the saved account and its exact selected passages as the approval target. It keeps them apart from editable or recovered unsaved wording. Reviewers judge substantive change, wording, attribution, dates, interpretation, and evidence limits. Automatic citation and revision checks establish integrity, not semantic correctness.

`SourceSpan.QuoteIn` reads the quote of a citation. The editors share it.

`ReviewCommand` maps a conflict, a bad request, and an operational failure to a status code and a message. An unauthorized actor goes to the access-denied page.

The workspace keeps conflicting edits. It disables the decision panel for unsaved, failed, or conflicting forms. Every mutation uses an antiforgery token. The reader preview updates on the server render after an explicit save.

### Evidence verification

The New changes list is the one read that does not verify full evidence. One query reads each stored comparison result, source, requested URL, and observation time into `NewDocumentChange`. That type holds the passage count and the first passage. The query loads no extraction text and does not compute the comparison again, so a page of 100 rows stays cheap. A list row is only a pointer.

Saving a comparison, the single review read, starting a draft, approval, and publication all verify the full evidence. A read verifies each comparison and its two extractions once and reuses them for every revision.

### Take off site

The record editor of each publishable kind shows Take off site to the owner. `TakeOffSitePanel` owns the markup. `PublishedRecordEditorPage` owns the post flow and gives `TakeOffRecord`, the kind and ID of the editor, to the panel and to the redirect. Each editor gives only its own decision call. `TakeOffSite.GetStatusAsync` reads the active manifest once. The panel shows the form while the active release holds the record, or while a committed withdrawal waits to be served. An off-site record shows the sentence that tells how it returns. When the active release is not the latest, the panel warns that the action ends the rollback pause. When the review host has no `TakeOffSite`, the owner sees one line: "Take off site needs the release directory, collection and issue files". `ReviewWorkspace.ConfigurePublication` registers `TakeOffSite` only when the release directory, the collection file, and the issue file are set. A reviewer sees nothing.

`TakeOffSite.ExecuteAsync` first checks the reason and the keys. It then reads the active manifest. If the manifest already withdraws the record, it serves the active release again and stops, with no key and no decision. This is the repair for a committed withdrawal that was not served. Otherwise it checks that the record is on the site, and that no relationship or brief cites it. A refusal here writes no decision. Then it records the blocking decision through the callback of the editor. An approved record gets Withdraw approval. A record that waits for review gets Request changes. A record that review already blocks, or that review rejected, gets none. Last, it calls `PublishRelease` with one withdrawal. From the decision on, every step uses `CancellationToken.None`, so a closed tab cannot stop it. After a success, it reads the active manifest. If that manifest still lists the record, for example after a replayed key and a later activate, it returns a refusal and never reports success. The two writes use the keys `<form key>:decision` and `<form key>:publish`, so a retry with the same key records no second decision. Every refusal is a sentence that says what happened and what to do next. Most are fixed text. The cascade sentence names the citing records from the manifest at run time. The owner never sees raw exception text. The log holds it. The decision panel shows the off-site sentence above the form. The Approve hint of the executive action editor changes when the shown revision cannot return the record. `PublishedRecordRules.CanReturn` owns that rule. In the other editors, `SaveAndApproveFields` warns when the shown revision of an off-site record cannot return it. It shows "Publishes soon." only to the owner, when the published state is known. A reviewer sees no promise.

An off-site record returns only when a person approves a revision higher than the withdrawn one, with a correction note. Save and approve with no edit approves the same revision, so it cannot return the record; see [publication](publication.md#corrections-and-withdrawal). An executive action has no person edit. It returns only after the worker writes a higher revision. A person then approves that revision with a note.

### Reader reports

The rail links to the queue at `/Review/Reports`. The link shows no count, because the layout would then run a query on every page. The home stat card shows the open count. The queue holds the reports that readers sent about published records. The worker pulls them from the search service; see [search](search.md#operational-pull). A report stores the record ID and kind, the revision, the category, the reader text, and the received time. It stores nothing about the reporter.

A reviewer or the owner dismisses a report or closes it with a correction. A dismissal needs no note. A resolved report cannot be resolved again. The dismiss command checks the expected version, as a review decision does, and a second command gets a conflict. The queue keeps an open report until a person acts. It deletes a closed report 365 days after its resolved time, whether the status is Dismissed or CorrectionNeeded. A correction with no newer published revision is deleted too, and its notice goes with it.

The list has two tabs, Open and Resolved. The Open tab lists the oldest report first, then the report ID ascending. The Resolved tab lists the newest report first by received time, then the report ID descending. Both use `ReviewKeyset.Page`, which has an ascending option for the Open tab. The pager links read Previous and Next. A row shows the category, the start of the text, the kind, and the revision. A report on a replaced revision shows "Revision N, current is M". M comes from one query for the page over the seven draft tables. The query matches the kind and the record ID. A report on a record that review storage does not hold shows "Not in review" and no editor link. The title of an open report links straight to the editor of its record. The title of any other report links to the report page.

The `reportPull` stage deletes the expired closed reports at the start of each pass, before the pull. `PullReaderReports` logs a failed deletion at error level and still pulls. The store compares the resolved time with the database clock.

Each editor shows the `ReaderReportPanel` above its form. The panel lists the open reports of the record with the category, the reader text, and a Dismiss button. It shows the oldest 64 open reports. If more open reports exist, it shows "N more reports stay open". For one report it reads "1 more report stays open". All Dismiss buttons post to one form, `ReaderReportDismissForm`, with the report ID and the version. The panel adds one hidden field for each shown open report ID to the approval form of the editor. That form is the Save form in the six editors with a form. It is the decision form in the executive action editor. A person fixes the wording, types the public text, and presses Save and approve. The store closes the listed reports in the transaction of the approval. It runs under the review lock of the record kind. It also takes row locks of `reader_reports`. See [advisory locks](../architecture.md#advisory-locks). The store closes each listed open report whose revision is older than the approved revision. The status is CorrectionNeeded, the list label is Corrected, and the note is fixed text. A report on the approved revision stays open. A no-edit approval still closes an older report. The current revision may be approved already. The panel then adds a sentence to an older report. The sentence reads "The current revision is already approved. Dismiss this report if it fixes the problem". A rollback leaves the report open. The panel shows a closed report with the title "A correction was approved" and the text "A person approved a correction for this report". It shows the notice while the active release holds no newer revision of the record than the revision of the report. A fix that is approved but not published keeps the notice. The review state of the record does not change. The executive action editor has no person edit. A person closes a report there by approving a newer revision, or dismisses it. When the current revision is already approved, the panel shows no approval hint there. It says "No person edits this record. If the report is wrong, dismiss it. The owner can take the record off the site". The report page also offers Dismiss, for a record that review storage does not hold.

### Authentication

The Host uses `Microsoft.AspNetCore.Authentication.OpenIdConnect` 10.0.14 for the Auth0 authorization-code flow with PKCE. The CLI acts as the configured owner subject. The authenticated `review` command binds to loopback and expects an HTTPS reverse proxy; see [host](host.md).

## Storage and contracts

- The generated [review schema](schema/review.md) lists every table, column, key, check, index, and trigger.
- The tables `reader_reports` and `reader_report_cursor` belong to the report queue; see the generated [reports schema](schema/reports.md). A report row holds these values: the report ID, the record ID, the kind, the revision, the category, and the text. It also holds the received time, the status, the note, the resolver, the resolved time, and a version. The version starts at 0 and rises by 1 when the report is resolved. The cursor table holds one row with the opaque cursor of the search service.
- Core/Review owns decision semantics. Application/Review owns authenticated commands and configured selection validation. Infrastructure/Review implements the store boundary with Postgres.
- `ReviewPolicy` holds the status rule, the open-concern rule, and the decision checks. It works on a record ID, the current revision number, the review state version, and the decisions. It knows no record type.
- Review writes take the review keys from `PostgresAdvisoryLock`. The keys and their order are in [advisory locks](../architecture.md#advisory-locks).
- `ReviewRecords` is the shared store core for each record type. Each store holds one instance over its draft, revision, and decision rows, its lock key, and its record ID property. It owns the create, save, and decide flow, the append step, the status filters, the draft page, and the unpublished approved list. Its bounded batch reads parse and validate one review cycle for each record into a `ReviewHistory`. Its batched revision 1 read parses and validates the shape of each revision 1. A store gives only its feature rules as delegates. They are the create body, the save preparation, the revision row builder, and the decision checks. `ReviewRecords` builds the decision row and its resolution rows itself. The save preparation also gets the draft row. Actions, votes, and executive actions also give a delegate that copies the listing columns to the draft row. For actions and votes these are the candidate ID, event date, issue IDs, and official IDs. Actions and votes share the headline and summary text rules in `ReviewText` and `ReviewTextRules`. Each store can give a callback for a withdrawn approval, which requeues the briefs that cite the record; see [briefs](briefs.md#staleness). The rows implement `IReviewDraftRow`, `IReviewRevisionRow`, and `IReviewDecisionRow`, and the revisions implement `IReviewRevision`. `IReviewRevision` is a deliberate departure from the concrete-types rule and the first interface in Core. Core cannot see Infrastructure, and the shared core needs it as its generic constraint.
- `ListedDrafts` owns the list read of statement drafts: the filters and the page. `ReviewKeyset.Page` has a plain form for two keys and a ranked form for three keys. The rows of statements, actions, and votes implement `IListedDraftRow`. Each draft row holds `event_on`, `issue_ids`, and `official_ids`, and the action and vote rows hold `candidate_id`. Each array has a GIN index, and the issue and official filters use `@>` so those indexes can serve them. Only `statement_drafts` has the index `ix_statement_drafts_listing`.
- `ReviewRecords.AppendRevision` is the one step that appends a revision, sets `last_revised_at_utc_ticks`, clears `held_reason`, and computes `review_status` again. The person save and the relationship and brief analysis appends call it. The action, vote, executive action, and statement analysis appends call it through `AppendCodeApprovedAsync`. Only a document-change create, a person create on a statement draft with no revision, and `StatementDraftRows.NewDraft` use `ReviewPolicy.GetInitialStatus`. Each of them sets `last_revised_at_utc_ticks` itself.
- `ReviewIdempotency` reads and writes replay receipts and checks the actor, key, and payload hash. `ReviewDecisionHistory` builds a decision from a row and replays the decisions of one review cycle. `IReviewDecisionRow` exposes the decision kind, so the cycle read finds the latest approval in SQL. It also exposes the actor and the notes, so `ReviewRecords` fills them for every record type. `ReviewKeyset` builds the keyset page filter. `ReviewJson` holds the stored JSON options.
- Five tables hold record pointers, immutable revision JSON, immutable decisions, the concerns that approvals resolve, and actor, operation, and request-key replay receipts.
- `document_change_revisions` holds one row for each revision. The row holds the author, the comparison, the headline, the summary, the institution, and the creation time. It also holds the optional significance, limits, and change date. The row also keeps the revision JSON as a copy, until a later step drops it.
- `document_change_revision_officials` and `document_change_revision_issues` hold one row for each selected ID, with its position. `document_change_revision_citations` holds one row for each citation span, with its position and the flag that marks the change date evidence. Each child table has a foreign key to its revision.
- The author columns of a document change revision are required. The other columns stay null on a revision that older code wrote, until the backfill moves it. `HeadlineSummaryColumns` owns the headline and summary columns. `ReviewTextColumns` adds the origin and the suggestion for the kinds that have them.
- Each decision table holds the decision as columns: the identity columns, `kind`, `actor_subject` (required), `note`, `correction_note`, `reason_code`, and the creation time. A child table `<kind>_review_decision_resolutions` holds one row for each concern that an approval resolves. `ReviewDecisionTableConfiguration` owns the column rules and the child table mapping for all seven kinds.
- Draft and decision expected versions are checked inside the locked transaction.
- Each draft row stores `last_revised_at_utc_ticks`. A new draft starts it at the creation time, and `AppendRevision` sets it to the time of each revision. A partial index on it and the record key, `ix_<table>_needs_action_revised`, serves the not-Approved reads. The draft tables of actions, votes, statements, and executive actions also store the nullable `held_reason`.
- Each draft row stores `review_status`, which `ReviewPolicy` computes in C#. Create, save, the action analysis append, and every decision write it under the lock. A check constraint lists the status names, which `ReviewDraftTableConfiguration.StatusCheck` builds from `ReviewStatus`. `ReviewStatus` adds `NotDrafted` for a record with no revision, which a document change never has.
- Each comparison row stores `has_changes`, which is `DocumentComparison.HasChanges()`: a complete comparison with at least one hunk.
- Partial indexes on `has_changes` and on the Approved and not-Approved statuses serve the filters, the New changes list, and the list counts.
- The list of unpublished approved drafts reads the active release records. It stays a read query on top of `review_status`.
- Revisions keep the author and the UTC save time. Decisions reference the exact revision with a composite foreign key.
- Reads validate stored identities, historical transitions, and exact retained evidence.
- Bounds: 64 open concerns, which also bound the decisions of a cycle (see [Invariants](#invariants)), 64 citations for each revision, and bounded field sizes. Writes fail before they exceed a bound.
- The public release contract includes review and publication dates and correction context. It excludes author identity, reviewer email, Auth0 identifiers, and private notes; see [publication](publication.md).

## Limits and planned work

- A newer update that Blocks before the rejection check sets no block. Code cannot tell whether that update changed facts. A blocked update shows in the blocked list, and old facts can publish until someone clears the blocked update.
- Live Auth0 tenant verification is pending. Both reviewers will reach the shared production workspace through their browsers over Tailscale; see [host](host.md#limits-and-planned-work).
- The official filter, the official chips of the document-change editor, and the official IDs that a save accepts all come from `ReviewOfficials`. It lists the `People` of the collection configuration (`CIVIC_LENS_COLLECTION_CONFIG`) with their names, with no limit on the count. Without that file the choices are empty and every `official` value is invalid.
- The filters and the order are computed for each page over the filtered set. This is fine at the present volume.
- The tab counts ignore the issue, official, and date filters. They count every record of the status.
- A record that code left for a person before the `ReviewHeldReason` migration has a null `held_reason`, because the old decline message was not stored. An action, a vote, or an executive action gets a reason when the worker next appends a revision of it and the approval check fails. A statement never gets one, because the worker writes only its first revision.
- The queue reads every key that needs a person and sorts them, because the order uses the composite ID and no index can serve it. On a scratch database with 3 000 such rows the first page took 2 ms. With 30 000 such rows it took 45 ms. The queue is bounded by the records that wait for a person. A page also reads the revisions and decisions of its records, so it runs up to four queries for each kind on the page. They read the drafts, the decisions, the concerns that approvals resolve, and the revisions. No approval means no read of resolved concerns. Relationship rows add one read of their statement headlines.
- The panel of Take off site reads the active manifest on every editor page load for the owner. This is one file read. It is fine at the present volume.
- The same statement at a new admitted URL is a new record. Code can approve it, so a statement that the owner took off the site can come back under another record ID.
- Take off site is on the record editors, not on the home page. The CLI command `releases publish <key> --withdraw <reference> "note"` still works.
- A held reason is the message of the failed approval check. Some messages name a rule and not the field. One example is "Text must be 1 to 256 characters and contain no NUL." Nobody has rewritten them.
- A deploy rollback to an image from before the migration `DropDecisionJson` cannot run until an explicit EF rollback of that migration happens. That image writes `decision_json`, and the column does not exist. The `Down` of the migration adds the column and rebuilds it from the decision columns and the resolution rows. The JSON has the same fields, but its key order and spacing differ from the original. `db migrate` only moves forward. If the migration raises "Cannot drop decision_json", the column is intact. `update.sh` has already stopped the worker and the review host, and they stay stopped until the operator starts them; see [operations](../operations.md#production-compose). The rollback order is in [operations](../operations.md#postgres-adapter-and-migrations), and it needs a developer with the EF tool.
- A deploy rollback to an image from before the migration `RejectDecision` works only while no record was rejected. Such an image does not know the kind Reject, the status Rejected, or the column `reason_code`. After the first rejection it cannot parse the rows. The `Down` of the migration then fails on the check constraints and rolls back, so the schema stays intact. It does not delete a decision, because decisions are immutable. Roll forward with a fixed image instead. The `Down` test runs with and without a rejected row: `RejectDecisionMigrationTests`. The rollback order is in [operations](../operations.md#postgres-adapter-and-migrations).
- A correction notice of a rejected executive action waits and does not revise the record. Any person approval applies it; see [Invariants](#invariants).
- A reader report by rejection cause has no page yet. The `reason_code` column holds the data.
- The R-63 pilot has four steps for document changes too; see [roadmap](../roadmap.md). Steps 1 to 3 are done in code. Both write paths write the columns and `revision_json`. The commands `document-changes revisions backfill` and `document-changes revisions verify` move and check old revisions. The runbook is in [operations](../operations.md#document-change-revision-backfill). Step 3 stays open until production runs this code. Step 4 drops the JSON. It needs a migration and a change of `DocumentChangeRevisionRows.Create`.
- The read-only database role reads these columns now. `readonly_access.revisions` in `deploy/scripts/readonly-grants.sql` returns `to_jsonb(t)` without `author_subject`, in the one column `row_data`. It returns every other column of a document change revision, including the headline, summary, significance, limits, institution, and change date. Its `revision_json` field holds the revision JSON without the author.
- Reads show the current review cycle only. A page of older cycles is future work.
- A read trusts the approval at the start of a cycle and does not check it against older concerns again. The decide step checked it under the lock when it was written.
- Local MCP will inspect jobs, explain processing, inspect source health, compare analysis runs, and run explicitly budgeted evaluations.
- MCP review tools will list and read cases, propose corrections, and record explicit decisions. Mutations will use expected versions and idempotency keys. Initial local tooling is read-only.
- AI suggestions, model predictions, and human decisions stay distinct records.
- D-03 decides the dynamic search across retained evidence and review records. Integrated visual comparison is planned and has no roadmap item.
- Global search and expanded reviewer source visibility are pending decisions. Add an evidence library page once document search exists.
- The analysis queues claim work by priority, so the drafting budget goes to the records that matter most first; see [analysis](analysis.md#storage-and-contracts). The action page lists the vote drafts of its bill, and the vote page links the action draft; see [actions](actions.md#behavior). The home page finds a draft by bill, roll call, record ID, or link; see [finding a draft](#finding-a-draft).
- A reviewer approves a weekly brief on its own. A brief cites records that are already published, and each cited record keeps its own decision bound to its exact revision. Approval needs every cited revision to be approved and in the active release. Model output never approves or publishes. See [briefs](briefs.md#limits-and-planned-work).
- See [roadmap](../roadmap.md) for order.
