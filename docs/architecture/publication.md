# Publication

## Purpose

The publication feature turns approved revisions into immutable, cumulative static releases. It activates a release atomically. A separate static file server reads only published files.

## Decisions

- Only the owner publishes or activates a release. One exception exists: the worker stage `factPublishing` publishes as the code subject, and only actions and votes.
- A record is published at its current revision, and only when that revision is approved and has no unresolved concerns. Code can approve an action or a vote. People approve the other kinds. The owner publishes all kinds.
- The `factPublishing` stage publishes an action or a vote when code approved its current revision. A record that a person approved waits for the owner, because a person approval is a judgment that code does not replace. The owner can still publish any approved record with the CLI or the workspace.
- The stage runs once an hour by the database clock. A tick publishes batches of up to 64 records until no ready record is left, and then it sleeps. A tick with nothing ready makes no release.
- A publication conflict ends the tick. A race with an owner publish is normal, and the next tick builds again from the latest release. Any other failure is reported and counted as a stage failure.
- The stage waits while the active release is not the latest release. This is the state after `releases activate` rolls back. It resumes when the owner activates the latest release or publishes from the CLI.
- A record that fails validation while the stage loads it is left out of the batch and reported with its ID and message. The other records publish in one release. The next tick tries the record again.
- The action and vote pages say "From the official record, checked" with the approval time. They do not claim that a person approved the record. When `textOrigin` is `model`, they add "An AI summary of the official record". Text that a person wrote gets no label. `ApprovedAtUtc` holds the time of the approval, by code or by a person. Enforced by `PublishedActionView` and `PublishedVoteView`. Tests: `ReleaseRendererTests.ActionAndVotePagesSayThatTheRecordComesFromTheOfficialRecordInsteadOfClaimingAPersonApprovedIt` and `ReleaseRendererTests.ActionAndVotePagesLabelAnAiSummaryOnlyWhenAModelWroteTheText`.
- A newer draft never replaces published content automatically.
- A release is cumulative. It holds the base release records plus explicit additions or replacements.
- Carried records are hard links to the immutable files of the base release. Disk therefore grows with published records, not with the number of releases.
- Each publish rebuilds `release.json`, `officials.json`, `catalog.json`, and the home page. It rebuilds the all-records pages, the issue and policy area pages, `search.html`, the officials pages, `report.html`, `method.html`, and the assets. It also writes again the page of each record that lists related records, when the new release holds a link that cites that record. Its record file stays the same hard link; see [related records](#related-records). It reads the previous manifest once, under the 32 MB manifest cap, `PublicationProtocol.MaximumManifestBytes`. It reads the previous `officials.json` once, under `PublishedOfficials.MaximumBytes`. It rebuilds the files of an official only when the official is touched; see the invariants. `PublicationProtocol.MaximumRecordsPerRelease` is the one owner of the record limit, which is 20,000. The database has no count check, because C# owns the rule.
- Postgres records which release is active. The `current` link is only a copy for the static server, so a failed link swap never drops committed records.
- Every publication write takes all six review locks in one fixed order, which prevents a deadlock. The order is in [advisory locks](../architecture.md#advisory-locks).
- A release has no status column. `is_active` marks the one active release: a commit sets it on the new row and clears the old one, and rollback moves it.
- Rollback is a CLI command only. The workspace has no rollback or activate control.
- Every release is kept. Carried records are hard links, so disk grows only with published records, and public MCP clients can pin a release. The [search](search.md) service pins releases too.
- In production, releases go to a Cloudflare R2 bucket behind the Cloudflare CDN on civic-lens.info. Terraform defines the bucket and the domain.
- Publish stages and checks a release on the server, then uploads it. The active release changes only after the upload finishes.
- Locally, a Caddy container serves the release root with `file_server { precompressed br gzip }`.
- Host renders the shared Razor components to static HTML, so publication needs no new project.
- Each manifest entry carries filters, so the facet pages and the search filters need no record file reads. Each published record type owns the mapping in its `ToEntry` method. A filter that the kind has no fact for stays empty; publish never guesses it.
- One loader owns each record kind: its ID shape, its ready list, and how publish loads and builds it. `PublishedRecordLoaders` lists them, and the publish and ready-list handlers go through that list. One loader owns the Application side of a kind. The other per-kind places are the `PublicationProtocol.IsRecordId` arm, the store state check, `PublishedRecordLabels.Kind`, the review link, and the `IReleaseRenderer` method.
- The loader base class gives each kind one owner for its Application rules. A non-generic base exists only so `PublishedRecordLoaders` can hold all record kinds in one list. The six kinds are real variation, with different IDs, stores, and records. The precedents are `PostgresAnalysisStore<TRun>` and `ReviewRecordPage`.
- `PublishedRecordLoader<TCandidate, TAddition>` owns the ready-list and load steps once. A kind supplies only its store reads, its ready row, and how it builds and renders one record. `PublishedRecordRules.Cite` is the one owner of a published citation for every kind.
- Official names in every record kind come from the current `PublicationCatalog`, not from stored revisions. The action `policyAreaIds` filter comes from the policy area ID that the draft stored. Drafting resolved it through `IssueConfiguration.PolicyAreaIdFor`, and the reviewer approved it with the revision. Publish never reads the issue configuration. A label that the configuration lacked at draft time gives an empty filter.
- A record ID is unique across all kinds, because all kinds share the flat `records/{id}` paths.
- A brief record embeds no source text. It holds the wording that a person approved and a list of citations. Each citation names a published record by kind, ID, and revision, and carries a copy of the cited headline. A brief is a weekly summary over other records, so it publishes only when the new release holds every record that it cites; see [briefs](briefs.md#publication).
- An action record embeds the full text of each cited extraction once. Each citation names its extraction, and the contract checks the quote against that source.
- A relationship record links one statement to one action or vote. It embeds no source text. It holds the wording that a person approved, the quote of the statement, and the fact of the target. Both are text. It also holds a citation of each side. A citation names a record by kind, ID, and revision, and carries a copy of the headline. A relationship publishes only when the new release holds both cited revisions and the latest decision on each is an approval. A link that a release already holds stays in later releases, whatever happens to the records that it cites. See [relationship record](#relationship-record).
- A vote record embeds the full text of each cited extraction once, as an action record does. Its citations are the vote day, the kind, the result facts, and the cast of each tracked member. The kind can be nomination, cloture, or motion to proceed. Only Senate votes use these three. They are new enum names, so they need no version bump. `PublishedEvidenceRules` owns the source and citation checks for actions and votes. A vote record also holds the raw result wording of the source, the totals of the whole roll call, and the majority of each party. See [Vote record](#vote-record).
- The manifest schema version is 1. A new record kind needs no version bump, because every reader ships with or after the release it reads. The publisher reads only releases of the current schema version. `app.js` and `public.js` ship inside each release. An older publisher fails loudly on the unknown kind.
- Release JSON uses relaxed escaping (`JavaScriptEncoder.UnsafeRelaxedJsonEscaping`), so non-ASCII letters and punctuation take UTF-8 bytes, not 6-byte `\uXXXX` escapes. This is safe because release JSON is fetched as JSON and never inlined in HTML or a script tag. Readers do not change.
- Unreviewed proposals, internal reviewer notes, operational job details, and mutation controls stay private.
- Public serving reads release contracts only. It never reads operational storage or private notes.
- The public UI is static pages on a CDN. Publish renders every public page, including the official, issue, policy area, and briefing pages. No server is on the public page path. Search and reader reports go to the search service.
- Search goes to the [search](search.md) service, which is also the public read API. Each release holds `search.html`, which calls it. The browser no longer searches the manifest.
- A release holds the member photos that its officials show. A photo file is named by the SHA-256 hash of the capture, not of the decoded image bytes: `photos/{hash}.jpg`. A name therefore never changes its bytes, and a changed photo gets a new name. App assets keep fixed names, because the renderer owns them. A hash name lets a CDN keep a photo for a long time.
- A publish writes the newest stored photo row of each official. It reads a capture only for a hash that the previous release lacks, and it links every other photo. Every publish path gets the artifact directory for this read: the worker, `releases publish`, and the review workspace. The directory is required: `releases publish` and the review workspace refuse to start without `CIVIC_LENS_ARTIFACT_DIRECTORY`.
- A new photo that cannot be read does not fail the publish. The profile keeps the photo of the previous release, and the file is linked. With no previous photo the official has no photo. Both cases log an error with the person and the attempt. A cancelled token, a database error, and a missing file in the previous release still fail the publish.
- A photo is only for the portrait on the official page. Photos are never used in ads.
- Each public page has one stable URL, so search engines can find it.
- Only a person withdraws a record. The owner gives `--withdraw <kind>:<id> <note>` to `releases publish`. A request can have withdrawals and no records. The code subject withdraws nothing.
- A record can leave the release only when review blocked it. Its status is `ApprovalWithdrawn`, `ChangesRequested`, or `AwaitingReviewWithConcerns`. The commit checks this under the review locks.
- A withdrawal removes the record from the manifest `records` list and adds a `PublishedWithdrawal` to the manifest `withdrawals` list. The release keeps no record file. The record page becomes a notice with no headline, body, or officials.
- A withdrawal never leaves a link to nothing. The publish refuses to withdraw a record while a relationship or a brief that stays in the release cites it. The owner withdraws the citing records in the same request.
- A person brings a withdrawn record back. The owner publishes the withdrawn ID as a record with `--note <kind>:<id> <text>`, as for a correction. The code subject cannot bring a record back.
- Every record page links to `report.html` with the record ID and revision in the query. One static report page serves all records. The page posts to the [search](search.md) service, which stores the report. The reader sends no contact data, and the page stores nothing about the reader.

## Invariants

Each line gives the rule, what enforces it, and the test that protects it. Cross-feature invariants are in [architecture](../architecture.md#invariants).

- A release holds at most `PublicationProtocol.MaximumRecordsPerRelease` records, and the manifest stays under the manifest cap at that count. Enforced by the `PublishRelease` record count check and manifest size check. Test: `PublishReleaseTests.RejectsMoreRecordsThanTheCapBeforeAnythingIsBuilt`, `PublishReleaseTests.AReleaseAtTheRecordLimitOfFilledStatementEntriesKeepsTheManifestUnderThreeQuartersOfTheManifestCap`, `PublishReleaseTests.AReleaseAtTheRecordLimitOfFilledActionEntriesKeepsTheManifestUnderThreeQuartersOfTheManifestCap`, and `PublishReleaseTests.RefusesAManifestOverTheManifestCapAndStagesNothing`.

## Behavior

### Public reader experience

A record explains what happened, who was involved, and when. Where evidence supports it, it explains why the event matters. It states what the evidence can and cannot establish. Readers move from the account into retained passages and exact citations. They do not need to read collection jobs or extraction metadata first.

A document-change record shows both versions, and observation history where needed to explain gaps. A current source link supplements the retained evidence; it does not replace it. Public records show their review and version context and published corrections.

### Release content

- Each document-change record carries the full extracted text of both versions, their source URLs, and their observation times. Changed regions are offsets into those texts.
- A citation holds an extraction ID, UTF-16 offsets, and the quoted text. The contract rejects a quote that does not match its offsets.
- Records show the approval date and the first-publication date. The home and all-records pages show the release date.
- `index.html` is the home page. It shows the latest brief, the 20 newest records, and links to the issue and policy area pages. The latest brief is the one with the newest week. It shows the headline and the paragraphs with their citation links, which lead to the brief page. The home page has no search panel.
- `all.html`, then `all-2.html` and so on, list every record 50 to a page, newest first, with relative previous and next links. They hold no search panel; `search.html` has the search.
- `issues.html` lists each issue and each policy area with its name and record count.
- Each issue has `issues/{id}.html`, then `issues/{id}.page-2.html` and so on. Each policy area has `policy-areas/{id}.html` with the same page suffix. A page lists the manifest entries that hold the ID in `issueIds` or `policyAreaIds`, 50 to a page, in the order of `ReleaseRecordOrder`. The search service uses the same rule when a search has no text. Each row shows the kind, the headline, the officials, and the event day, else the first publication day. A facet has pages only when its ID is a valid path segment. See Limits. `PublicationProtocol` owns every page path.
- A page outside the root folder builds each link from a `../` prefix, as a record page does.
- Officials, issues, and policy areas appear by their configured name. An ID with no configured name appears as the ID.
- Only the release manifest shows the schema version.
- `officials.json` lists each official that a published record names. A record names an official when its manifest entry names the official. A record also names an official when a vote of the release holds the official as a member. A vote entry names no official. Publish therefore reads the members of the vote revisions of the release in one database query. The query takes the record IDs and revision numbers of the manifest, so it covers carried votes and new ones. It returns a record ID and a person ID for each member. It sends two array parameters, so the list size does not matter. It reads no vote file for a configured person. A person who left the configuration takes the name of an entry that names the person. A person named only by votes takes the name from one vote record, read from this publish or from the previous release. Each profile holds the ID, the name, the Wikidata ID, the website, and the dated terms. A term holds the office and the dates. It holds the party, the caucus, the state, and the district when the source gives them. The caucus is the party whose caucus the official joins, when it differs from the party. A term with no end is ongoing.
- `PublicationOfficials` joins a person to terms. It matches the bioguide ID to the latest member snapshot first. When no term matches, it matches the Wikidata ID to the latest executive snapshot. A person with no match is listed by name with no terms. A Wikidata ID with no executive official is not an error. The website is the valid roster URL of the member, else the configured website of the person. A former member who is not in the current roster takes the configured website. A member who leaves the roster loses the roster URL, as the terms do. A website must pass `PublishedWebsite`. A roster URL that fails the rule becomes no website and never fails a publish.
- A vote file holds the votes of one official in one Congress. A row holds the record ID, the vote day, and the roll call (Congress, session, number). It also holds the bill type and number when the vote has a bill. It holds the cast, the result, the totals, the party of the official, and the majority cast of that party. It holds the headline, the vote kind, and the tracked issue IDs. Rows are newest first. A publish takes the new rows from the vote records that it already holds. It reads a vote file only for a touched official, and only the files that its pages need. It finds the files of an official by a listing of one folder of the previous release. The members of the replaced revisions of all Congresses come from one database query.
- `officials/{id}.html` is the current page. It shows the name and a table of the offices with their dated terms. It shows one table of rows, newest first. The rows are the entries that name the official and the votes of the current Congress. A profile with a website adds a link labeled "Official website" with the host of the URL. Links lead to `officials/{id}/{congress}.html`, one page of votes for each earlier Congress. A past page shows only the name and its votes, so a roster change does not rewrite it. The date of a row is the event date of the entry, else its first publication day, and for a vote the vote day. A vote row shows the cast, the roll call, and the line "Result of the vote" with the raw result wording. An official with a vote file also has an issue panel, "Issues they work on"; see [Issue panel](#issue-panel). `officials.html` lists the officials with the count of the records other than votes that name each official. It has no vote count, because a publish does not read the vote files of an untouched official. An official who left the configuration is always touched. The home page and the search page link to it. `PublicationProtocol` owns the paths.
- The current page also shows the portrait of the official above the offices; see the invariants. The photo files are `photos/{hash}.jpg` in the root of the release, and `PublicationProtocol` owns the path. A publish writes the file of a new photo from the capture, and links the file of a photo that the previous release holds. The setting of the artifact directory is in [operations](../operations.md#publish-a-static-release).
- `catalog.json` lists the issues and policy areas that the records of the release use, each as an ID and a name. It uses the names of the facet pages, so an ID with no configured name appears as the ID.

A release holds six kinds of record. Each manifest entry has a `kind`: `documentChange`, `statement`, `action`, `vote`, `brief`, or `relationship`, a lowercase camel string. All kinds share the `records/` folder, the record data path, and the record page path.

| Kind | Record ID |
|---|---|
| `documentChange` | The draft ID: 32 lowercase hex characters |
| `statement` | The candidate ID: 64 characters |
| `action` | The action record ID: 64 lowercase hex characters |
| `vote` | The vote record ID: 64 lowercase hex characters |
| `brief` | The brief record ID: 64 lowercase hex characters; the [briefs](briefs.md#decisions) page defines it |
| `relationship` | The pair key: 64 lowercase hex characters; the [statements](statements.md#decisions) page defines it |

A statement record carries one source version with the full extracted text, the source URL, and the observation time. It also carries:

- speakers by configured name, and other speakers
- issues, policy areas, and bill numbers
- the optional statement date with its evidence
- 1 to 32 quotations, each with its kind: `directQuotation` or `releaseText`

Every quotation must equal the source text at its offsets.

An action record carries:

- the bill identity (congress, type, and number) and the bill title
- the policy area with its citation, the policy area ID stored at draft time, and the tracked issue IDs
- the CRS summary citation, when the revision has one
- 1 to 600 sponsorships. Each has the official by configured name, the role (`sponsor` or `cosponsor`), and the original flag. It also has the sponsored date, the optional withdrawn date, and one or two citations.
- 1 to 8 sources, each with the full extracted text of one cited Congress.gov API page, its URL, and its observation time

The sources are the distinct cited extractions in citation order, so the first one is the page of the first sponsorship. Every citation must name one of the sources and quote its text exactly. A source that no citation names is rejected.

A brief record carries:

- the headline and 1 to 12 paragraphs, each with the citation IDs that it uses
- the week start (a Monday), the cutoff release number, and the coverage counts: considered, sent to the model, and cited
- 1 to 256 citations. Each has its ID, kind, record ID, revision number, and a copy of the cited headline

A relationship record carries:

- the headline, which joins the headline of the statement and the headline of the target
- a citation of the statement and a citation of the target. Each has the kind, the record ID, the revision number, and a copy of the headline
- the type, one of `describesOwnBill`, `statesPositionOn`, `claimsCreditFor`, or `statementAboutVote`, and the reason in one sentence
- the quote of the statement and the text of the fact of the target. Both are text only. The builder takes the quote from the article text. Its span must lie on the extraction of the statement and inside one passage of the statement
- the optional statement date, the speakers by configured name, and the issue and policy area IDs of both sides

The approval time of a record is the latest approval of its current revision, for every kind. One Application rule owns that time.

### Publish

One publish request names 1 to 64 records to publish or withdraw, each as a kind and an ID. For each kind, publication loads all selected drafts and their verified evidence in one repeatable-read transaction. Each read uses a fixed number of queries for any selection of 1 to 64 drafts. The publisher builds records from this evidence and does not read it again.

1. Application builds the release contract. A page step then renders every page that the publish writes, and Host renders the static HTML. See [related records](#related-records).
2. The owner action builds the release in a staging directory, verifies it, and moves it to a uniquely named directory under `releases/`.
3. Under all six review locks, the commit checks each added record's revision and review-state version again, in the draft table of its kind. For each added brief or relationship it also checks that every citation is current in the records of the new release. For each withdrawn record it checks that review blocked the current revision. It also checks the next release number and the active release it built on. It then requeues the brief of the week of each record that the release changes, drops, or adds again; see [briefs](briefs.md#staleness).
4. In the same transaction, it records a sequentially numbered release and marks it as active. It stamps the release time from the database clock after it holds all review locks. The commit does not take a time from the caller.
5. After the commit, it takes all six review locks again, reads the active release, and atomically replaces the relative `current` symbolic link.

Publish, replay, and activate all end with step 5. An older command therefore cannot move the link back after a newer one.

The review state is checked at commit, so a concurrent blocking decision cannot be ignored. A commit that fails on a conflict or invalid input deletes its directory. If that cleanup fails, or an unknown failure occurs, the directory stays. Only committed releases can be activated.

Each publication builds on the recorded active release, not on the link. A replayed publish request and the activate command both point the link at the recorded active release. This repairs a link that is out of date. Publish requests reuse the review replay receipts.

### Automatic publication of facts

The worker runs the stage `factPublishing` when `CIVIC_LENS_FACT_PUBLISHING=1`; see [operations](../operations.md#automatic-publication-of-facts). It acts as the code subject `civic-lens:code` with the owner role. The stage follows the weekly brief stage. It has its own wakeup on the database clock, and the worker runs it beside the other stages.

Before each batch, a tick checks the release state. It stops when the active release is not the latest release. It then lists the ready actions and votes that code approved with `ListCodeApprovedUnpublishedAsync`, up to 64 of each kind. The owner list uses the read of all approved records. The tick publishes up to 64 records with `PublishRelease`. A newer approved revision of a published record is a normal addition, and `RequirePublishable` accepts it. The tick repeats until no ready record is left. Then the stage waits for the next full hour.

The tick stops early in two cases. A `PublicationConflictException` ends it, and the next tick builds again. A replay ends it too. A replay happens after a rollback followed by a CLI publish: the rolled-back records list again, and their key finds the stored release.

A record can fail validation while `PublishedRecordLoader.LoadAsync` builds it, for example when an official has no configured public name. The loader tags the exception with the record. The tick leaves that record out, reports it, and builds the batch again with the others. The next tick tries the record again.

### Rollback

Rollback records an earlier release as active and then points the link at it. It also requeues the brief of the week of each record that differs between the two releases. The next publication builds on the rolled-back release, so it does not restore the records that were rolled back. A publication built before a rollback fails on commit.

The activate command reads the manifest of the replaced release and the manifest of the release that the link serves after the switch. It reports three lists next to the release summary. `restoredWithdrawals` holds the records that the replaced release withdrew and the activated release holds as records. `withdrawnAgain` holds the records that the replaced release held and the activated release withdraws. `blocked` holds the records of the activated release that review now blocks. The reads are advice and take no lock. If a read fails, the command still returns the summary and logs a warning, because the switch is done. A failure of the served manifest empties all three lists. A failure of the replaced manifest empties the first two lists. A failure of the review read empties `blocked`.

### Owner publish section

The Review home page shows a publish section to the owner only, and the handlers also enforce the owner role. The ready-to-publish read lists approved document changes, statements, actions, votes, relationships, and briefs that the active release does not hold at their current revision. A brief or relationship whose citations are not all current in the active release is not listed. A record is a replacement when the active release holds an older revision. Otherwise it is new.

SQL selects a bounded candidate set for each kind from the review and active-release tables. Application then applies the one publishability rule in `PublishedRecordRules`, which the publish handler also uses. The kinds share the publish limit equally. A kind with fewer ready records gives its unused share to the other kinds.

The owner selects records with checkboxes. A summary step lists each headline, its kind, and the next release number. Each replacement row has a note box. A replacement without a note shows a message and publishes nothing. Only the confirm form calls the publish handler, with one idempotency key for each page render. The page lists recent releases read-only.

### Blocked published records

`ListBlockedPublished` serves the owner list of published records that review blocks. It reads the active manifest and gives the entries to `BlockedPublishedRecords`. That class reads the current review status of each entry with `IPublicationStore.ReadReviewStatusesAsync` and keeps the entries that `PublishedRecordRules.IsWithdrawable` accepts. The store method uses the same read as the commit check for a withdrawal, so the list and the commit agree. Each row holds the kind, the record ID, the headline, the published revision, and the review status. The list is empty when no release is active.

The CLI command `releases blocked` and the Blocked by review panel on the Review home page show the list. The panel links each row to the editor and shows the `releases publish <key> --withdraw <kind>:<id> "note"` command. The home page reads the active manifest a second time for this panel. The panel is for the owner only.

### Corrections and withdrawal

A correction replaces a record. A withdrawal removes it. Withdrawing approval in review does not change published artifacts. Only a publish with `--withdraw` does.

Each of the six record files holds a `corrections` list of `PublishedCorrection`. An entry holds the replaced revision number, the publication time, and an optional note. A note means a person correction. No note means that code updated the record from the source. The list runs newest first. It holds at most 20 entries with a note. A code update replaces a newest code entry, so code entries never pile up. A record that no release replaced has an empty list.

`PublicationCorrections` owns the list and the note rule. A publish that replaces a record of the active release reads the earlier list from the record file of that release. It puts the new entry first. The note check on a first publication runs here, after the idempotency lookup, because it needs the active release. A replay never runs it. A person must give a note for each replacement. The code subject gives no note. `PublishReleaseRequest.Notes` carries the notes, and the idempotency hash covers them. The publish refuses a note on a first publication, a note for a record outside the request, and two notes for one record. It also refuses a blank or NUL note. It counts a Windows line break as one character.

The record page shows each entry above the other panels. The Timeline panel adds an event for each entry. A page that a later publish renders again keeps the entries, because the page reads them from the record file.

A withdrawal needs the owner and a note. `PublishReleaseRequest.Withdrawals` carries the notes, and the idempotency hash covers them. A request can have withdrawals and no records. The record must be in the active release. At commit, review must have blocked the record.

`PublicationWithdrawals` builds one `PublishedWithdrawal` for each withdrawn record. It holds the kind, the record ID, the withdrawn revision, both times, the note, and the correction list of the record. The manifest keeps the entry in `withdrawals`. The release holds no `records/{id}.json` for the record. The page `records/{id}.html` is a notice. A later publish links the notice from the previous release.

`WithdrawalCascade` runs after the publish loads its additions. It refuses the withdrawal while a relationship or a brief that stays in the release cites a withdrawn record. It finds relationships with `IRelationshipReviewStore.FindCitingAsync` over the carried relationship IDs. It reads each carried brief file for its citations. The error lists the citing records. A record that the same request adds meets the same rule earlier. `PublicationBuild.WithRemoved` takes the withdrawn records out of the release records that the loaders check.

A withdrawn relationship leaves the related panels of the statement and of the action or vote that it cited. The publish writes those pages again. A withdrawn or returned action changes the bill link of the carried votes on its bill. The store finds those votes with `FindVoteRecordIdsOnBillsOfActionsAsync`, the inverse of the bill lookup, and the publish writes their pages again. A withdrawn vote leaves the vote files of its members. It reads only the Congress of the vote file, and the members come from the database as for a replaced vote. A Congress with no row left disappears. A withdrawn record counts as a change for each official it named, so the publish writes their pages again. A withdrawal requeues the brief of the week of the record; see [briefs](briefs.md#staleness).

A person brings a withdrawn record back by publishing its ID with a note, once review has approved a higher revision. `PublicationCorrections` continues the corrections from the withdrawal and adds one entry for the withdrawn revision. The publish drops the returned ID from `withdrawals`, so the manifest lists the record again. The addition page replaces the notice page, because the notice loop reads only the remaining withdrawals. The owner can also select the record in the Publish section of the review UI and write a note. The code subject cannot return a record. `WithdrawnFactException` tags the record, so the stage `factPublishing` logs one line and leaves the record out.

A relationship or a brief that cited the record stays withdrawn. A person publishes it again, in the same request or later. The pages of officials, the vote files, the search rows, and the brief requeue follow the added record, as for any other addition.

### Vote record

`PublishedVote` is the contract of a vote record. `PublishedVoteBuilder` builds it from an approved `VoteDraftRevision`, the review decisions, and the cited extractions. It maps each member official through `PublishedRecordRules.MapOfficial` and copies each citation through `PublishedRecordRules.Cite`. The vote kind enum mirrors the Core `VoteKind`. `PublishVoteTests` tests the builder through `PublishRelease`, as for the other kinds.

The builder reads the result from the saved result line. `VoteTally` reads the totals from the saved total lines. It reads the member lines of the first cited member extraction, which holds every member of the roll call. It groups the casts by the party that `VoteParties` gives for the vote day. `PublishRelease` reads the latest member snapshot once for each publish. `PublicationBuild` carries it to `VoteRecordLoader`, and `ReleaseDataFiles` passes it to `PublicationOfficials.ResolveAsync`. The source party letter of a member line serves the House cross-check and the party of a member who left the roster. The Senate has no party total lines, so its cross-check uses the count line. The official pages and the search service list votes. `VoteRecordLoader` owns the vote kind for publish and the ready list. `PostgresVoteReviewStore.GetForPublicationAsync` reads the selected drafts, their review cycles, and the cited extractions. It also reads the IDs of the action records with the same congress, bill type, and bill number. Several bill sources can draft one bill, so there can be more than one ID. The loader passes the first ID whose action record is in the release to `RenderVoteAsync`. The release holds an action record when the base release has it or the same publish adds it. Loaders run in list order and action comes before vote, so a same-release action counts. The page links to it. Otherwise the page shows the bill as text.

### Relationship record

`PublishedRelationship` is the contract of a relationship record. `PublishedRelationshipBuilder` builds it from an approved `RelationshipRevision`, the cited statement revision with its article text, and the cited target. `RelationshipRecordLoader` owns the kind for publish and the ready list, as `BriefRecordLoader` does for briefs. `PostgresRelationshipReviewStore.GetForPublicationAsync` reads the selected drafts and their cited revisions in one repeatable-read transaction. It flags each relationship whose cited revisions are not current in the release that the loader passes. The ready-list read uses the active release.

The review flag "cited records changed" keeps the approved-revision rule of [statements](statements.md#relationship-review). Publication uses the release rule above, as briefs do. The two flags can differ, because a cited record can be approved at a newer revision that the release does not hold yet.

A relationship page names the cited revision number of each side. It links to the current page of each cited record, which can show a newer revision. The page shows the reason, the quote of the statement, and the fact of the target. Its caveat says that the link states no verdict.

### Related records

A statement, action, or vote page lists the relationships of the new release that cite its record. The page step builds the list at render time. `ReleaseLinks` holds the relationships of the new release: the ones that the publish adds, and the carried ones that it reads from the previous release. One database read names the carried relationships that cite a record this publish renders. `PostgresRelationshipReviewStore.FindCitingAsync` does it from the pair rows. The publish then reads only those files, and none when it adds no statement, action, vote, or relationship. `PublishedRecordFiles.MaximumCitedRecordBytes` caps the read of a cited record. It derives from the source limits, so it holds the largest action record. `ReleaseLinks.Citing` orders a list by the statement date, with an undated statement last, and then by record ID.

`ReleasePages` renders every page that the publish writes. A loader gives each added record a page renderer that takes its related list. A record that the publish adds or replaces therefore lists its links, including the carried ones. A statement, action, or vote that an added link cites, and that the release carries, gets its page written again. `ICarriedPageLoader.RenderCarriedAsync` renders it from the carried record file with the related list. The kind loader owns this step, so the vote loader finds the action record of the bill again. `PublishRelease` links the record file of such a record and writes the new page.

A record page that no new link cites, and that the publish does not add or replace, stays a hard link. A later publish that replaces a cited record lists its carried links.

## Storage and contracts

- The generated [publication schema](schema/publication.md) lists every table, column, key, check, index, and trigger.
- Each release row lists its records as kind, record ID, and revision. It does not list withdrawn records.
- The manifest `release.json` holds `records` and `withdrawals`. A withdrawal holds the kind, the record ID, the withdrawn revision, the first publication time, the withdrawal time, the note, and the corrections. The field `withdrawals` is required. A returned record leaves `withdrawals`.
- The ready lists read the active row and match by kind, so a statement ID cannot hide a document change.
- The `photo` of an official profile is null when the official has no photo. It is a fact about the official, not a field for an older version. The manifest and the record files carry no optional field that exists for an older version. Each manifest entry requires `kind`, `officials`, `issueIds`, and `policyAreaIds`. Each vote record and each row of the official vote files holds `chamber` (`house` or `senate`). Each row of the official vote files holds `kind` and `issueIds`. Each of the six record files holds `corrections`, and the manifest holds `withdrawals`; see [Corrections and withdrawal](#corrections-and-withdrawal). The files `officials.json`, `catalog.json`, and `officials/{id}/votes-{congress}.json` are part of each release. Action and vote records require `textOrigin` (`model` or `person`). `PublishedOfficeTerm` allows a null party and a null end. Readers accept version 1 only. A release of another version is not readable, so do the dev reset before the first version 1 publish; see [operations](../operations.md#publish-a-static-release).
- `PublishedOfficials` and `PublishedCatalog` each have a `Validate` method. `IssueConfiguration` refuses an issue or policy area name over 256 characters, so a catalog entry never fails the publish. Officials are capped at `PublishedOfficials.MaximumOfficials`, each official at `PublishedOfficials.MaximumTerms` terms, the catalog at `PublishedCatalog.MaximumEntries` entries in each list, and every text value at 256 characters. The search service ignores both files. `PublishedOfficialVotes` is capped at `PublishedOfficialVotes.MaximumVotes` rows and `PublishedOfficialVotes.MaximumBytes` bytes, and its rows hold one Congress. A row allows 64 issue IDs of 256 characters, so `PublishedOfficialVotes.MaximumBytesPerVote` is 52 KB, which allows 3 bytes for each character.

|---|---|---|---|---|---|---|
| `officials` (ID and configured name) | Officials | Speakers | The sponsor, when tracked | Empty | Empty | The speakers of the statement |
| `issueIds` | Issue IDs | Issue IDs | Tracked issue IDs | Empty | Tracked issue IDs | The issue IDs of both sides |
| `policyAreaIds` | Empty | Policy area IDs | The policy area ID stored with the approved revision, or empty | Empty | Empty | The policy area IDs of both sides |

| `eventDate` | Evidenced change date, or empty | Evidenced statement date, or empty | Latest sponsored or withdrawn date | The Monday that starts the week | The vote day | The statement date, or empty |

- `src/CivicLens.Publication.Contracts/PublicationProtocol.cs` owns the version; see [Behavior versions](../architecture.md#behavior-versions).
- Each release also holds `release.json.gz` and `release.json.br`, at `PublicationProtocol.ManifestGzipPath` and `ManifestBrotliPath`. They compress the exact manifest bytes, so a static server can send them without compressing on each request.
- A separate static file server serves the release root read-only. It has no access to operational storage.

## Limits and planned work

- A release carries unchanged pages from an earlier release by hard link. Such a page keeps the head it was written with until a publish writes it again.
- An official with no vote file has no current Congress, so the page shows no issue panel. A statement with no day counts in the Congress of its first publication day.
- A House resolution roll call whose bill title has not arrived is classed as Passage, so it counts as substantive; see the [votes limit](votes.md#limits-and-planned-work).
- Missed votes count only published roll calls. A roll call whose vote did not publish, such as a blocked or refused vote, is in neither the missed count nor the held count.
- The profile counts a roll call once. Any cast other than "Not Voting" counts, so a House free-text cast counts. A sponsorship counts in the Congress of its latest sponsorship day, which can be a withdrawal day.
- Real bill titles have at most 544 characters in development data. A release where every action entry has a 4,000 character title is over 32 MB. The publish then refuses it with a clear error.
- A row of an official vote file can hold 64 issue IDs of 256 characters. The read cap of a file is therefore about 266 MB. Real issue IDs have at most 60 characters.
- Each release links its photo files, so a photo file stays on disk while any release uses it. Keep-last-N retention removes it with the last release that links it. A takedown of one photo needs a new publish; see the [roster limits](roster.md#limits-and-planned-work).
- Release directories grow until [R-24](../roadmap.md#later) adds keep-last-N retention. Each release is about 29 MB in development. A backlog makes several releases in one tick.
- A record that cannot build still takes a place in the 64 records that the tick lists. More than 63 such records in one kind can hide other records until a person fixes them.
- A ready record that cannot build is logged at error level at every tick until a person fixes it. A store read that fails, for example on a changed citation, fails the tick.
- After a rollback and a CLI publish, the rolled-back records list again with the same key. The stage replays the stored release each tick and publishes nothing until new records change the batch. Publish those records with the CLI.
- The stage has no heartbeat or status row yet. [R-21](../roadmap.md#later) adds the process view.
- A vote record embeds at most `PublishedVote.MaximumSources` sources: the detail, the members, and the bill detail.
- An action record embeds at most `PublishedAction.MaximumSources` sources. The worst case is the detail page, 3 cosponsor pages (250 rows), and the summaries page, which is 5 sources. A record over the cap fails publish loudly.
- The stage `factPublishing` leaves out a withdrawn action or vote that code approves again. It logs one line for each skipped record at every tick, until a person returns the record.
- A returned record counts against the cap of 20 notes. A record with 20 notes cannot return yet.
- The review UI returns a record through the same select and confirm steps as a publish. It cannot withdraw a record. Only the CLI withdraws.
- A relationship or a brief that cited a withdrawn record stays withdrawn when the record returns. A person must publish it again.
- A withdrawn record still answers with its notice page and status 200. A static 410 needs a Cloudflare rule, which comes with [R-24](../roadmap.md#later). The search service has the same limit; see [search](search.md). The notice page has no `noindex`.
- The withdrawal check of citations reads every carried brief file when the request withdraws a statement, a document change, or an action. The cost grows with the number of briefs.
- Old release directories keep the withdrawn content until [R-24](../roadmap.md#later) adds retention. A pinned search release can still find the record; see [search](search.md).
- A replacement reads the record file of each replaced record in the active release, to copy its corrections. The cost grows with the number of replaced records, at most 64.
- A record keeps at most 20 corrections with a note. A person cannot publish a 21st correction of one record yet. Code updates still publish.
- A rollback followed by a publish drops the rolled-back revision and its note from the history. The list copies forward from the active release. A rollback to a release before a withdrawal restores the record. A publish from there drops the withdrawal history.
- The R2 upload, the CDN, and the local Caddy container are not built yet. They are part of R-24.
- An official page lists every entry that names the official, with no paging. A statement-heavy official can have a long page. A relationship or a document change that names the official appears with the other entries.
- A replaced vote touches its old members in every Congress of the replaced votes of that publish. The result is correct, but a publish may rewrite identical files.
- An official who is configured again keeps the "no longer tracked" notice until a publish touches the official. The profile does not record the notice.
- Votes of one day on an official page follow the record ID, not the roll call number.
- Official pages stay unpaged. Add year paging only if a measured official page grows too large.
- A related list orders links by the statement date. On a statement page every link has the same date, so the order there falls back to the link ID. Dates of the target records are not in the relationship file.
- A publish that adds or replaces a statement, action, vote, or relationship reads the carried relationship files that cite those records. It also sends the IDs of all relationships in the release to one database query. The cost of the query grows with the number of published relationships.
- A carried vote page lists a bill action link only when the release holds an action of that bill. A later action does not write the vote page again.
- A relationship flagged "no longer matches" still publishes. Only a person withdraws it. The owner publish list and the summary step show the flag. The `releases publish` command shows no flag, because it names records by ID and prints only the release summary.
- A relationship waits in the owner publish list until both cited records are in the active release. This follows the rule for briefs. The owner publishes the cited records first, and then the relationship.
- Expandable evidence and shareable records are planned against published releases.
- Public filter pages are an MVP requirement. The issue, policy area, and official pages are built.
- A facet page lists the officials and the event day of each record. It does not list the issues of a record. The all-records and home pages stay newest by first publication.
- Reader reports on a published record go through the search service. The operational application pulls each report into the review queue, and a person handles it; see [review](review.md#reader-reports). The report names the record ID, the revision, and the release number. A correction banner shows on the review page of the record until the active release holds a newer revision.
- Split the manifest by kind when it grows over 4 MB.
- At 20,000 entries the worst realistic manifest is about 14.6 MB, under three quarters of the 32 MB cap. `PublishRelease` refuses a manifest over the cap.
- A facet ID that the catalog does not name still gets pages, and they show the ID. This keeps a carried record from blocking a later publish after an issue leaves the configuration. `PublicationProtocol.MaximumFacetIdLength` is the one length limit. `IssueConfiguration` applies it to configured issue and policy area IDs, so the configuration fails to load on a longer ID. A carried manifest ID can still be longer or can hold other characters. Such a facet ID gets no pages. The facet list shows its ID with no link.
- The manifest filter fields stay, because the facet pages and the search service use them.
- Each release row stores `records_json`, about 2 MB at 20,000 records. Review queries expand the active one.
- A future live public Blazor deployment must read published releases only and stay separate from the operational application.
- Each publish rebuilds the home, all-records, search, and facet pages from the manifest in memory. The measured case has 20,000 records, 100 issues, 20 policy areas, 2 issues and 1 policy area for each record, and a local disk. It writes 1,603 page files, which are 400 all-records pages, 1,200 facet pages, the home page, `issues.html`, and `search.html`. They total 33 MB, and rendering and writing them takes about 1.0 second. The file count is one page for each 50 records of each facet, so it grows with the number of facet memberships, not with releases. A record holds up to 64 issue IDs and 64 policy area IDs, so the facet page count has no fixed cap. Only the configured issues keep it low.
- A future mobile client would read public release contracts through an API, not operational storage.
- Public MCP will expose `search_records`, `get_record`, `get_official_timeline`, and `compare_document_versions`. It returns published data with IDs, citations, dates, review status, coverage caveats, and the release ID.
- Public MCP cannot start collection, inference, or edits. It bounds and pages responses, limits requests, and accepts record IDs, not arbitrary fetch URLs. It treats source passages as untrusted attributed content.
- Public MCP will search through the search service API, over the same entries as the website. The website and public MCP will share one release, and clients can pin it across calls.
- Public MCP needs request compute, but never the local database or AI inference.
- Postgres and capture files need coordinated backups and a tested restore. Production backup rules are in [host](host.md#limits-and-planned-work).
- Retention must keep the evidence that published releases reference. Disposable captures follow an explicit policy, which is not agreed yet.
- Monitoring must cover freshness, skipped and deferred work, source failures, storage, and spend.
- See [roadmap](../roadmap.md) for order.
