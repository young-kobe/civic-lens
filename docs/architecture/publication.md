# Publication

## Purpose

The publication feature turns approved revisions into immutable, cumulative releases of data files. It activates a release atomically. The publisher writes data only and writes no page. `PublicApi` serves every public page. Caddy serves only the member photos of the active release.

## Decisions

- Only the owner publishes or activates a release. One exception exists: the worker stage `publishing` publishes as the code subject.
- A record is published at its current revision, and only when that revision is approved and has no unresolved concerns. Code can approve an action, a vote, or an executive action. People approve the other kinds. The worker and the owner publish all kinds.
- The `publishing` stage publishes every approved record of every kind, whoever approved it. A person approval needs no owner step. A person approval that replaces a published record needs a correction note. The editor writes the note when the person approves, and the approval decision keeps it. The worker leaves the record out and logs it in two cases. The approval has no note, or the record already has 20 corrections with a note. The other records still publish. A note on a first publication is dropped. A relationship or a brief lists only when its citations are current in the active release. A later wake publishes it when its citations are current.
- The stage wakes when the worker starts, about 60 seconds after an approval, and at each full hour. It also wakes when the gap of 10 minutes after the newest release ends. A wake makes at most one release. It publishes up to 64 ready records. Each of the seven kinds gets an equal share. A kind with fewer ready records gives its unused share to the others. A wake with nothing ready makes no release, except a status-only release on a wake that passed a full hour. A wake inside the gap makes no release. A kind alternates published replacements and new records, a replacement first, and replacements fill at most half of the kind while new records wait. A correction reaches readers soon. At the record cap, the batch shrinks to the free slots; see the record cap invariant.
- A read of one kind can hold rows that are not ready. One example is a brief with changed citations. The tick reads that kind again without those rows. It stops when the kind has enough ready records or no row is left. A not ready record may become ready after the next release, so only that listing leaves it out. Enforced by `PublishApprovedRecords.ListKindAsync` and `PublishedRecordLoader.ListReadyAsync`, which reports the IDs of the rows that it dropped. Test: `PublishApprovedRecordsTests.ManyRowsThatAreNotReadyDoNotHideAReadyRecordBecauseTheReadRepeatsWithoutThem`.
- A publication conflict ends the tick. A race with an owner publish is normal, and the next tick builds again from the latest release. Any other failure is reported and counted as a stage failure.
- The stage waits while the active release is not the latest release. This is the state after `releases activate` rolls back. It resumes when the owner activates the latest release or publishes from the CLI.
- A record that fails validation while the stage loads it is left out of the batch and reported with its ID and message. The other records publish in one release. The next tick tries the record again.
- `PublicApi` serves every public page by server rendering. The pages read the `public_api` views, so each public fact has one owner. Cloudflare caches each page for each release and serves a stale copy for 24 hours when the service is down. See [public site](public-site.md).
- A published executive action holds its AI summary, with a citation for each sentence, when its revision has one. The text of the document is then a source of the record. See [executive actions](executive-actions.md#publication).
- A newer draft never replaces published content automatically.
- A release is cumulative. It holds the base release records plus explicit additions or replacements.
- Each vote kind, executive action type, and cast word that has a definition maps to its term. `PublishedRecordLabels` enforces the map. Test: TEST-PENDING (each vote kind, executive action type, and cast word maps to its glossary term).
- Carried records are hard links to the immutable files of the base release. Disk therefore grows with published records, not with the number of releases.
- Each publish rebuilds `release.json`, `officials.json`, `officials-summary.json`, and `bill-status.json`. It reads the previous manifest once, under the 64 MiB manifest cap, `PublicationProtocol.MaximumManifestBytes`. It reads the previous `officials.json` once, under `PublishedOfficials.MaximumBytes`. It rebuilds the vote files and the summary row of an official only when the official is touched; see the invariants. `PublicationProtocol.MaximumRecordsPerRelease` is the one owner of the record limit, which is 40,000. The database has no count check, because C# owns the rule.
- Postgres records which release is active. The `current` link is only a copy for Caddy, which serves the photos, so a failed link swap never drops committed records.
- Every publication write takes all seven review locks in one fixed order, which prevents a deadlock. The order is in [advisory locks](../architecture.md#advisory-locks).
- A release has no status column. `is_active` marks the one active release: a commit sets it on the new row and clears the old one, and rollback moves it.
- Rollback is a CLI command only. The workspace has no rollback or activate control.
- The host keeps the files of the 30 highest release numbers and the active release. It also keeps the newest release of each of the last 7 UTC days. The database keeps every release row. Briefs, the release list, and the stale brief check read the rows. The [search](search.md) service reads release files over HTTP, so a pruned release on the host does not break it.
- At launch, Caddy serves the photos of the active release through the Cloudflare tunnel on civic-lens.info. See [Web server](../operations.md#web-server).
- Publish stages and checks a release on the server. The active release changes only after the checks pass.
- Locally, a Caddy container serves `/photos/{hash}.jpg` from the release root.
- Each manifest entry carries filters, so a reader of the manifest needs no record file reads. Each published record type owns the mapping in its `ToEntry` method. A filter that the kind has no fact for stays empty; publish never guesses it.
- One loader owns each record kind: its ID shape, its ready list, and how publish loads and builds it. `PublishedRecordLoaders` lists them, and the publish and ready-list handlers go through that list. One loader owns the Application side of a kind. The other per-kind places are the `PublicationProtocol.IsRecordId` arm, the store state check, `PublishedRecordLabels.Kind`, and the review link.
- The loader base class gives each kind one owner for its Application rules. A non-generic base exists only so `PublishedRecordLoaders` can hold all record kinds in one list. The seven kinds are real variation, with different IDs, stores, and records. The precedents are `PostgresAnalysisStore<TRun>` and `ReviewRecordPage`.
- `PublishedRecordLoader<TCandidate, TAddition>` owns the ready-list and load steps once. A kind supplies only its store reads, its ready row, and how it builds one record. `PublishedRecordRules.Cite` is the one owner of a published citation for every kind.
- Official names in every record kind come from the current `PublicationCatalog`, not from stored revisions. The action `policyAreaIds` filter comes from the policy area ID that the draft stored. Drafting resolved it through `IssueConfiguration.PolicyAreaIdFor`, and the reviewer approved it with the revision. Publish never reads the issue configuration. A label that the configuration lacked at draft time gives an empty filter.
- A record ID is unique across all kinds, because all kinds share the flat `records/{id}` paths.
- A brief record embeds no source text. It holds the wording that a person approved and a list of citations. Each citation names a published record by kind, ID, and revision, and carries a copy of the cited headline. A brief is a weekly summary over other records, so it publishes only when the new release holds every record that it cites; see [briefs](briefs.md#publication).
- An action record embeds the full text of each cited extraction once. Each citation names its extraction, and the contract checks the quote against that source.
- The latest action of the bill of an action record lives in `bill-status.json`, not in the record file or the manifest. A bill moves after approval, and a record revision stays frozen. The file holds one row for each action record of the release that has a stored status. A row has the record ID, the text, the date, and the time that Civic Lens read it. An action with no stored status has no row. An older reader ignores the file. See [bill status line](#bill-status-line).
- A relationship record links one statement to one action or vote. It embeds no source text. It holds the wording that a person approved, the quote of the statement, and the fact of the target. Both are text. It also holds a citation of each side. A citation names a record by kind, ID, and revision, and carries a copy of the headline. A relationship publishes only when the new release holds both cited revisions and the latest decision on each is an approval. A link that a release already holds stays in later releases, whatever happens to the records that it cites. See [relationship record](#relationship-record).
- A vote record embeds the full text of each cited extraction once, as an action record does. Its citations are the vote day, the kind, the result facts, and the cast of each tracked member. The kind can be nomination, cloture, or motion to proceed. Only Senate votes use these three. They are new enum names, so they need no version bump. `PublishedEvidenceRules` owns the source and citation checks for actions and votes. A vote record also holds the raw result wording of the source, the totals of the whole roll call, and the majority of each party. See [Vote record](#vote-record).
- The manifest schema version is 1. A new record kind needs no version bump, because every reader ships with or after the release it reads. The publisher reads only releases of the current schema version. An older publisher fails loudly on the unknown kind.
- Release JSON uses relaxed escaping (`JavaScriptEncoder.UnsafeRelaxedJsonEscaping`), so non-ASCII letters and punctuation take UTF-8 bytes, not 6-byte `\uXXXX` escapes. This is safe because release JSON is fetched as JSON and never inlined in HTML or a script tag. Readers do not change.
- Unreviewed proposals, internal reviewer notes, operational job details, and mutation controls stay private.
- Public serving reads the `public_api` views and the photo files of the release. It never reads other operational storage or private notes.
- Search goes to the [search](search.md) service, which is also the public read API. The browser does not search the manifest.
- A release holds the member photos that its officials show. A photo file is named by the SHA-256 hash of the capture, not of the decoded image bytes: `photos/{hash}.jpg`. A name therefore never changes its bytes, and a changed photo gets a new name. A hash name lets a CDN keep a photo for a long time.
- A publish writes the newest stored photo row of each official whose newest setting does not withhold the photo. It reads a capture only for a hash that the previous release lacks, and it links every other photo. Every publish path gets the artifact directory for this read: the worker, `releases publish`, and the review workspace. The directory is required: `releases publish` and the review workspace refuse to start without `CIVIC_LENS_ARTIFACT_DIRECTORY`.
- A new photo that cannot be read does not fail the publish. The profile keeps the photo of the previous release, and the file is linked. With no previous photo the official has no photo. Both cases log an error with the person and the attempt. A cancelled token, a database error, and a missing file in the previous release still fail the publish.
- A photo is only for the portrait on the official page and on the officials list. Photos are never used in ads.
- Only a person withdraws a record. The owner gives `--withdraw <kind>:<id> <note>` to `releases publish`, or uses Take off site on the record editor. A request can have withdrawals and no records. The code subject withdraws nothing.
- A record can leave the release only when review blocked it. Its status is `ApprovalWithdrawn`, `ChangesRequested`, `AwaitingReviewWithConcerns`, or `Rejected`. The commit checks this under the review locks.
- A withdrawal removes the record from the manifest `records` list and adds a `PublishedWithdrawal` to the manifest `withdrawals` list. The release keeps no record file. `PublicApi` then serves a notice with no headline, body, or officials.
- A withdrawal never leaves a link to nothing. The publish refuses to withdraw a record while a relationship or a brief that stays in the release cites it. The owner withdraws the citing records in the same request.
- A person brings a withdrawn record back. The worker returns it when a person approved a higher revision with a correction note. A record whose newest approval has no note, or was made by code, stays withdrawn. The worker logs it and skips it. The owner can also run `releases publish <key> <kind>:<id>`, but only for a person approval. A code approval never returns a record, on any path. To free the record, a person withdraws the code approval and approves the revision again with a note.
- The entries backfill takes the entry of a revision from the oldest kept folder whose release lies in the range of the state row. It compares the entry in every later kept folder of that range, and a difference blocks the row with the reason `foldersDiffer`. A kept folder of that range that omits the revision or lists another revision is a difference too. A kept folder holds `release.json`. A missing manifest file means the folder was retired.
- A mismatch skips the row with a reason and never fixes a value. The run goes on. The command exits with 1 when a row was skipped or an open range has no row. It also exits with 1 when the limit left a checked range without a row.
- The entries backfill takes no advisory lock. It relies on `PublishedEntries.InsertAsync`: `ON CONFLICT DO NOTHING` and `RequireSameAsync` make a rerun and a race with a commit safe.
- One class, `ReleaseEntryComparison`, owns the rule that two entries agree outside the eight new fields. `ReleaseEntryRewrite` and the entries backfill both call it.
- The entries backfill runs now, before the other backfills. It reports the counts that it cannot prove, and it does not wait for the other backfills.

### Approved public data extensions

R-68 in the [roadmap](../roadmap.md#active-r-68-redesign) owns the remaining approved extensions and completion gates.

- Each release binds its exact record revisions to immutable correction histories. Equal ordered histories share one verified content-addressed body.

## Invariants

- **Bounded correction bootstrap.** The owner command counts attempted candidate files, including invalid files, against its requested limit. Small keyset pages bound memory. The candidate query limits rows after the cursor within each selected release. It then applies the global page limit and lookahead across releases. The outer release lower bound prevents rescanning earlier releases. A continuation cursor reaches later records; a fresh scan retries earlier failures. `BackfillCorrectionHistories` and `PublishedEntries` enforce these rules. Tests: `BackfillCorrectionHistoriesTests`, `PostgresCorrectionHistoryTests`, and `ReleaseCommandTests`.
- **Bounded correction verification.** The owner command checks existing and missing bindings against immutable files, with a requested file limit. Each store page covers one selected release. Its candidate query reads at most the page limit plus one row after the cursor position within that release. Store pages use short read-only repeatable-read transactions that close before file reads. Enforcers: `VerifyCorrectionHistories` and `PostgresPublicationStore`. Tests: `VerifyCorrectionHistoriesTests`, `PostgresCorrectionHistoryTests.VerificationPageReadsInsideARepeatableReadReadOnlyTransactionAndWritesNothing`, and `ReleaseCommandTests`.
- **Verification binds to one release.** A release and its correction bindings are immutable. The cursor holds the release number, the directory name, and the last record. It also holds the failures already found in that release. A change to the selected release set never fails the whole run. The walk goes through the selected releases in release order. Suppose the cursor names a release that the selection no longer holds under that number and directory. The release then appears in `skippedReleases` with reason `notSelected` or `directoryChanged`. The walk then continues with the next selected release. Enforcers: `CorrectionHistoryWalk` and `VerifyCorrectionHistories`. Tests: `VerifyCorrectionHistoriesTests.ReleaseRetiredMidWalkIsSkippedAndReportedWhileLaterReleasesContinue`, `VerifyCorrectionHistoriesTests.ChangedDirectoryForTheSameNumberIsReportedAndTheWalkContinuesWithTheNextRelease`, and `PostgresCorrectionHistoryTests.VerificationCursorReportsADirectoryChangeForTheSameReleaseNumber`.
- **A verified release has no failed record.** `verifiedReleases` lists a release only when its last record page finished in this call. No record of the release may fail. This holds for this call and for earlier calls that the cursor carries. A corrupt binding fails its own release and hides no other release. Enforcer: `VerifyCorrectionHistories`. Tests: `VerifyCorrectionHistoriesTests.ReleaseIsNeverVerifiedWhenAnyRecordFailedInThisCallOrInAnEarlierCall` and `VerifyCorrectionHistoriesTests.CorruptBindingInOneReleaseFailsItsRecordsWithoutHidingOtherReleases`.
- **The result lists the selection after the last file read.** `selection` holds the number, the directory name, and a start cursor of each selected release. It is read after the last file read. A release added after the walk started appears there. The walk also reaches it when its number is above the cursor. Enforcers: `VerifyCorrectionHistories` and `PostgresPublicationStore.ReadRetainedReleaseSelectionAsync`. Tests: `VerifyCorrectionHistoriesTests.ReleaseAddedAfterTheWalkEndedIsListedAndVerifiedOnItsOwnFromItsSelectionCursor` and `VerifyCorrectionHistoriesTests.ReleaseAddedBetweenCallsIsReachedByTheSameWalk`.
- **Bill count rollout.** The owner backfill writes one release per transaction. It writes only after the manifest, officials file, and record files agree with the tables in both directions. The write transaction then checks retention, directory, and membership again under the review locks. An exact snapshot replays, a partial or changed one fails without repair, and a release with no Congress to count fails and rolls back. Enforcers: `ReleaseBillCountFiles`, `BackfillReleaseBillCounts`, `PostgresPublicationStore.CommitBillCountsAsync`, and `ReleaseBillCounts.FillAsync`. Tests: `BackfillReleaseBillCountsTests`, `PostgresReleaseBillCountsTests.OwnerBackfillWritesTheRowsThatTheReadOnlyVerifierAcceptsAndReplayChangesNothing`, `PostgresReleaseBillCountsTests.OwnerWriteRefusesAReleaseThatWasRetiredAfterItsFilesWereChecked`, `PostgresReleaseBillCountsTests.OwnerWriteAndVerifierRefuseMembershipThatDiffersFromWhatTheFilesWereCheckedAgainstInEitherDirection`, `PostgresReleaseBillCountsTests.PartialExistingSnapshotIsRefusedByTheOwnerWriteAndNotRepaired`, `PostgresReleaseBillCountsTests.ReleaseWithoutAnyCongressCoverageIsRefusedByTheWriteAndFailsTheVerifier`, and `PostgresReleaseBillCountsTests.ACountWriteFailureRollsBackBothTablesOfTheOwnerWrite`.
- **Bill count verification.** The verifier is read-only. It repeats the file checks of the backfill, then compares saved rows with the expected counts in both directions in a repeatable-read, read-only transaction. Missing rows, extra rows, changed counts, and zero saved rows all fail. The writer and the verifier use the same expected-count SQL text, so a wrong saved row cannot pass. The cursor carries the selection fingerprint, and a final selection check protects the terminal result. Enforcers: `VerifyReleaseBillCounts`, `ReleaseBillCounts.VerifyAsync`, and `PostgresPublicationStore.VerifyBillCountsAsync`. Tests: `VerifyReleaseBillCountsTests`, `PostgresReleaseBillCountsTests.VerifierFindsMissingExtraAndChangedRowsInBothDirectionsAndTreatsNoRowsAsAFailure`, `PostgresReleaseBillCountsTests.VerifierOnAReleaseWithNoRowsWritesNothing`, `PostgresReleaseBillCountsTests.ReleasePagesFollowTheCursorPinTheSelectionAndGoStaleWhenItChanges`, and `ReleaseCommandTests`.
- **Party line-up rollout.** The owner command `releases lineups backfill` converts one retained release in each transaction. It has the same limit, release-number cursor, and file checks as the bill count backfill. The JSON result adds `skipped`. It reads the manifest, the officials file, and every action and vote file before it writes, because the line-up counts the same bills. These file checks prove release membership only. The line-up rows come from the tables, not from the files. The write transaction checks retention and membership again under the review locks, and then runs `ReleaseIssuePartyCounts.FillAsync`, the writer that a new publication runs. An exact snapshot replays and counts as `alreadyPresent`. A release with no counted issue needs no rows and writes none. It counts as `skipped`, apart from `added` and `alreadyPresent`. A partial or changed snapshot fails without repair as `lineUpsInvalid`. `ReleaseIssuePartyCounts` owns the line-up rules. `ReleaseIssueCounts` owns the eligible bills. The publish writer, the backfill, and the verifier share both. Enforcers: `RetainedReleaseScan`, `BackfillReleasePartyLineUps`, `PostgresPublicationStore.CommitPartyLineUpsAsync`, and `ReleaseIssuePartyCounts.FillAsync`. Tests: `BackfillReleasePartyLineUpsTests`, `PostgresReleasePartyLineUpBackfillTests.BackfillWritesTheSameRowsThatTheFreshPublishWriterWroteForTheSameReleaseNames`, `PostgresReleasePartyLineUpBackfillTests.ARerunChangesNothingAndReportsNoWrite`, `PostgresReleasePartyLineUpBackfillTests.APartialOrChangedSnapshotIsRefusedByTheBackfillAndIsNotRepaired`, `PostgresReleasePartyLineUpBackfillTests.AReleaseWithNoCountedIssueStoresNoRowsAndServesNoLineUpAndTheVerifierAcceptsIt`, and `ReleaseCommandTests`.
- **Party line-up verification.** `releases lineups verify` is read-only and has the same cursor and fingerprint as the bill count verifier, and its result adds `skipped`. It repeats the file checks. They prove release membership only. Then one read-only repeatable-read statement compares the saved rows with the expected rows in both directions. It also checks that the parts add up to `release_issues.bills`. A read-only transaction cannot create a table. So the statement builds the expected rows as CTEs. It uses the same select texts as the writer uses for its temp tables. Missing rows give `lineUpsMissing`. A forged, extra, or changed row gives `lineUpsDifferent`. A release that expects no rows and holds none counts as `skipped`, not as `verified`, and it serves a null `lineUp`. Enforcers: `RetainedReleaseScan`, `VerifyReleasePartyLineUps`, `ReleaseIssuePartyCounts.VerifyAsync`, and `PostgresPublicationStore.VerifyPartyLineUpsAsync`. Tests: `VerifyReleasePartyLineUpsTests`, `PostgresReleasePartyLineUpBackfillTests.VerifierFindsAForgedExtraOrMissingRowInBothDirections`, `PostgresReleasePartyLineUpBackfillTests.VerifierOnAReleaseWithMissingRowsWritesNothing`, `PostgresReleasePartyLineUpBackfillTests.ARowThatNoCountedIssueExpectsIsReportedAsDifferent`, and `ReleaseCommandTests`.
- **Bootstrap publication binding.** Preparation reads only immutable private release files and verifies their identity and typed entry facts. Final binding rechecks retention, the served directory, and exact revision membership under the existing publication locks. Existing bindings must match their verified content. `PostgresPublicationStore` and `CorrectionHistoryCopies` enforce this rule. Tests: `PostgresCorrectionHistoryTests`.

- **Immutable correction history.** Every committed ordinary record has one history binding for its exact release, kind, ID, and revision. An empty body differs from a missing binding. `CorrectionHistoryCopies` validates complete bodies and rejects incompatible revision bindings. The database enforces keys, foreign keys, positions, and time ranges. Protected by `PostgresCorrectionHistoryTests` and `PublishedCorrectionHistoryIdentityTests`.

Each line gives the rule, what enforces it, and the test that protects it. Cross-feature invariants are in [architecture](../architecture.md#invariants).

- Display code writes a bill number in the official style, such as "H.R. 9576", "H.J.Res. 213", or "S. 2403". Enforced by `BillNumbers.Of` in `Publication.Contracts`, the one owner that `ActionLabels`, the official page, and any public route call. It does not rewrite stored text. Stored text keeps its own style, for example a stored headline or summary, or a Congress.gov or House Clerk line cited as evidence. `ActionCodeText.Of` writes stored code text with a strict lookup in the same table (`BillNumbers.TypeLabel`). A bill type outside the table throws there, and display shows it in upper case. Tests: `BillNumbersTests.ABillNumberPrintsInTheOfficialStyleWhateverTheCaseOfItsStoredType`, `BillNumbersTests.ABillTypeOutsideTheTableShowsInUpperCaseInDisplayButFailsAsAStoredLabel`, and `ActionCodeTextTests.EachBillTypeUsesItsPrintedAbbreviation`.
- Only an approved record with no open concern publishes. Enforced by `PublishedRecordRules.IsPublishable`, which each loader applies to its publish and its ready list. Tests: `PublishReleaseTests.RejectsDraftsThatAreNotCleanlyApproved`, `PublishActionTests.ActionThatIsNotApprovedIsRefusedBecauseNoModelOrDraftMaySpeakForTheSite`, `PublishVoteTests.AVoteWhoseRevisionNobodyApprovedIsRefusedBecauseAModelRevisionNeverPublishesAlone`, `PublishVoteTests.AVoteWithAnOpenConcernIsRefusedAndIsNotListed`, and `PublishApprovedRecordsTests.AnActionThatReviewDoesNotApproveIsNotPublishedByATickBecauseOnlyAnApprovedRecordIsReady`.
- A release holds at most `PublicationProtocol.MaximumRecordsPerRelease` records, and the manifest stays under the manifest cap at that count. Enforced by the `PublishRelease` record count check and manifest size check. Test: `PublishReleaseTests.RejectsMoreRecordsThanTheCapBeforeAnythingIsBuilt`, `PublishReleaseTests.AReleaseAtTheRecordLimitOfFilledStatementEntriesKeepsTheManifestUnderThreeQuartersOfTheManifestCap`, `PublishReleaseTests.AReleaseAtTheRecordLimitOfFilledActionEntriesKeepsTheManifestUnderThreeQuartersOfTheManifestCap`, and `PublishReleaseTests.RefusesAManifestOverTheManifestCapAndStagesNothing`.
- Vote wording uses one unconflicted cited question and result. A kind-specific meaning or next step requires a complete known question and a result compatible with that kind. A measure-specific step also requires matching cited identity. A simple resolution must belong to that chamber. `PublishedVote` owns the fact prefixes shared with the producer. `VoteWording` prepares this input once. An unsupported complete question uses the general Yes and No lines. Every reader shows the shared unknown next-step sentence when its input cannot establish a step. `VoteWordingInput`, `VoteWording`, `VoteMeaning`, `NextStep`, and `PlainVoteWords.ResultWord` enforce the rule. Tests: `VoteWordingTests.AnUnrecognizedQuestionSuffixKeepsOnlyTheApprovedGeneralMeaningAndUnknownStep`, `VoteWordingTests.AnIncompatibleResultKindUsesOnlyTheFallbacks`, `VoteWordingTests.AResolutionIdentityFromTheOtherChamberUsesTheGeneralStep`, `VoteWordingTests.MissingOrUnknownResultAndConflictingCapturedFactsUseFallbacks`, and `VoteWordingTests.AConflictingCitedMeasureIdentityDoesNotSelectAMeasureSpecificStep`.
- Manifest filters hold at most `PublishedRecordEntry.MaximumFilterValues` distinct, nonblank values, each at most `PublishedRecordEntry.MaximumFilterValueLength` characters. Enforced by `PublishedRecordEntry.Validate`, which `PublicationRelease.Validate` calls. Test: `PublicationReleaseTests.FiltersAreBoundedAndDistinctSoOneEntryCannotSwellTheManifest`.
- An entry's filters come from the revision that the release publishes. Enforced by `PublishedDocumentChange.ToEntry`, `PublishedStatement.ToEntry`, and `PublishedAction.ToEntry`. Tests: `PublishStatementTests.EachKindFillsItsSearchFiltersFromTheRevisionItPublishes`, `PublishStatementTests.ARepublishedStatementReplacesItsCarriedEntryInsteadOfDuplicatingIt`, `PublishActionTests.AnActionFillsItsSearchFiltersFromTheRevisionItPublishesAndNamesOnlyItsSponsor`, and `PublishActionTests.ARepublishedActionReplacesItsCarriedEntryInsteadOfDuplicatingIt`.
- The table `publication_record_states` holds, for every release number, exactly the records that the release lists. Each row is a range of releases that hold one revision of one record. A commit compares its records with the state of the highest release, never the active release, because a rollback makes them differ. Enforced by `PublicationRecordStates.RecordAsync`, which `PostgresPublicationStore.CommitAsync` calls in the commit transaction, and by the migration `PublicationRecordStates` for earlier releases. The migration `DropPublicationRecordsJson` compares the table with `records_json` and aborts the drop on any difference. Prune and activate write nothing to the table. After it writes the rows, one count query reads the rows that cover the new release number, carried rows included. The commit rolls back when the count differs from the number of records that the release lists. The commit throws `PublicationStateMismatchException`, which is not a publication conflict, so the worker reports it as a stage failure. `PublishRelease` deletes the staged folder, and `releases publish` prints the counts. The check guards the writer and compares counts only, so it does not catch a wrong revision or drift in earlier releases. The column `publication_releases.records_json` no longer exists. The table is the only source of the records of a release. Readers use only the table: `ReviewQueries.ReadActiveReleaseRecordsAsync`, `ReviewQueries.ReadReleaseRecordsAsync`, and `BriefFirstRelease`. - The table `published_records` is the only owner of the first publication time of a record. A record has one first time, also after a rollback. Enforced by `PublishedRecords`, the primary key on kind and record ID, and `PublishRelease`, which reads the time before it builds. The commit also calls `PublishedRecords.RequireStoredTimesAsync`. It throws `PublicationConflictException` when a stored time differs from the time in the release. Tests: `PublishFirstPublishedTests.ARecordPublishedAgainAfterARollbackKeepsItsFirstTimeInItsFileItsManifestEntryAndTheTable`, `PostgresPublishedRecordsTests.ARollbackAndAPublishOfTheRecordAgainKeepTheFirstTimeBecauseTheTableHasInsertsOnly`, and `PostgresPublishedRecordsTests.ACommitWhoseTimeDiffersFromTheStoredTimeConflictsAndWritesNoReleaseBecauseTheReleaseFileWouldSplitTheFirstTime`.
- No code updates or deletes a row of `published_records`. The commit inserts a row for each added record with `ON CONFLICT DO NOTHING`, in the commit transaction. Enforced by `PublishedRecords`, the one writer. Test: `PublishedRecordsInsertOnlyTests.OnlyThePublicationWriterTouchesFirstPublicationTimesExceptForColumnReadGrants`. It scans the production source, because no other test fits a write-only table.

## Behavior

### Public reader experience

A record explains what happened, who was involved, and when. Where evidence supports it, it explains why the event matters. It states what the evidence can and cannot establish. Readers move from the account into retained passages and exact citations. They do not need to read collection jobs or extraction metadata first.

A document-change record shows both versions, and observation history where needed to explain gaps. A current source link supplements the retained evidence; it does not replace it. Public records show their review and version context and published corrections.

### Release content

- A release folder holds only data: `release.json` with `release.json.gz` and `release.json.br`, `records/{id}.json`, `officials.json`, `officials-summary.json`, `bill-status.json`, `officials/{id}/votes-{congress}.json`, and `photos/{hash}.jpg`. It holds no page, no shared asset, no `catalog.json`, no `sitemap.xml`, no `robots.txt`, and no `404.html`. `PublicApi` serves the sitemap, the robots file, and the not found page.
- `PreviousRelease` reads `bill-status.json` to keep the status read times and to find a changed status. It carries the summary rows of `officials-summary.json`, and the publish computes the touched summaries from the vote files. `officials.json` and the record files are private snapshots for `PreviousRelease`, the backfills, and the verifies. R-63 moves them to tables later. Only `photos/` reaches readers, through Caddy.
- An executive action record has the official title as its headline. It carries the facts with their citations, and the saved Federal Register record as its one source. It has no summary. Test: TEST-PENDING (An executive action record has the official title as its headline. See [executive actions]executive-actions.md).
- Each document-change record carries the full extracted text of both versions, their source URLs, and their observation times. Changed regions are offsets into those texts.
- A citation holds an extraction ID, UTF-16 offsets, and the quoted text. The contract rejects a quote that does not match its offsets.
- Records show the approval date and the first-publication date.
- Officials, issues, and policy areas appear by their configured name. An ID with no configured name appears as the ID.
- Only the release manifest shows the schema version.
- `officials.json` lists each official that a published record names. A record names an official when its manifest entry names the official. A record also names an official when a vote of the release holds the official as a member. A vote entry names no official. Publish therefore reads the members of the vote revisions of the release in one database query. The query takes the record IDs and revision numbers of the manifest, so it covers carried votes and new ones. It returns a record ID and a person ID for each member. It sends two array parameters, so the list size does not matter. It reads no vote file for a configured person. A person who left the configuration takes the name of an entry that names the person. A person named only by votes takes the name from one vote record, read from this publish or from the previous release. Each profile holds the ID, the name, the Wikidata ID, the website, and the dated terms. A term holds the office, its `kind`, and the dates. The `kind` is `senator`, `representative`, `executive`, `judicial`, or `other`. It holds the party, the caucus, the state, and the district when the source gives them. The caucus is the party whose caucus the official joins, when it differs from the party. A term with no end is ongoing.
- `PublicationOfficials` joins a person to terms. It matches the bioguide ID to the latest member snapshot first. When no term matches, it matches the Wikidata ID to the latest executive snapshot. A person with no match is listed by name with no terms. A Wikidata ID with no executive official is not an error. The website is the valid roster URL of the member, else the website of the newest setting of the person. A former member who is not in the current roster takes the website of the newest setting. A member who leaves the roster loses the roster URL, as the terms do. A website must pass `PublishedWebsite`. A roster URL that fails the rule becomes no website and never fails a publish.
- A vote file holds the votes of one official in one Congress. A row holds the record ID, the vote day, and the roll call (Congress, session, number). It also holds the bill type and number when the vote has a bill. It holds the cast, the result, the totals, the party of the official, and the majority cast of that party. It holds the headline, the vote kind, and the tracked issue IDs. Rows are newest first. A publish takes the new rows from the vote records that it already holds. It reads a vote file only for a touched official. It finds the files of an official by a listing of one folder of the previous release. The members of the replaced revisions of all Congresses come from one database query.
- The photo files are `photos/{hash}.jpg` in the root of the release, and `PublicationProtocol` owns the path. A publish writes the file of a new photo from the capture, and links the file of a photo that the previous release holds. The setting of the artifact directory is in [operations](../operations.md#publish-a-release).

A release holds six kinds of record. Each manifest entry has a `kind`: `documentChange`, `statement`, `action`, `vote`, `brief`, or `relationship`, a lowercase camel string. All kinds share the `records/` folder, and the record data path.

| Kind | Record ID |
|---|---|
| `documentChange` | The draft ID: 32 lowercase hex characters |
| `statement` | The candidate ID: 64 characters |
| `action` | The action record ID: 64 lowercase hex characters |
| `vote` | The vote record ID: 64 lowercase hex characters |
| `brief` | The brief record ID: 64 lowercase hex characters; the [briefs](briefs.md#decisions) page defines it |
| `relationship` | The pair key: 64 lowercase hex characters; the [statements](statements.md#decisions) page defines it |

A statement record carries one source version with the full extracted text, the source URL, and the observation time. It also carries:

- speakers by configured name, and other speakers
- issues, policy areas, and bill numbers
- the optional statement date with its evidence
- 1 to 32 quotations, each with its kind: `directQuotation` or `releaseText`
- `textOrigin` and `approvedBy`, both required; see the invariants for their rules
- an optional `articleUrl`, the link of the article, when the source is a feed that lists the article. It is null when the source is the article page. A null value keeps old files valid, so the schema version stays 1.

Every quotation must equal the source text at its offsets.

The source URL of a statement is the URL that the collector requested for the cited capture. For a feed item, the source is the feed and `articleUrl` is the item link. The statement page of `PublicApi` links the article and says that the source is the feed that lists it. `PublishedStatementBuilder` sets both URLs. `PublishedStatement.Validate` requires a web URL for the link. Tests: `PublishStatementTests.AStatementFromAFeedCitesTheFeedCaptureAndLinksTheArticleBecauseTheReaderNeedsBoth`, `PublishStatementTests.AStatementFromTheArticlePageHasNoSeparateArticleLinkBecauseItsSourceIsTheArticle`, `PublishedStatementTests.RejectsAnArticleLinkThatIsNotAWebUrlBecauseTheReaderFollowsIt`, and `PublishedStatementTests.ARecordWrittenBeforeTheArticleLinkExistedStillReadsWithNoLink`.

An action record carries:

- the bill identity (congress, type, and number) and the bill title
- the policy area with its citation, the policy area ID stored at draft time, and the tracked issue IDs. The model chose the tracked issues from the policy area candidates
- the CRS summary citation, when the revision has one
- 1 to 600 sponsorships. Each has the official by configured name, the role (`sponsor` or `cosponsor`), and the original flag. It also has the sponsored date, the optional withdrawn date, and one or two citations.
- 1 to 8 sources, each with the full extracted text of one cited Congress.gov API page, its URL, and its observation time

The sources are the distinct cited extractions in citation order, so the first one is the page of the first sponsorship. Every citation must name one of the sources and quote its text exactly. A source that no citation names is rejected.

A brief record carries:

- the headline and 1 to 12 paragraphs, each with the citation IDs that it uses
- the week start (a Monday), the cutoff release number, and the coverage counts: considered, sent to the model, and cited
- 1 to 256 citations. Each has its ID, kind, record ID, revision number, and a copy of the cited headline

A relationship record carries:

- the headline, which joins the headline of the statement and the headline of the target
- a citation of the statement and a citation of the target. Each has the kind, the record ID, the revision number, and a copy of the headline
- the type, one of `describesOwnBill`, `statesPositionOn`, `claimsCreditFor`, or `statementAboutVote`, and the reason in one sentence
- the quote of the statement and the text of the fact of the target. Both are text only. The builder takes the quote from the article text. Its span must lie on the extraction of the statement and inside one passage of the statement
- the optional statement date, the speakers by configured name, and the issue and policy area IDs of both sides

The approval time of a record is the latest approval of its current revision, for every kind. One Application rule owns that time.

### Publish

One publish request names up to 64 records to publish or withdraw, each as a kind and an ID. It can name none; see the empty publish invariant. For each kind, publication loads all selected drafts and their verified evidence in one repeatable-read transaction. Each read uses a fixed number of queries for any selection of 1 to 64 drafts. The publisher builds records from this evidence and does not read it again. Before it builds, it reads the stored first publication time of the named records in one query. A record with no row, which the active release does not hold, is new and takes the clock time.

1. Application builds the release contract and writes the data files.
2. The owner action builds the release in a staging directory, verifies it, and moves it to a uniquely named directory under `releases/`.
3. Under all seven review locks, the commit checks each added record's revision and review-state version again, in the draft table of its kind. For each added brief or relationship it also checks that every citation is current in the records of the new release. For each withdrawn record it checks that review blocked the current revision. It also checks the next release number and the active release it built on. It then requeues the brief of the week of each record that the release changes, drops, or adds again; see [briefs](briefs.md#staleness).
4. In the same transaction, it records a sequentially numbered release and marks it as active. It stamps the release time from the database clock after it holds all review locks. The commit does not take a time from the caller. It also inserts the name rows of the release. It also inserts the first publication time of each added record into `published_records`, and it keeps any row that exists. It then checks that each stored time equals the time in the release. If one differs, the commit throws `PublicationConflictException`. The worker builds again at its next tick. A CLI publish exits with the error. The commit then inserts the entry rows of the added records, and it keeps any row that exists. If a kept row differs from the release entry, the commit throws the same exception. It writes the rows of the withdrawal tables.
5. After the commit, it takes all seven review locks again, reads the active release, and atomically replaces the relative `current` symbolic link.

Publish, replay, and activate all end with step 5. An older command therefore cannot move the link back after a newer one.

The review state is checked at commit, so a concurrent blocking decision cannot be ignored. A commit that fails on a conflict or invalid input deletes its directory. If that cleanup fails, or an unknown failure occurs, the directory stays. Only committed releases can be activated.

Each publication builds on the recorded active release, not on the link. A replayed publish request and the activate command both point the link at the recorded active release. This repairs a link that is out of date. Publish requests reuse the review replay receipts.

### Automatic publication

The worker runs the stage `publishing` when `CIVIC_LENS_PUBLISHING=1`; see [operations](../operations.md#automatic-publication). It acts as the code subject `civic-lens:code` with the owner role. The stage follows the weekly brief stage. It has its own wakeup on the database clock, and the worker runs it beside the other stages.

Each wake runs one pass. The pass first checks the gap; see the invariants. It then checks the release state, and it stops when the active release is not the latest release. It lists the ready records of all seven kinds with the loader ready reads, up to 64 of each kind. It keeps 64 in all, with an equal share for each kind. The pass publishes them with `PublishRelease`. A newer approved revision of a published record is a normal addition, and `RequirePublishable` accepts it. The pass makes one release. Records left over wait for the next wake.

When no record is ready, the tick checks `PublishRelease.HasBillStatusChangeAsync`. It reads the previous status file and one status query, and it stages nothing. When a status changed, the tick publishes one status-only release with the code subject. The key is `status-after-` and the number of the release that it builds on. A [bill status](#bill-status-line) never needs a record.

An approval wakes the stage. A trigger on each of the seven `*_drafts` tables sends `pg_notify` on the channel `civic_lens_publishing`. It fires when a draft is inserted as `Approved`. It fires when `review_status` becomes `Approved`. It also fires when an `Approved` draft gets a new revision number. The payload is a deadline in ticks: the database clock plus 60 seconds. The migration `PublishOnApprovalNotify` holds the 60 seconds as a named constant. The trigger does not read the releases.

The wakeup keeps the earliest deadline it has heard, so a burst of approvals gives one wake and the deadline never slides. The wake clears the deadline. A later approval starts a new window. The wakeup `PostgresPublishingWakeup` adds two more wake times to the approval deadline. They are the next full hour and the end of the gap after the newest release. The newest release is the row of `publication_releases` with the highest `published_at_utc_ticks`. The wakeup is the `PostgresDeadlineWakeup` that the analysis queues use, with an extra deadline query like the brief wakeup.

The gap is 10 minutes. The database clock measures it, against `published_at_utc_ticks`. The commit writes that time from the database clock, so the gap starts at the commit and a long build does not shorten it. A wake inside the gap makes no release, and the wakeup then waits for the end of the gap. At that wake the pass publishes the next 64 ready records. A backlog therefore drains at 64 records for each 10 minutes plus the build time, which is at most 9216 records a day. The 30 kept releases then cover at least 5 hours. The limit of 64 is the size of one publish request. It stays, because the memory and commit time of a larger release are not measured. The worker start wake follows the same gap. The hourly wake is a fallback for a lost notification. It is also the only wake that can make a status-only release.

The command `releases activate` of the latest release sends no wake. A stage that waits after a rollback resumes at its next wake: an approval, the end of the gap, or the next full hour.

A tick that fails or ends on a conflict leaves its records ready. It starts a gap of 10 minutes on the clock of the process. Wakes in that gap do nothing and schedule nothing. The first wake after the gap tries again. That wake is an approval or the next full hour. A restart of the worker clears this gap. The release gap from the stored releases still holds.

The tick stops early in two cases. A `PublicationConflictException` ends it, and the next tick builds again. A replay ends it too. A replay happens after a rollback followed by a CLI publish: the rolled-back records list again, and their key finds the stored release.

A person approval that replaces a published record needs the correction note of its approval. Without it, `PublicationCorrections` raises `MissingCorrectionNoteException` in the build. A record with 20 corrections with a note raises `CorrectionLimitException` for a new note. Both exceptions are tagged like a validation failure, but the tick logs one line at information level and leaves the record out. The other records publish. The record waits. To get out of the missing note state, withdraw the approval, then press Save and approve with no edit and with a note. That approves the same revision again. Under the cap this publishes the record. At the cap, the blocked list shows the record.

A record can fail validation while `PublishedRecordLoader.LoadAsync` builds it, for example when an official has no configured public name. The loader tags the exception with the record. The tick leaves that record out, reports it, and builds the batch again with the others. The next tick tries the record again.

### Rollback

Rollback first checks that the manifest of the earlier release exists. A missing manifest refuses the command with exit code 2 and changes nothing. Rollback then records the release as active and points the link at it. It also requeues the brief of the week of each record that differs between the two releases. The next publication builds on the rolled-back release, so it does not restore the records that were rolled back. A publication built before a rollback fails on commit.

The activate command reads the manifest of the replaced release and the manifest of the release that the link serves after the switch. It reports three lists next to the release summary. `restoredWithdrawals` holds the records that the replaced release withdrew and the activated release holds as records. `withdrawnAgain` holds the records that the replaced release held and the activated release withdraws. `blocked` holds the records of the activated release that review now blocks. The reads are advice and take no lock. If a read fails, the command still returns the summary and logs a warning, because the switch is done. A failure of the served manifest empties all three lists. A failure of the replaced manifest empties the first two lists. A failure of the review read empties `blocked`.

### Release retention

After a publish serves the active release, `PruneReleases` removes old release folders. It is best effort. A failure or a shutdown is logged as a warning and never fails the publish. The next publish tries again.

Step 1 runs under the lock. `PostgresPublicationStore.PruneAsync` takes the seven review locks in the order of `ReviewKeysInOrder`, as `ServeActiveAsync` does. It reads the database clock. It reads the 30 highest release rows. The query groups the rows by UTC day since the start of the day 6 days back. It returns the highest number of each day, so at most 7 rows load. It also finds the folder of the active row. `ReleaseRetention.Plan` turns the rows and the time into a `ReleaseRetentionPlan`. The plan keeps the 30 highest numbers and the highest number of each UTC day in the last 7 days. The callback reads the folder that the `current` link serves. `FileReleaseDirectory.RetireAsync` then lists the folders in `releases/` from the disk. It moves each folder that the plan retires into `deleting/`, except the active folder and the served folder. The plan retires a number only when it is at or below the highest committed number and not kept. Each move is one rename, so a half-deleted folder never holds a `release.json` under a release name. A folder with no database row is retired too, when its number is at or below the highest committed number. A folder above that number may belong to a release in progress, so it stays. The step runs without the shutdown token, because a rename is fast. A release in progress with a number below the highest committed number can no longer commit, so retiring its folder is safe.

Step 2 runs after the lock ends. `DeleteRetiredAsync` deletes every folder in `deleting/`, including folders that a crash left. It may stop on shutdown, and the next prune finishes the work. A discard of a failed publish deletes its own folder the same way. Hard links make each newer release keep its own copy of every carried file.

The database rows stay. After a prune, `releases activate` for a pruned release is refused with "has no files on this machine". The release list still shows it.

### Blocked published records

`ListBlockedPublished` serves the owner list of published records that review blocks. It reads the active manifest and gives the entries to `BlockedPublishedRecords`. That class reads the current review state of each entry with `IPublicationStore.ReadReviewStatusesAsync`. It lists the entries that `PublishedRecordRules.IsWithdrawable` accepts with the reason `ReviewBlocksIt`. A published record whose newer revision a person rejected is one of them. The rejection does not remove the live text, so the owner takes the record off with Take off site. The store method uses the same read as the commit check for a withdrawal, so the list and the commit agree. The store also names the actor of the latest approval, but only for an approved revision that the release does not hold. It reads one decision row for each such record. For each of those records that a person approved, the class reads the correction list from the record file of the active release. It lists the record with the reason `CorrectionLimit` when the list holds 20 notes. It also checks each withdrawn notice of the manifest, with the withdrawn revision as the published revision. It lists the notice with the reason `WithdrawnAtCorrectionLimit` when a person approved a higher revision and the notice holds 20 notes. The notice already holds its correction list, so this check reads no file. The notice holds no headline, so the row reads "Withdrawn record" and the record ID. `BlockedPublishedRecord.StuckText` gives the text of each reason. Each row holds the kind, the record ID, the headline, the published revision, the review status, and the reason. The list is empty when no release is active.

The CLI command `releases blocked` shows the list. The CLI JSON holds the reason of each row. The Review home page shows only the stuck rows, in the Needs a person queue. A stuck row has the badge "Cannot publish" and the reason text. A withdrawal does not free it. A row with the reason `ReviewBlocksIt` is in the queue by its review status, except a rejected record. A rejected record leaves the queue. A published record whose newer revision is rejected shows as a "Cannot publish" row. Its text says the live text stays until the owner takes it off. The owner withdraws it with Take off site on the record editor, or with the CLI command `releases publish <key> --withdraw <kind>:<id> "note"`; see [review](review.md#take-off-site). The home page reads one record file for each person-approved candidate on each owner page load. The home page reads the active manifest a second time for the stuck rows. The stuck rows are for the owner only. The Review home page also lists recent releases, read-only. It has no publish control, because the stage `publishing` publishes every approval.

### Corrections and withdrawal

Publication prepares typed correction copies before it takes the final review locks. New records reuse their already validated correction arrays. Carried records reuse the preceding release's verified bindings. A missing legacy binding is recovered from the complete validated private record file, with exact kind, ID, and revision checks. Vote text comparisons also validate the exact preceding vote file. Public requests do not use this fallback.

The store clones input arrays at preparation. It hashes the exact ordered fields with a versioned, length-prefixed UTF-8 encoding. UTC ticks and the original offset both participate. Equal histories share a body only after full readback verification. Preparation writes a header and its children atomically. An existing incomplete or conflicting body fails without repair. The final commit inserts every binding after the published entry rows exist, within the same release transaction.

The owner can bootstrap earlier retained releases with `releases corrections backfill <limit> [cursor]`. The candidate query pages missing bindings by release, kind, and record ID. It includes retention-policy releases, the active database release, and the served directory. It excludes retired releases. Each record file must validate and agree with its exact typed revision facts. A verified empty history gets a binding too. Preparation reuses the same content-addressed copies as normal publication. The final transaction checks that each target release remains retained and each record still has the prepared revision. A changed or conflicting binding fails without replacement.

The separate owner command `releases corrections verify <limit> [cursor]` checks all selected record histories, including existing bindings. It compares each immutable file with the exact stored revision, entry facts, and ordered history. Time ticks and original offsets remain exact. Missing or malformed histories fail; the command never repairs them. Normal reads batch histories by release. A failed batch retries individual histories only to isolate corrupt peers. Each store page has one read-only repeatable-read snapshot of one release, closed before file reads. The walk goes through the selected releases in release order. The cursor binds to one release by number and directory name, and carries the record position and the failures already found in that release. A page reports the release it covered and whether that release finished. Suppose the cursor release is no longer selected, or its directory differs. The result then reports it in `skippedReleases`. The walk continues with the next selected release. The result lists the releases fully verified in the call and the current selection, read after the last file read. The command writes nothing. This verifies history agreement for stored membership; run `releases entries verify` separately to prove membership against release manifests.

A correction replaces a record. A withdrawal removes it. Withdrawing approval in review does not change published artifacts. Only a publish with a withdrawal does. The CLI option `--withdraw` and Take off site on the record editor both run that publish.

Each of the seven record files holds a `corrections` list of `PublishedCorrection`. An entry holds the replaced revision number, the publication time, an optional note, and an optional `factsUnchanged` flag. A note means a person correction. No note means that code updated the record from the source. The flag is absent unless true, so older files read as before. It marks a vote update where only the headline or the summary changed. The page then reads "Summary rewritten by the AI model". It ends with "The vote facts did not change." Code compares the two vote files. It never trusts a stored reason. The list runs newest first. It holds at most 20 entries with a note. A code update replaces the code entry of its kind in the newest run, so a run holds at most two entries. A record that no release replaced has an empty list.

`PublicationCorrections` owns the list and the note rule. A publish that replaces a record of the active release reads the earlier list from the record file of that release. It puts the new entry first. A person must give a note for each replacement. The editor writes the note at approve time, and `ReviewDecision.CorrectionNote` keeps it in the approval decision. `PublishedRecordRules.CorrectionNoteOf` reads the note of the latest approval of the published revision. The code subject gives no note. A note on a first publication is dropped. The note rules are in `CorrectionNoteText`, which the approval and the withdrawal note share.


A withdrawal needs the owner and a note. `PublishReleaseRequest.Withdrawals` carries the notes, and the idempotency hash covers them. A request can have withdrawals and no records. The record must be in the active release. At commit, review must have blocked the record.

`PublicationWithdrawals` builds one `PublishedWithdrawal` for each withdrawn record. It holds the kind, the record ID, the withdrawn revision, both times, the note, and the correction list of the record. The manifest keeps the entry in `withdrawals`. The release holds no `records/{id}.json` for the record. `PublicApi` serves a notice for the record.

`WithdrawalCascade` runs after the publish loads its additions. It refuses the withdrawal while a relationship or a brief that stays in the release cites a withdrawn record. It finds relationships with `IRelationshipReviewStore.FindCitingAsync` over the carried relationship IDs. It reads each carried brief file for its citations. The error lists the citing records. A record that the same request adds meets the same rule earlier. `PublicationBuild.WithRemoved` takes the withdrawn records out of the release records that the loaders check. Take off site calls the read-only `WithdrawalCascade.FindCitersAsync` before it writes a decision, so a predictable refusal writes nothing. The commit-time check stays.

A withdrawn or returned action changes the bill link of the votes on its bill. The bill action map of the publish holds the new links. A withdrawn vote leaves the vote files of its members. It reads only the Congress of the vote file, and the members come from the database as for a replaced vote. A Congress with no row left disappears. A withdrawn record counts as a change for each official it named, so the publish rewrites their files. A withdrawal requeues the brief of the week of the record; see [briefs](briefs.md#staleness).

The worker returns a withdrawn record once a person has approved a higher revision with a correction note. The owner can also return it with `releases publish <key> <kind>:<id>`. Every returned record has a person approval and a note. `PublicationCorrections` continues the corrections from the withdrawal and adds one entry for the withdrawn revision. The publish drops the returned ID from `withdrawals`, so the manifest lists the record again. A code approval keeps the record withdrawn on every path. A revision that is not higher keeps it withdrawn too. `WithdrawnRecordException` tags the record, so the stage `publishing` logs one line and leaves the record out. A person approval without a note raises `MissingCorrectionNoteException`, and the stage skips it the same way.

A relationship or a brief that cited the record stays withdrawn. A person publishes it again, in the same request or later. The official files, the search rows, and the brief requeue follow the added record, as for any other addition.

### Vote record

`PublishedVote` is the contract of a vote record. `PublishedVoteBuilder` builds it from an approved `VoteDraftRevision`, the review decisions, and the cited extractions. It maps each member official through `PublishedRecordRules.MapOfficial` and copies each citation through `PublishedRecordRules.Cite`. The vote kind enum mirrors the Core `VoteKind`. The source enum `PublishedVoteSource` mirrors the Core `VoteSource` the same way: `CongressGov` or `Voteview`. `PublishedVoteSources` maps it, and `PublishedVote.source` is required. `PublishVoteTests` tests the builder through `PublishRelease`, as for the other kinds.

The builder reads the result from the saved result line. `VoteTally` reads the totals from the saved total lines. It reads the member lines of the first cited member extraction, which holds every member of the roll call. It groups the casts by the party that `VoteParties` gives for the vote day. `PublishRelease` reads the latest member snapshot once for each publish. `PublicationBuild` carries it to `VoteRecordLoader`, and `ReleaseDataFiles` passes it to `PublicationOfficials.ResolveAsync`. The source party letter of a member line serves the House cross-check and the party of a member who left the roster. The Senate has no party total lines, so its cross-check uses the count line. The search service lists votes. `VoteRecordLoader` owns the vote kind for publish and the ready list. `PostgresVoteReviewStore.GetForPublicationAsync` reads the selected drafts, their review cycles, and the cited extractions. It also reads the IDs of the action records with the same congress, bill type, and bill number. Several bill sources can draft one bill, so there can be more than one ID. The loader keeps the first ID whose action record is in the release. The release holds an action record when the base release has it or the same publish adds it. Loaders run in list order and action comes before vote, so a same-release action counts. A vote with no such action shows its bill as text.

`VoteTally` also groups all captured casts into `PublishedVote.PartyTallies`, including members outside the tracked set. The same grouped counts supply the existing party majorities. A candidate vote retains null chamber totals and no party majorities. It gets party tallies only when the exact cited candidate-header count map matches every captured cast. The shared `PublishedVote.CandidateCountsOf` parser bounds that map and rejects duplicate or ambiguous labels. Candidate choices count as Other; Present and Not Voting keep their own buckets. Incomplete or ambiguous candidate evidence keeps tallies null and preserves publication of the earlier contract. Typed per-revision tally storage writes these groups through the existing stored-column writer; see [votes](votes.md#storage-and-contracts). Legacy conversion uses the existing stored-column backfill. The vote-detail API serves these typed groups. The owner command `releases tallies verify` compares the stored rows with the party tallies of the kept vote file of each revision, as [votes](votes.md#invariants) and [operations](../operations.md#vote-party-tally-verification) describe. Production conversion and verification remain rollout gates.

The vote page shows the approved Yes and No meaning only when the cited question and result are internally consistent. It uses general wording for an unsupported complete question. It always shows the next-step heading and either one exact known outcome or the shared unknown sentence, including when cited wording inputs are unavailable. `PlainVoteWords.ResultWord` is the only result mapper. The wording uses the saved vote question and facts, never current bill status or a later historical event. Cited confirmation or rejection supports nomination wording without guessing an office or appointment date. Cited legislation supports bill, resolution, conference-report and override routes. Uncited Voteview bill metadata cannot select those routes. A title that may propose a constitutional amendment blocks override law wording; that refusal does not enable constitutional-purpose detail. Constitutional amendment, partial report and second-degree amendment details stay unknown until their captured inputs support a complete recognized shape.

### Relationship record

`PublishedRelationship` is the contract of a relationship record. `PublishedRelationshipBuilder` builds it from an approved `RelationshipRevision`, the cited statement revision with its article text, and the cited target. `RelationshipRecordLoader` owns the kind for publish and the ready list, as `BriefRecordLoader` does for briefs. `PostgresRelationshipReviewStore.GetForPublicationAsync` reads the selected drafts and their cited revisions in one repeatable-read transaction. It flags each relationship whose cited revisions are not current in the release that the loader passes. The ready-list read uses the active release.

The review flag "cited records changed" keeps the approved-revision rule of [statements](statements.md#relationship-review). Publication uses the release rule above, as briefs do. The two flags can differ, because a cited record can be approved at a newer revision that the release does not hold yet.

A relationship page names the cited revision number of each side. It links to the current page of each cited record, which can show a newer revision. The page shows the reason, the quote of the statement, and the fact of the target. Its caveat says that the link states no verdict.


### Bill history snapshots

Each release binds the newest verified, completed Actions chain for each bill, independently of its newest status. A newer unfinished chain keeps the prior verified history. `PostgresPublicationStore.ReadBillInputsAsync` selects both inputs in one statement. A chain starts at zero, has no missing pages, and closes exactly once on its last page. Every page has a nonnull verified import count. Its observation time is the latest capture observation across those pages, through their exact extractions. Gate updates and job settlement times do not date the history.

Publication prepares missing immutable copies before taking final review locks. `PublishedBillHistories` streams the actions inside Postgres and checks that the copied count matches the verified import count. It loads no action object graph. A capture is copied once per representation version; later releases reuse that copy without reading its body. A concurrent insert can cause a publication conflict, which the existing publication retry path handles. The final commit checks the bill identity and exact representation version, then inserts its release binding. A capture completed after selection belongs to the next release. Existing copies and release bindings stay unchanged.

The copy key is the detail job and `ProjectionVersion`. Existing copies have version 0. New verified copies and bindings use `BillHistoryCapture.CurrentProjectionVersion`, currently 1. A representation change triggers publication even when its capture identity stays the same. Unverified legacy history is absent from new bindings until recovery verifies it; the bill can still publish. Before checking for a nonzero representation, downgrade locks the history actions, release bindings, and history parents in that order. It refuses downgrade once a nonzero representation exists. Test: `PostgresBillStreamTests.DowngradeCannotEraseAProjectionCommittedWhileItIsStarting`.

The number of a public law comes only from a whole official action matching `BillStatusMeaning.PublicLawNumberOf`. Missing evidence stays null. History is served through the API, with no history file. Completed empty history has an observation time and count zero; absent history has neither.

Invariant: a release reads its immutable completed capture, never growing operational action rows. Enforcers: `BillHistoryCaptures`, `PublishedBillHistories`, and `ReleaseBillHistories`. Tests: `PostgresBillStreamTests.PreparingHistoryCopiesTypedActionsOnceAndReusesTheImmutableCopy`, `PublishBillHistoryTests.AHistoryCompletedAfterSelectionWaitsForTheNextRelease`, and `ActionHistoryEndpointsTests.PagesKeepTheSnapshotMetadataOrderAndNullableOfficialFieldsAndRejectAChangedRelease`.

Invariant: history repair creates a new representation without changing legacy copies or bindings. Enforcers: the composite history keys, `ReleaseBillHistories`, and `BillPublicationInput.HasHistoryChange`. Tests: `PostgresBillStreamTests.VerifiedCopiesAndReleaseBindingsDoNotOverwriteLegacyEmptyHistoryOfTheSameCapture` and `PublishBillHistoryTests.AVerifiedRepresentationOfTheSameCapturePublishesOnceWithoutChangingItsObservationTime`.

### Bill status line

An action page of `PublicApi` shows where the bill stands on Congress.gov. The status is not part of the record. A [bill gate](bills.md) stores the `latestAction` of each bill version that Civic Lens fetched. Each publish reads the status of every action record of the release in one snapshot query, `IPublicationStore.ReadBillInputsAsync`. The query joins the record to its bill and takes the newest version. It takes the read time from the creation time of the gate row. `ReleaseBillStatuses` writes the rows to `bill-status.json`, sorted by record ID. The commit of the release writes the same rows to the table `release_bill_statuses`, with the release number. The table has the columns `release_number`, `record_id`, `latest_action_text`, `latest_action_date`, `read_at_utc_ticks`, and `status`. The column `status` holds the stage name that `BillStatusMeaning.StageOf` gives. It is null until a writer fills it. The stage is not in `bill-status.json`. The key is the release number and the record ID. The API view `bill_status` reads this table and not the gate, so the API shows the status that the active release pinned.

The publish compares the row of each action record with the row of the previous release. A status changed when its text or date differs, when the previous release has no row, or when the row is gone. The record file stays the same hard link. The store also returns the bill type of each action, as `ActionBillStatus`, because the meaning of "Received in the Senate" depends on it. The published row holds no bill type. The status refreshes in the database on the normal bill update path. It reaches the site in the next publish. The worker publishes a status-only release when no record is ready; see [automatic publication](#automatic-publication).

The action page shows three facts: "Latest action on Congress.gov", "Status read on", and "Official bill page". The first fact holds the plain meaning from `BillStatusMeaning` and the action date. The rules are in the table below. The read time is the time of the first read of that text and date. A later read of the same action keeps it, so the page and `bill-status.json` show one time. The `latestAction` of the bill detail has no action code, so the meaning comes from the text.

| Text has this whole shape | Meaning |
|---|---|
| "Referred to the Subcommittee on X" | "In committee: sent to the Subcommittee on X." |
| "Referred to the Committee on X", "Referred to the House Committee on X", "Referred to the Senate Committee on X", or "Read twice and referred to the Committee on X" | "In committee: sent to the Committee on X." The chamber shows only when the text states it. |
| "Received in the Senate", alone, or followed by " and [Read twice and ]referred to the ...", or by ". Read twice. Placed on ...", for a House bill type | "Passed the House. Now in the Senate." |
| "Received in the House", with the same shapes, for a Senate bill type | "Passed the Senate. Now in the House." |
| "Placed on Senate Legislative Calendar" | "Waiting for a possible Senate floor vote." |
| "Placed on the Union Calendar" or "Placed on the House Calendar" | "Waiting for a possible House floor vote." |
| "Ordered to be Reported", with only an optional "in the Nature of a Substitute", an optional "(Amended)", and an optional "by Voice Vote", "by Unanimous Consent", or "by the Yeas and Nays: N - N" | "A committee voted to send this bill to the full chamber." It reads "this measure" for a resolution type: hres, sres, hconres, sconres, hjres, and sjres. |
| "Became Public Law No: 119-21." | "Became law: Public Law 119-21." |
| Any other text, such as "Motion to reconsider laid on the table." | "Latest official action: " and the raw text |

The rules run in the order of the table. A rule matches the whole text from its start. Any other ending, such as "Unfavorably", "Adversely", or "read the third time, and passed", shows the raw text. `PublicLawNumberOf` shares the public-law matcher with the meaning rule. It accepts ASCII digits and an optional final period, and rejects trailing text or a newline. Other action text returns no law number.

The committee name stops at the first ". " or " (". A committee rule accepts only these tails. One is the final period. One is a citation in the form ". (text: ...)", ". (consideration: ...)", or ". (Sponsor introductory remarks on measure: ...)". The last is the House form with a second committee, and its fixed Speaker clause, shown below.

```text
Referred to the Committee on X, and in addition to the Committee on Y, for a period to be subsequently determined by the Speaker, in each case for consideration of such provisions as fall within the jurisdiction of the committee concerned.
```

That form reads "In committee: sent to the Committee on X, and in addition to the Committee on Y." The citation never shows. A name with " (", such as "Intelligence (Permanent Select)", shows the raw text. A raw text with no final period gets one, so the action date stays its own sentence. In 16,808 dev bill details, the rules cover 91.0% (15,289).

### Issue tags

Each action and each vote chooses its issues separately. One bill can show different issues on its action and its vote, or on two roll calls. The sponsored and voted counts can then disagree for that bill.




### Public API views

Model document-change text uses `PublishedWording.ModelDocumentChange`: "Drafted by an AI model from these source versions. A person checked it before publication." Person text has no AI label.

Document changes expose six views bound to the active published revision: the parent, officials, source versions, changed regions, word edits, and citations. Source URLs are final capture URLs. Observed times and full text come from the exact comparison extractions. A date-evidence flag identifies an existing citation. It never replaces that citation. Region and word-edit completion counts distinguish missing projections from empty lists. Public role access remains limited to views. `DocumentChangeViewsTests` protects revision binding, activation, rollback, ordering, and final URLs.

`PublicApi` reads published data through the restricted `public_api` views. They cover votes, bills, statements, briefs, issues, related records, withdrawals, executive actions, officials, ZIP districts, and release names. Official figures include `official_party_lines` alongside attendance. See [search](search.md#api) for the routes and [the column reference](public-api-columns.txt) for the view columns.

The statement detail views add the source and quotation evidence for an eligible active statement revision. `statement_sources` has one row per statement with the extraction ID, the collection attempt's requested URL and observation time, and the extracted text. `statement_quotations` has one ordered row per quotation with its extraction ID, offsets, length, and kind. Both views join through `public_api.statements`, retaining its active revision and publication eligibility checks. `PublicApiGrants` gives the public role only these view grants and the view owner only the base columns they need. The views do not add source text to statement list rows. `GET /v1/statements/{recordId}` returns the complete bounded source once and derives quotation text in C# using UTF-16 offsets. It calls the same `PublishedStatement.ValidateContent` rule as release validation.

- The view `public_api.active_release` reads only `release_number` and `published_at_utc_ticks` from the active row of `publication_releases`. `/v1/release` and list readers use it to retain release identity even when the release holds no records. `PublicApiActiveReleaseIdentity` owns the view, and the shared `PublicApiGrants` step grants the public role SELECT access. The view is security-barrier protected and exposes no other release columns. The view `public_api.active_records` joins the active row of `publication_releases` with `publication_record_states`. A record belongs to release N when `first_release <= N` and `last_release` is null or at least N. It shows kind, record ID, revision number, release number, and publication time. Readers use it for record membership and record data. `withdrawals` and `withdrawal_corrections` join the active row of `publication_releases` directly, because an all-withdrawn release has no `active_records` row. The six name views join the active row of `publication_releases` directly, and `zip_districts` joins neither. For an empty active release, `active_records` has no row but the name views can still show its names. No function and no stored copy exist.
- The view `public_api.votes` has one row for each active vote. It shows the roll call, the bill, the headline, the summary, `text_origin`, `label`, the four counts, `question`, and `result`. The counts come from the member rows by cast. `Yea` and `Aye` count as yea. `Nay` and `No` count as nay. A vote revision with no member list appears in no vote view. `public_api.vote_party_tallies` exposes the nullable completeness marker and typed five-cast buckets for only the exact active revision. The vote detail API validates the group count and each group through `PublishedPartyTally`; an incomplete or malformed positive marker fails the request.
- Vote detail returns `PublishedVoteFact` objects with text and citations, the complete bounded source set, and date and kind citations. The paged member response adds each cast citation. Each route uses one SQL statement, so its release and evidence share one snapshot. The API derives quote text from stored UTF-16 offsets and calls the same `PublishedVote.ValidateEvidence` or `ValidateMemberEvidence` rules as the release contract. Missing source metadata, invalid ranges, mismatched facts or casts, and excess sources, facts, or members fail the request. Enforcers: `VoteStore` and `PublishedVote`. Tests: `VoteEndpointsTests`, `VoteMembersEndpointsTests`, and `PublicApiVoteEvidenceMigrationTests`.
- The columns `question` and `result` read the same columns of `vote_revisions`. `question` is null when the source gives no question. `result` is never null. `VoteFacts` owns the rule that takes both from the facts, and `VoteRevisionRows` writes them once. The migration `VoteQuestionResultColumns` filled existing rows from the fact rows and replaced the view. The SQL of the view holds no prefix.
- The column `label` holds the public wording of each origin. A model text gets "An AI summary of the official record". A code text gets "Written automatically from Congress.gov data, with no AI". A person text has no label, as on the pages. `PublishedRecordLabels` owns the wording.
- The view `public_api.vote_members` shows position, official ID, cast, party, caucus, the cast citation's extraction ID and UTF-16 offsets, and the state and district. One `LATERAL` join picks the term for the caucus, the state, and the district, so the three always come from the same term. The district is 0 for an at-large state and null for a senator. All three are null when no term matches. The official ID is our configured official ID, the same ID as `PublishedOfficial.Id`. No view shows a bioguide ID. The view `public_api.vote_issues` shows the issue ID of tracked issues only.

The API omits zero-count kinds and hides agreement if any active vote has unknown Congress. Enforced by `PublicApiPartyAgreement` and `PartyAgreementStore`. Tests: `PartyAgreementEndpointsTests` and `PublicApiPartyAgreementMigrationTests`.
- The view `public_api.member_votes` has one row for each cast of an active vote. It shows the official ID, `vote_cast`, and the vote columns that the member votes route needs. Those are `record_id`, the roll call, the bill, `kind`, `headline`, `label`, `text_origin`, and `result`. The column `issue_ids` lists the tracked issue IDs of the active revision. The issue filter of the member votes route reads it, for the issue page of a reader. It holds the same IDs as `vote_issues` and no untracked issue. It joins the base tables itself, with the same active-release filter as `votes`. So a query for one official can use the person index. It has no member count and no bioguide ID. `label` repeats the wording of `votes`.

- The view `public_api.bills` has one row for each active bill record. It shows the bill identity (`congress`, `bill_type`, `bill_number`), the title, the headline, and the summary. It also shows `text_origin`, `label`, the policy area name and ID, `event_date`, `sponsor_count`, `cosponsor_count`, and `bill_line`. The line comes from the entry row of the active revision. It is null when that row holds no line or does not exist yet. A bill whose revision cites bill text adds `why_it_matters`, `text_version_name`, `text_version_date`, `text_chars_read`, and `text_chars_total`. The `text_*` columns come from the `bill_text_versions` row that the revision cites, and count characters of that one version. `why_it_matters` is null unless `text_origin` is Model, because model text shows only with its origin and label. It serves rows only when `text_origin` is Model and the revision cites bill text, so a person edit hides the terms. The `definition` is the plain-quote form of an exact quote of the definitions section of the bill text, never AI wording. `cut` is true when the quote ends before the end of its definition paragraph. The rollback of `PublicApiBillTextQuotes` rebuilds the old key term view and gives the role its SELECT grant again. - A published action may hold `billText`. It is null for an action that cites the CRS summary or no summary. It holds the version name and date, and the characters read and the total. The field is optional, so the schema version stays 1. `billText` may also hold `keyTerms`, from 1 to 5 objects with a `term` and a `citation` of the exact definition quote. - The columns `event_date` and `cosponsor_count` read `action_revisions.event_on` and `action_revisions.cosponsor_count`. `ActionRevisionRows` writes both once, from `ActionDraftRevision.EventOn` and `ActionDraftRevision.CosponsorCount`. - The view `public_api.bill_status` has one row for each active bill whose active release pinned a status. It shows `latest_action_text`, `latest_action_date`, `read_at_utc_ticks`, and `status`. The bill detail page uses them as the "Latest action on Congress.gov" and "Status read on" facts. The row comes from `release_bill_statuses`, the rows that the commit of the active release wrote. The view never reads `bill_gates`, so a bill that moved after the publish shows its old status until the next release. The worker publishes a status-only release about every hour when a status changed, so the lag is about 1 hour. The view applies the same filter as `bills`. It holds no plain meaning of the text. `BillStatusMeaning` owns the meaning, and no SQL copy of it exists.
- The view `public_api.record_links` has two rows for each active relationship. One row is for the page of the statement, and its related record is the target. The other row is for the page of the target, and its related record is the statement. A row shows the page record (`record_id`, `kind`) and the related record (`related_kind`, `related_record_id`, `related_headline`, `related_text_origin`, `related_label`). It also shows `link_type`, `statement_date`, and `link_record_id`. The last one is the relationship record that explains the link. The link values come from the entry row of the relationship. The headline, its origin, and its label come from the view `public_api.record_headlines`. That view reads the active revision of the statement, action, or vote, so the headline is the current headline of the related record. It is not the headline that the relationship cites. A statement has no origin column: the author kind `Analysis` gives `Model`, and any other author kind gives `Person`. The label of a statement is null unless code approved a model text. The label is null for person text. A record with no headline gives no row. Each branch of `record_links` starts from the link table, and it names the page record by a column of that table. So the filter on the record ID uses the indexes of the link table. The headline is a lateral lookup with `OFFSET 0`, which stops the planner from scanning every headline of the release. A local plan with 3,000 links reads the link index and then one revision row for each link. A row shows only when the relationship, the statement, and the target are all active. `PublishedRelationship.Other` names the other end, and the view gives the same end. The route orders by `statement_date`, undated last, then `link_record_id`.
- The view `public_api.vote_facts` shows ordered fact text and each fact's extraction ID and UTF-16 offsets for the exact active vote revision. The facts are the question, the result, the count lines, and the party total lines that the vote page lists. `vote_evidence` supplies the source kind and date and kind citations. `vote_sources` unions all date, kind, fact, and member citation sources. It reads their exact extraction text, final capture URL, and observation time, preserving missing metadata for the reader to reject. Its `position` column numbers each source by its first citation, as `PublishedRecordRules.Sources` orders the sources of the record file.
- The search ingest will read typed views instead of `release.json` and the record files. The migration `PublicApiSearchSources` adds `action_sources` and `executive_action_sources`. - `PublicApiGrants` owns every role and privilege statement. It creates the role `civic_lens_public` without LOGIN and without a password, and it sets the role limits. It grants CONNECT, USAGE on the schema, SELECT on the views, and the column grants of the view owner. It revokes `TEMPORARY` and the advisory lock functions from `PUBLIC`. `db migrate` runs it after the migrations, every time, and every statement is idempotent. A restore with `--no-privileges`, a rollback, or a new migration cannot leave the grants behind, because the next `db migrate` sets them again. The step holds no secret, and a role belongs to the cluster, so the operator enables the login. See [public role login](../operations.md#public-role-login).
- The migration creates only the owner role, because the views need it when they are created. `readonly-grants.sql` does not revoke `TEMPORARY`. `PublicApiGrants` owns that revoke for the whole database, so run `db migrate` before the installer.
- Tradeoff: the views live in the operational database. An outage of that database stops live read routes, while cached pages stay up.

## Storage and contracts

`published_correction_histories` stores the body ID, encoding version, and declared count. A zero-count header represents a verified empty history. `published_correction_history_entries` stores ordered revisions, UTC ticks, offsets, nullable notes, and the facts-unchanged flag. `release_correction_histories` binds a release and exact published entry revision to its body. These tables are private; the public role receives no table privileges. The verification command result is JSON. It has `examined`, `verified`, `failed`, `failures`, and `nextCursor`. `verifiedReleases` gives release number and directory name. `skippedReleases` adds a reason. `selection` adds the cursor that starts a walk at that release. The cursor is an opaque string. It holds the release number, the directory name, and the last record. It also holds the earlier failure count of that release. No table stores a verification result.

`release_bill_counts` stores each release's total eligible bills and expected nonzero official-row count by Congress. `release_official_bill_counts` stores sparse sponsored and cosponsored counts for named officials, with foreign keys to the release's Congress total and official row. New publications insert both tables in the final commit transaction. The schema migration creates them empty. The owner command `releases counts backfill <limit> [release-number]` converts the active, served, and retained rollback releases, one release per write transaction. Before the write, `ReleaseBillCountFiles` reads the manifest, the officials file, and each action and vote record file with the bounded readers. It validates each file with its contract. It requires the manifest and the state table to list the same action and vote revisions in both directions. It requires each file to agree with the stored projection. The projection holds the Congress, the event date, the sponsor IDs, and the cosponsor IDs. A cosponsor counts when its role is Cosponsor and it has no withdrawal date. No sponsor row may name the same official. The file rule `PublishedAction.ToEntry`, the Core rule `ActionDraftRevision.CosponsorIds`, and the SQL rule use this one definition. The officials file must list exactly the stored release officials. The write transaction takes the review locks. Then it checks that the release exists, is retained, has the same directory, and lists the validated revisions. It calls `ReleaseBillCounts.FillAsync` with the Congress of the release day. An exact existing snapshot is a replay. A partial or changed snapshot fails, and a release with no Congress to count fails and rolls back. The owner command `releases counts verify <limit> [cursor]` repeats the file checks. Then it compares the saved rows with the expected counts in both directions. It compares the saved rows in one read-only repeatable-read transaction and never writes. A release with no saved rows fails. Its cursor carries the fingerprint of the selected releases, and a final selection check protects the terminal result. `ReleaseBillCounts` owns the expected-count SQL once. The writer saves it into temporary tables. The verifier reads the same text as common table expressions, because PostgreSQL refuses temporary tables in a read-only transaction. The views `public_api.release_bill_counts` and `public_api.release_official_bill_counts` show the rows of the active release to the public readers.

The bill view appends `crs_summary_text` and `crs_summary_version` from the exact published action revision. The version is null when its body is null. C# stores the body at revision write time, using the pinned summary citation; the full block remains evidence. Enforcers: `ActionRevisionRows.FillCrsSummary` and the `PublicApiCrsSummary` view. Tests: `ActionCrsSummaryTests` and `BillEndpointsTests.CrsSummaryUsesThePublishedRevisionAndExposesOnlyItsBodyAndSummaryVersion`. Downgrade restores the dependent bill-history and vote views and removes the added owner grants. Test: `PublicApiCrsSummaryMigrationTests.DowngradeRemovesCrsColumnsAndOwnerGrantsAndRestoresTheDependentPublicViews`.

The bill view also appends `summary_from_crs`. It is true for model text with no bill text and a stored CRS summary version. The view `public_api.bill_sponsorship_parties` gives the term party of each sponsorship on its sponsorship date. A day that no term holds, a blank party, or two parties on one day give null. The migration `PublicApiBillSponsorPartiesAndTimes` owns both. Its downgrade restores the dependent views `bill_actions`, `votes`, and `action_sources`. Test: `PublicApiBillSponsorPartiesAndTimesMigrationTests.DowngradeRestoresTheBillViewsAndUpgradeGivesThePublicRoleThePartyAndTheCrsFlag`. The bill page reads its checked time from `approved_at_utc_ticks` in `public_api.record_entries` and its first time from `public_api.record_first_publications`. Test: `BillPageTests.TheSourceFoldShowsTheStoredApprovalTimeAndTheFirstPublicationTime`.

The migration `PublicApiStatementSpeakerTerms` adds `public_api.statement_speaker_terms`. It gives the term party and the seat of each statement speaker on the statement date. Its `TermPartyOn` fragment is the one SQL source of the term party rule. The issue line-up of the release commit reads it too. The migration rebuilds `bill_sponsorship_parties` from it with the same columns and rows. The seat comes from the one term that holds the day. Test: `PublicApiStatementSpeakerTermsMigrationTests.DowngradeKeepsTheBillPartiesAndUpgradeGivesThePublicRoleTheSpeakerPartyAndSeatOfTheStatementDate`.

`published_bill_histories` holds a completed capture identity, representation version, bill identity, observation time, action count, and optional public-law number. Its key is `(detail_job_id, projection_version)`. `published_bill_history_actions` adds position to that key. `release_bill_histories` binds a release and bill record to the exact copy and version. These tables are publication-owned. Operational IDs and representation versions stay internal. `public_api.bills` appends the public-law number and history metadata; `public_api.bill_actions` exposes only actions of the active published bills.

The public views expose stored vote alignment, member party, normalized member-vote side, party-majority cast, and official photo paths. Member caucus, state, and district come from the matching chamber term in the active release on the vote date. Missing values remain null. The [API reference](search.md#api) lists the response fields.

Statement and relationship entries pin `approved_by` as `Code` or `Person`, never a reviewer identity. The commit writes it from the published record. Existing entries get it through `releases entries backfill`, from the kept record file, never from live review decisions. A pinned value cannot be overwritten. A publication cannot fill an existing null classifier from a new review decision. Statement headlines remain hidden until their classifier is known. A relationship with no classifier shows no link label. An unresolved open classifier makes the backfill command fail. Older manifests may omit the field; their published statement and relationship files supply it during backfill. A relationship file without `approvedBy` reads as `person`. The view owner has no grant on `statement_review_decisions`.

Every entry pins `approved_at_utc_ticks`, the approval time of the published revision. It is null until filled. The manifest entry holds it as `approvedAtUtc`. Each builder takes it from the review decisions through `PublishedRecordRules.GetApprovalTime`. The commit writes it from the entry, the same way it writes `approved_by`. A public page reads the stored column through `public_api.record_entries`, and it never copies the C# rule in SQL. The view `public_api.briefs` reads the same column from `published_entries` for the active brief revision, so the brief page shows the published time. The migration `PublicApiBriefCoverage` owns that view column. Its rollback sets that column to null, so the rollback of `PublishedEntryApprovalTime` can then drop the base column. Test: `PublicApiViewsTests.ABriefShowsItsCoverageItsCutoffItsPublishedApprovalTimeAndNotALaterApprovalAndItsFirstPublicationTime`. Existing rows get it through `releases entries backfill`, from the kept record file. A stored time cannot be overwritten. A publish whose entry holds another time conflicts. An older manifest may omit the field, and its record file supplies it. `releases entries verify` rebuilds the time from the table and compares the bytes with the manifest, so a differing time fails the release. The migration `PublishedEntryApprovalTime` adds the column and a check that holds a valid tick count. The view `public_api.record_entries` shows the time as its last column. A rollback of the migration drops the column and restores the older view with its grant.

- The generated schema docs do not list views. [public-api-columns.txt](public-api-columns.txt) lists every column of every `public_api` view.
- The state table lists the records of each release as kind, record ID, and revision. It does not list withdrawn records.
- The table `published_records` holds one row for each record that was ever published: `kind`, `record_id`, and `first_published_at_utc_ticks`. The key is `kind` and `record_id`. `kind` uses the same spelling as `publication_record_states`. Code inserts rows and never changes them. A rollback keeps them. The migration `PublishedRecords` creates the table empty. `releases first-published backfill` fills it from the active manifest; see [operations](../operations.md#first-publication-backfill).
- Six tables hold the names of each release: `release_officials`, `release_official_terms`, `release_issues`, `release_issue_includes`, `release_issue_excludes`, and `release_policy_areas`. Each key starts with `release_number`, which has a foreign key to `publication_releases`. An official row holds the ID, the name, the Wikidata ID, and the website. A term row holds the office, kind, state, district, party, caucus, and the start and end dates. An issue row holds its name, definition, nullable `count_congress`, nullable `substantive_votes`, and nullable `bills`. The count columns are either all null for an unsupported calendar date, or hold a positive Congress and nonnegative counts. The migration `ReleaseNames` creates the name tables and views; `ReleaseHomeIssueCounts` adds and backfills the immutable counts. Publish writes names and counts in the release commit transaction. A release that an older image published has no name rows, and its views stay empty. Two more tables hold the party line-up of the bills of each issue. `release_issue_party_lineups` has one header row for each issue of a release that has counts. Its key is `release_number` and `issue_id`, with a foreign key to `release_issues`. It holds `unknown_bills`. These are the bills with no sponsor party. `release_issue_party_counts` holds one row for each party with at least one bill. Its key is the release, the issue, and the `party` label. It has a foreign key to the header. A check keeps `bills` above 0. The Congress is `release_issues.count_congress`, and the base is `release_issues.bills`, so no second copy exists. The header table makes a release with a zero count different from a release with no snapshot. The migration `ReleaseIssuePartyLineups` creates both tables and the view. Older retained releases have no rows. The official row also holds the nullable `photo_path`. It is the path of the portrait in the release, and the official files of the release hold the same value.
- The table `published_entries` holds one row for each record revision that a release added. The key is `kind`, `record_id`, and `revision_number`. The row holds the scalar facts of the revision: headline, source host, event date, bill title, document type, and the link columns. It also holds seven pairs of nullable columns, one pair for each revision table. The pair of the entry kind is set, equals the key, and has a foreign key to the revision table. The entry has no first publication time, because `published_records` owns it. The link columns `statement_record_id`, `target_kind`, and `target_record_id` have foreign keys to `published_records`. The column `statement_kind` is generated. The matched official of a relationship entry is the row of `published_entry_officials` with `is_matched` set. The arrays are in `published_entry_officials` (ID only), `published_entry_issues`, and `published_entry_policy_areas`. Each has the entry key and `position`. The tables hold no official name, no vote count, no chamber, and no cosponsor. The nullable column `congress` holds the Congress of the record day. The alignment and the party figures of a vote live in the vote tables, not in the entry tables; see [votes](votes.md#storage-and-contracts). No view reads these stored columns yet. The migration `PublishedEntries` creates the tables empty. Nothing reads them yet. `releases entries backfill` fills the rows of record revisions from earlier releases. A revision that no kept folder lists gets no row.
- The table `publication_record_states` holds one row for each range of releases in which a record has one revision: `kind`, `record_id`, `revision_number`, `first_release`, and `last_release`. A null `last_release` means the range is open, so the record is still in the highest release. A withdrawn record has no open range, and the manifest holds the withdrawal details. `kind` uses the wire spelling of the manifest, which `PublishedEnumJsonConverter` owns. `PublishedRecordReference.NameOf` must match it. A record that leaves and returns has two rows. The state at release R is the rows with `first_release <= R` and a null `last_release` or `last_release >= R`. A commit reads the open rows, which are the highest release, and writes only the records that entered, left, or changed revision. Activate and prune write nothing to the table. Review queries and the brief queries read this table. The migration `DropPublicationRecordsJson` removed the column `records_json`.
- The table `publication_withdrawals` holds one row for each range of releases that list one withdrawal of a record. The columns are `kind`, `record_id`, `withdrawn_revision_number`, `withdrawn_at_utc_ticks`, `note`, `first_release`, and `last_release`. The key is `kind`, `record_id`, and `first_release`. One foreign key points to `published_records`. Two foreign keys point to `publication_releases`. A null `last_release` means the range is open. The range rule is the same as in `publication_record_states`. The table `publication_withdrawal_corrections` holds the corrections of a withdrawal. A row holds the key of the withdrawal, `position`, `replaced_revision_number`, `published_at_utc_ticks`, `note`, and `facts_unchanged`. The migration `PublicationWithdrawals` creates both tables empty.
- The manifest `release.json` holds `records` and `withdrawals`. A withdrawal holds the kind, the record ID, the withdrawn revision, the first publication time, the withdrawal time, the note, and the corrections. The field `withdrawals` is required. A returned record leaves `withdrawals`.
- The ready lists read the active row and match by kind, so a statement ID cannot hide a document change.
- `bill-status.json` is part of each release and is optional for a reader. It holds `records`, a list of `recordId`, `text`, `date`, and `observedAtUtc`. `PreviousRelease` reads it to keep the status read times and to find a changed status. The search service never reads it.
- The `photo` of an official profile is null when the official has no photo. It is a fact about the official, not a field for an older version. The manifest and the record files carry no optional field that exists for an older version. The exceptions are `source` of a vote record and the entry fields `yeaCount`, `nayCount`, `alignment`, `chamber`, `voteKind`, `congress`, and `cosponsorIds`. Each manifest entry requires `kind`, `officials`, `issueIds`, and `policyAreaIds`. Each vote record and each row of the official vote files holds `chamber` (`house` or `senate`). Each vote record holds `source` (`congressGov` or `voteview`). A vote file with no `source` reads as `congressGov`. Each row of the official vote files holds `kind` and `issueIds`. Each of the seven record files holds `corrections`, and the manifest holds `withdrawals`; see [Corrections and withdrawal](#corrections-and-withdrawal). The files `officials.json`, `officials-summary.json`, and `officials/{id}/votes-{congress}.json` are part of each release. Action, vote, and statement records require `textOrigin` (`model`, `person`, or `code`). Only action records hold `code`. An action record may hold an optional `billCitation` for the title and introduced lines of the bill page. It counts as a citation, so every source stays cited. Statement records also require `approvedBy` (`code` or `person`). The version stays 1, because production holds live releases and every new field is optional. `PublishedOfficeTerm` allows a null party and a null end, and it requires `kind`. Readers accept version 1 only. An older release, or one with a term without `kind`, is not readable; see [Dev database reset](../operations.md#dev-database-reset).
- `PublishedOfficials` has a `Validate` method. Officials are capped at `PublishedOfficials.MaximumOfficials`, each official at `PublishedOfficials.MaximumTerms` terms, and every text value at 256 characters. The search service ignores these files. `PublishedOfficialVotes` is capped at `PublishedOfficialVotes.MaximumVotes` rows and `PublishedOfficialVotes.MaximumBytes` bytes, and its rows hold one Congress. A row allows 64 issue IDs of 256 characters, so `PublishedOfficialVotes.MaximumBytesPerVote` is 52 KB, which allows 3 bytes for each character. `PublishedOfficialSummaries` is capped at `PublishedOfficials.MaximumOfficials` rows and `PublishedOfficialSummaries.MaximumBytes` bytes. A row holds at most `PublishedOfficialSummary.MaximumRows` rows of each kind.

## Limits and planned work

- A retained release that is not converted has no party line-up rows, so a rollback to it serves a null `lineUp`. The owner command `releases lineups backfill` converts it, and `releases lineups verify` proves it. Run both in production for the active and retained rollback releases before the issue page reads the line-up. Keep the verifier result of one complete scan. Each release reads all its action and vote files. A release whose issues have no stored counts for its Congress gets no rows and keeps a null `lineUp`. The line-up reads the issue counts in `release_issues`, which the migration `ReleaseHomeIssueCounts` fills. It does not read the bill count tables. A bill with sponsors of two parties, or two matching terms with two parties, counts as unknown, because a bill must count once.
- The party line-up fill reads sponsorships and terms by key, one lookup for each bill. `PostgresReleaseIssueFillPerformanceTests` runs both issue fills on 15,000 bills, 20 issues, and 600 officials, after ANALYZE, within 1 s. Three local runs took 0.13 to 0.16 s for the Home counts and 0.37 s for the line-up. Both are slow on a fresh table with no statistics, because they share the eligible bills SQL. The Home counts took about 6.8 s in that case. A join of two derived sets in place of the lookups ran for minutes. `PostgresPublicationRecordStateTests.TheStateDiffForFifteenThousandPublishedRecordsStaysFast` names no issue, so it does not run the fill.
- Correction bootstrap pages bound returned candidates and file reads. A fresh missing-binding query can still examine all retained membership combinations. Cursor continuation skips earlier keys. The requested file limit does not bound all SQL work; larger retained sets need measurement. Verification pages read one release by the primary key order of its record states. A release verified once stays verified, so an operator controller keeps the ledger outside the database.

- Run the bounded correction-history bootstrap for the active and retained rollback releases before deploying the shared public reader. The bootstrap and separate verifier are implemented; live conversion and coverage checks remain pending. New publication commits already write exact bindings. Private release JSON remains conversion input only. The shared corrections reader is implemented in PublicApi. It deploys only after the bootstrap and verify pass.

- The bill count backfill and verifier are implemented, and the production run covered 31 releases with no failure. The official route and the ZIP lookup read the stored snapshots. Each release reads all its action and vote files, so a run costs one file read for each record. A run that finds a partial snapshot needs a person to decide the repair, because the command never repairs rows. The verifier proves counts and projection agreement only. It does not prove that sponsorship citations or other child evidence are complete. A release with no stored Congress total shows a caption in place of the bill figure. It never shows zero. The migration `DropPublicApiOfficialBillCounts` drops the unused live view `public_api.official_bill_counts`, and its rollback restores it. The issue route still counts `bills` from `public_api.bill_issues`, and the Home issue tile already reads the stored `release_issues.bills`.
- The entry tables hold the revision facts of the manifest entries. Only `public_api.bills` reads their `bill_line`. No other reader uses them. `releases entries backfill` fills the revisions of earlier releases from the kept folders, but a revision that only a retired folder held has no row. The backfill reads the whole state table in one query, so its memory use grows with the number of revision ranges. The limit bounds only the inserts. Each run reads every kept manifest that covers a range without a row. It also reads the first record file of each such range. `releases entries verify` proves that the tables rebuild the kept manifests. It does not compute the left-out fields from their owners. So it cannot show how often a view would differ from the published name, vote count, alignment, or cosponsor list. A later `officials` view supplies the names, and the public views compute the vote counts, the alignment, and the cosponsors. Then the change adds the foreign key from `publication_record_states`. A relationship entry needs `published_records` rows for its statement and target. Until `releases first-published backfill` has run, the commit stops with `FirstPublishedMissingException` for a target of an earlier release.
- `releases entries verify` writes each stored manifest again with the current serializer. An older image can write a release before a manifest field exists, for example the entry `chamber` field. That release fails with `manifestNotReproducible`, although its entries are correct. Only the newest kept release proves the current tables, so check that release. Old releases that fail this way need no repair. No test.
- An entry field that a later contract change adds needs a new column. Existing rows keep it null until a one-time fill.
- A relationship file published before `approvedBy` reads as `Person`, so the backfill labels it "A reviewer checked this link". Before the backfill, the owner checks production for links that code approved.
- A re-approval of the same revision after a withdrawal and a rollback stops the next publish with a conflict on the stored approval time. `approved_by` does the same when `Code` changes to `Person`. No command updates an entry row. The operator corrects `approved_at_utc_ticks` or `approved_by` with manual SQL on `published_entries`.
- `PublicApiGrants` revokes privileges on system functions and on the database, so `db migrate` needs a superuser. R-24 revisits this for a managed database, where the owner may not be a superuser.
- The PublicApi withdrawal views read the typed withdrawal rows only for the active release; old releases retain their own range-bound notice meaning. Withdrawals made before the migration have no rows. The first commit after the migration opens a row for each carried withdrawal at its own release number, so `first_release` is wrong for them. The backfill change must fix those rows and fill the earlier ranges.
- The withdrawal tables have no foreign key to the entry table. A later change adds the key from `kind`, `record_id`, and `withdrawn_revision_number`.
- The weekly brief of a record still comes from `BriefFirstRelease`, which reads the release rows. It does not read `published_records`. A later change can move it to the table.
- Until `releases first-published backfill` runs, a publish that adds a record of the active release stops. A publish whose release lists any withdrawal, carried or new, stops the same way. `PublishRelease.RequireFirstPublished` owns this check. On a deploy that adds the migration `PublicationWithdrawals`, the operator stops the worker, migrates, runs the backfill, and starts the worker. A record that no active entry or withdrawal names has no row until a publish adds it.
- When every row of a chamber holds it only in `previous`, `ShownCongress` can pick an older Congress than the figures allow. This edge case is not fixed.
- The code text of an action is stored in its revision. A revision written before this form keeps "Introduced May 21, 2025" until a change to the bill writes a new revision.
- New vote kinds and treaty votes wait for a contract choice.
- `PlainVoteWords` is not in any AI prompt yet. A later PR, "plain language prompt for vote and action text", plans to wire it in. Until then, only the pages use it.
- The status of a bill reaches the site only in a publish. The worker checks for a status change once for each publish tick. The first publish after the backfill finds no earlier row, so it writes a status row for every action that has a status.
- The status backfill reads saved captures, so a backfilled status is as old as the capture. A bill that no later update touched keeps that status and its read time.
- After `releases activate` of a release older than a rewrite, run the rewrite options again. `--rewrite-officials` rewrites the vote files and the summary row of every official. `--rewrite-entries` rebuilds the carried action entries and the stored entry rows. Use a new idempotency key each time, because the same key and payload replay the old result with no rewrite.
- An image from before the vote and cosponsor entry fields, `voteKind`, `congress`, and `billLine` cannot read a release that a newer image made. `UnmappedMemberHandling.Disallow` refuses the new members, and a new publish writes them in every entry, as null when empty. A new manifest writes `billLine` as null in an entry with no line. It also refuses the `previous` member of a summary row. To go back to the older image, first activate a release that it made.
- `cosponsorIds` and the cosponsor count leave out a withdrawn cosponsorship, and leave out an official who is also a sponsor of the same action. A sponsor list still includes a withdrawn sponsorship. The count covers every Congress that the release holds.
- A carried revision keeps the line that it first got, also when the line rule changes later. A returned action, or an older revision that publishes again, gets the line of the current rule. When the rule changed for that revision, the publish conflicts with its row. The same is true after the owner activates a release from before the line. Its entries hold no line, so the next rewrite takes the line of the rule, and it conflicts with a row that holds another line.
- The bill line comes only from the CRS summary of the action. The first-sentence rule of `BillLine` is a stopgap. Planned work: a later PR replaces it with a model line that carries a quote. Code checks the quote against the CRS summary. The line has the label "AI summary of the Congressional Research Service summary." and a link to the full summary. An action with no CRS summary has no line until then.
- `PublishRelease` reads all release vote revisions in every publish, to map each vote to its bill action. One vote revision that is not stored or not backfilled stops every publish. Run `votes revisions verify` and expect exit code 0 before a deploy that ships the bill line.
- The bill line rollout needs one command: `releases publish <idempotency-key> --rewrite-entries`. `--rewrite-entries` gives carried actions their `billLine`. The commit also fills the null lines of their rows. A plain publish does not. Run the rollout in this order. Deploy. Run `releases entries backfill <limit>` until it exits with 0 and `openRangesWithoutRow` is 0. Run the rewrite publish, which stops when a carried action has no row. Run `releases entries verify`. Verify fails for a release until its rows hold the lines. Rows of closed ranges from before the line keep a null line.
- The vote kind and Congress rollout needs one command: `releases publish <idempotency-key> --rewrite-entries`. Run it once in the deploy that ships the fields. Carried vote entries then get `voteKind` and `congress`. Until then they lack both, and a reader of them shows no count. If this change and the bill line change ship in one deploy, one run of the same command covers both.
- A House resolution roll call whose bill title has not arrived is classed as Passage, so it counts as substantive; see the [votes limit](votes.md#limits-and-planned-work).
- Missed votes count only the roll calls on this site. A roll call whose vote did not publish, such as a blocked or refused vote, is in neither the missed count nor the held count.
- Real bill titles have at most 544 characters in development data. A release where every action entry has a 4,000 character title is over 64 MiB. The publish then refuses it with a clear error.
- A row of an official vote file can hold 64 issue IDs of 256 characters. The read cap of a file is therefore about 266 MB. Real issue IDs have at most 60 characters.
- Each release links its photo files, so a photo file stays on disk while any kept release uses it. A prune removes it with the last release that links it. A takedown of one photo is an owner setting and needs a new publish. Kept releases keep the file until a prune removes them; see [operations](../operations.md#take-down-a-member-photo). A withheld photo and withdrawn content can stay in a kept release folder with no time limit. A prune removes a folder only when four things are true. At least 30 higher release numbers exist. The release is not the highest of a UTC day in the last 7 days. The folder is not the active or served folder. A later publish runs the prune. Seven days is the minimum for the highest release of a day. It is not a maximum for any folder. Restic backups can keep `releases/` for up to 6 months (see [operations](../operations.md#backups)). The search index keeps withdrawn rows (see [search](search.md#invariants)). A rollback to such a release shows them again.
- A change only to the tracked state of a person or to an issue name is not a profile change. A publish with no record refuses it.
- The host keeps the 30 highest release numbers and the newest release of each of the last 7 UTC days. It prunes the other release directories. It keeps the active release and the release that `current` serves. A rollback can reach only a kept release. During a burst of publishes, the 30 newest releases can span a few minutes. A rollback to a state before the burst then reaches only the last release of each earlier day, up to 6 days back. A drain publishes about one release every 7 seconds. Each release is about 29 MB in development. It is not measured whether that figure is the total size or the size that carried files do not share. The rule keeps at most 36 folders, plus the active and served folders when they are older. At 29 MB without sharing, 36 folders are about 1.0 GB, and 38 folders are about 1.1 GB. The daily releases need 7 days to build after the first deploy, so full rollback reach takes 7 days to appear. Hard links share carried files, so the real size is lower. A backlog makes several releases in one tick. A prune does not remove orphan folders in `staging/`, which a crash leaves.
- The loader drops relationships and briefs that are not ready after the store has alternated replacements and new records. After a mass change of citations, many drops can break the alternation. Replacements can then fill more than half of a batch. The next tick reads again without the dropped rows.
- A record that cannot build still takes a place in the 64 records that the tick lists. More than 63 such records in one kind can hide other records until a person fixes them.
- A ready record that cannot build is logged at error level at every tick until a person fixes it. A store read that fails, for example on a changed citation, fails the tick.
- After a rollback and a CLI publish, the rolled-back records list again with the same key. The stage replays the stored release each tick and publishes nothing until new records change the batch. Publish those records with the CLI.
- The stage has no status row. Its loop writes the `publishing` heartbeat; see [collection](collection.md#autonomous-collection-engine).
- A vote record embeds at most `PublishedVote.MaximumSources` sources: the detail, the members, and the bill detail.
- An action record embeds at most `PublishedAction.MaximumSources` sources. The worst case is the detail page, 3 cosponsor pages (250 rows), and the summaries page, which is 5 sources. A record over the cap fails publish loudly.
- The stage `publishing` leaves out a withdrawn record that is approved again at the withdrawn revision, by code, or by a person without a note. It logs one line for each skipped record at every tick, until a person approves a higher revision with a note.
- A returned record counts against the cap of 20 notes. A record with 20 notes cannot return yet.
- The worker or the CLI returns a record. The CLI and Take off site on the record editor withdraw.
- A relationship or a brief that cited a withdrawn record stays withdrawn when the record returns. A person must publish it again.
- A withdrawn record still answers with its notice page and status 200. A 410 status needs a Cloudflare rule, which comes with [R-24](../roadmap.md#later). The search service has the same limit; see [search](search.md). The notice page has `noindex`, so search engines drop it.
- The withdrawal check of citations reads every carried brief file when the request withdraws a statement, a document change, or an action. The cost grows with the number of briefs.
- Kept release directories keep the withdrawn content until a prune removes them. A pinned search release can still find the record; see [search](search.md).
- The privacy table of the about page says "Nothing" for a page read. Its search row says "Nothing" too. Both stay true only while the deploy keeps no access logs for page reads or search requests. The deploy configuration sets that; see [Web server](../operations.md#web-server).
- The about page says a backup can keep a closed report for up to 6 months after the review system deletes it. That stays true only while the nightly backups run and `backup.sh` keeps 6 monthly snapshots; see [Backups](../operations.md#backups).
- A replacement reads the record file of each replaced record in the active release, to copy its corrections. The cost grows with the number of replaced records, at most 64.
- A record keeps at most 20 corrections with a note. A person cannot publish a 21st correction of one record yet. Code updates still publish.
- A rollback followed by a publish drops the rolled-back revision and its note from the history. The list copies forward from the active release. A rollback to a release before a withdrawal restores the record. A publish from there drops the withdrawal history.
- Only the statement page labels a statement date that code read. The link page, the paired day on an official page, and the link editor show that date with no label. `PublishedRelationship` carries no `approvedBy` for its statements yet.
- The record page of an official lists every entry that names the official, 15 rows a page in the browser. A relationship or a document change that names the official appears with the other entries. The official page shows only the newest five items of each section.
- A replaced vote touches its old members in every Congress of the replaced votes of that publish. The result is correct, but a publish may rewrite identical files.
- A relationship flagged "no longer matches" still publishes. Only a person withdraws it. The owner sees an approved link with the flag as a row in the Needs a person queue; see [review](review.md#needs-a-person-queue). The review editor shows the flag. The `releases publish` command shows no flag, because it names records by ID and prints only the release summary.
- A relationship waits until both cited records are in the active release. This follows the rule for briefs. A later wake publishes the relationship after the cited records.
- A record with 20 corrections that have a note cannot take another person revision. For an action, a vote, a statement, or an executive action, only a code-approved revision can publish. For other kinds, no new revision can publish. The worker logs the record and skips it at every tick. The Review home page and `releases blocked` list it.
- A withdrawn record with 20 corrections that have a note cannot return. A person approval with a note raises `CorrectionLimitException`, one without a note raises `MissingCorrectionNoteException`, and a code approval raises `WithdrawnRecordException`. The blocked list shows it when a person approved a higher revision. No cap-free way out exists yet.
- The approve page shows the correction note box for every approval, also for a first publication, because the page does not read the active release. A note on a first publication is dropped.
- Expandable evidence and shareable records are planned against published releases.
- `PublicApi` reads the `public_api` views through a role that can read nothing else. The release manifest is no data path for public pages. The views cover votes, bills, statements and their speakers, executive actions, and officials. `PublicApi` serves lists and details for votes, bills, officials, and statements, plus withdrawal notices. The statement detail endpoint serves bounded source text, quotations, and citations from the active published revision. The official routes expose the portrait path and attendance figures. Party-vote figures are implemented. Statement counts by Congress and issue remain planned. Publication pins official photos, entry Congress, vote parties, and alignment in columns. Counts of sponsored bills use the Congress of the bill number. `PublicApi` also serves the ZIP lookup from `zip_districts` and the name views.
- The manifest is one file, and each publish reads the previous one. R-63 moves its entries to tables, so a publish no longer reads it. Release 910 held 18,281 records in 14.9 MB, about 815 bytes for each record.
- At 40,000 action entries with 15 cosponsor IDs each, the manifest is 52,280,111 bytes (about 49.9 MiB), about 78% of the 64 MiB cap. That leaves about 370 bytes of headroom for each entry. The 15 IDs and the 114-character title are assumed inputs, not measured from data. `PublicationReleaseTests.AManifestOfTheMaximumNumberOfRealisticActionEntriesWithCosponsorsStaysUnderTheManifestByteCap` measures it. `PublishRelease` refuses a manifest over the cap.
- The manifest filter fields stay, because the search service uses them.
- A deploy rollback to an image from before the migration `DropPublicationRecordsJson` cannot run until an explicit EF rollback of that migration happens. That image reads and writes `records_json`, and the column does not exist. The `Down` of the migration adds the column and rebuilds it from `publication_record_states` for every release, in the shape `kind`, `recordId`, and `revisionNumber`. The order of the entries in a release is by kind and then by record ID, because the table does not keep the original order. `db migrate` only moves forward.
- `deploy/scripts/update.sh` stops the worker and the review host before `db migrate`, so no old image commits a release during the migration. A manual migration needs the same stops. Do not run `releases publish` during `update.sh`, because that one-off container uses the old image.
- A future mobile client would read public release contracts through an API, not operational storage.
- Public MCP will expose `search_records`, `get_record`, `get_official_timeline`, and `compare_document_versions`. It returns published data with IDs, citations, dates, review status, coverage caveats, and the release ID.
- Public MCP cannot start collection, inference, or edits. It bounds and pages responses, limits requests, and accepts record IDs, not arbitrary fetch URLs. It treats source passages as untrusted attributed content.
- Public MCP will run in a separate deployment and call the public API for published data. It uses no public release-file feed. The website and public MCP share the same release, and clients can pin it across calls.
- Public MCP needs request compute, but never the local database or AI inference.
- Postgres and capture files need coordinated backups and a tested restore. Production backup rules are in [host](host.md#limits-and-planned-work).
- Retention must keep the evidence that published releases reference. Disposable captures follow an explicit policy, which is not agreed yet.
- Monitoring must cover freshness, skipped and deferred work, source failures, storage, and spend.
