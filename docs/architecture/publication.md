# Publication

## Purpose

The publication feature turns approved revisions into immutable, cumulative static releases. It activates a release atomically. A separate static file server reads only published files.

## Decisions

- Only the owner publishes or activates a release.
- A record is published at its current revision, and only when that revision is approved and has no unresolved concerns. Code can approve an action or a vote. People approve the other kinds. The owner publishes all kinds.
- The action and vote pages say "From the official record, checked" with the approval time. They do not claim that a person approved the record. When `textOrigin` is `model`, they add "An AI summary of the official record". Text that a person wrote gets no label. `ApprovedAtUtc` holds the time of the approval, by code or by a person. Enforced by `PublishedActionView` and `PublishedVoteView`. Tests: `ReleaseRendererTests.ActionAndVotePagesSayThatTheRecordComesFromTheOfficialRecordInsteadOfClaimingAPersonApprovedIt` and `ReleaseRendererTests.ActionAndVotePagesLabelAnAiSummaryOnlyWhenAModelWroteTheText`.
- A newer draft never replaces published content automatically.
- A release is cumulative. It holds the base release records plus explicit additions or replacements.
- Carried records are hard links to the immutable files of the base release. Disk therefore grows with published records, not with the number of releases.
- Each publish rebuilds `release.json`, `officials.json`, `catalog.json`, the home page, the all-records pages, the issue and policy area pages, `search.html`, and the assets. It also writes again the page of each record that lists related records, when the new release holds a link that cites that record. Its record file stays the same hard link; see [related records](#related-records). It reads the previous manifest once, under the 32 MB manifest cap, `PublicationProtocol.MaximumManifestBytes`. `PublicationProtocol.MaximumRecordsPerRelease` is the one owner of the record limit, which is 20,000. The database has no count check, because C# owns the rule.
- Postgres records which release is active. The `current` link is only a copy for the static server, so a failed link swap never drops committed records.
- Every publication write takes all six review locks in one fixed order, which prevents a deadlock. The order is in [advisory locks](../architecture.md#advisory-locks).
- A release has no status column. `is_active` marks the one active release: a commit sets it on the new row and clears the old one, and rollback moves it.
- Rollback is a CLI command only. The workspace has no rollback or activate control.
- Every release is kept. Carried records are hard links, so disk grows only with published records, and public MCP clients can pin a release. The [search](search.md) service pins releases too.
- In production, releases go to a Cloudflare R2 bucket behind the Cloudflare CDN on civic-lens.info. Terraform defines the bucket and the domain.
- Publish stages and checks a release on the server, then uploads it. The active release changes only after the upload finishes.
- Locally, a Caddy container serves the release root with `file_server { precompressed br gzip }`.
- Host renders the shared Razor components to static HTML, so publication needs no new project.
- Each manifest entry carries filters, so the facet pages and the search filters need no record file reads. Each published record type owns the mapping in its `ToEntry` method. A filter that the kind has no fact for stays empty; publish never guesses it.
- One loader owns each record kind: its ID shape, its ready list, and how publish loads and builds it. `PublishedRecordLoaders` lists them, and the publish and ready-list handlers go through that list. One loader owns the Application side of a kind. The other per-kind places are the `PublicationProtocol.IsRecordId` arm, the store state check, `PublishedRecordLabels.Kind`, the review link, and the `IReleaseRenderer` method.
- The loader base class gives each kind one owner for its Application rules. A non-generic base exists only so `PublishedRecordLoaders` can hold all record kinds in one list. The six kinds are real variation, with different IDs, stores, and records. The precedents are `PostgresAnalysisStore<TRun>` and `ReviewRecordPage`.
- `PublishedRecordLoader<TCandidate, TAddition>` owns the ready-list and load steps once. A kind supplies only its store reads, its ready row, and how it builds and renders one record. `PublishedRecordRules.Cite` is the one owner of a published citation for every kind.
- Official names in every record kind come from the current `PublicationCatalog`, not from stored revisions. The action `policyAreaIds` filter comes from the policy area ID that the draft stored. Drafting resolved it through `IssueConfiguration.PolicyAreaIdFor`, and the reviewer approved it with the revision. Publish never reads the issue configuration. A label that the configuration lacked at draft time gives an empty filter.
- A record ID is unique across all kinds, because all kinds share the flat `records/{id}` paths.
- A brief record embeds no source text. It holds the wording that a person approved and a list of citations. Each citation names a published record by kind, ID, and revision, and carries a copy of the cited headline. A brief is a weekly summary over other records, so it publishes only when the new release holds every record that it cites; see [briefs](briefs.md#publication).
- An action record embeds the full text of each cited extraction once. Each citation names its extraction, and the contract checks the quote against that source.
- A relationship record links one statement to one action or vote. It embeds no source text. It holds the wording that a person approved, the quote of the statement, and the fact of the target. Both are text. It also holds a citation of each side. A citation names a record by kind, ID, and revision, and carries a copy of the headline. A relationship publishes only when the new release holds both cited revisions and the latest decision on each is an approval. A link that a release already holds stays in later releases, whatever happens to the records that it cites. See [relationship record](#relationship-record).
- A vote record embeds the full text of each cited extraction once, as an action record does. Its citations are the vote day, the kind, the result facts, and the cast of each tracked member. `PublishedEvidenceRules` owns the source and citation checks for actions and votes.
- The manifest schema version is 5. A new record kind needs no version bump, because every reader ships with or after the release it reads. Versions flatten under roadmap R-23. The publisher reads only releases of the current schema version. `app.js` ships inside each release. An older publisher fails loudly on the unknown kind.
- Release JSON uses relaxed escaping (`JavaScriptEncoder.UnsafeRelaxedJsonEscaping`), so non-ASCII letters and punctuation take UTF-8 bytes, not 6-byte `\uXXXX` escapes. This is safe because release JSON is fetched as JSON and never inlined in HTML or a script tag. Readers do not change.
- Unreviewed proposals, internal reviewer notes, operational job details, and mutation controls stay private.
- Public serving reads release contracts only. It never reads operational storage or private notes.
- The public UI is static pages on a CDN. Publish renders every public page, including the official, issue, policy area, and briefing pages. No server is on the public page path. Search and reader reports go to the R-40 service.
- Search goes to the R-40 [search](search.md) service, which is also the public read API. Each release holds `search.html`, which calls it. The browser no longer searches the manifest.
- Each public page has one stable URL, so search engines can find it.

## Invariants

Each line gives the rule, what enforces it, and the test that protects it. Cross-feature invariants are in [architecture](../architecture.md#invariants).

Enforced by the `PublishRelease` record count check and manifest size check. Test: `PublishReleaseTests.RejectsMoreRecordsThanTheCapBeforeAnythingIsBuilt`, `PublishReleaseTests.AReleaseAtTheRecordLimitOfFilledStatementEntriesKeepsTheManifestUnderThreeQuartersOfTheManifestCap`, `PublishReleaseTests.AReleaseAtTheRecordLimitOfFilledActionEntriesKeepsTheManifestUnderThreeQuartersOfTheManifestCap`, and `PublishReleaseTests.RefusesAManifestOverTheManifestCapAndStagesNothing`.

- A manifest of schema version 4 or older is refused, and the version 5 files round trip and stay within their caps. The caps keep the file size bounded. The search service reads neither file yet. The byte cap comes with the reader in PR 2b of R-36. Enforced by `PublicationRelease.Validate`, `PublishedOfficials.Validate`, and `PublishedCatalog.Validate`. Tests: `PublicationReleaseTests.RejectsASchemaVersionThisReaderDoesNotKnow`, `PublishedOfficialsTests.ASchemaFiveReleaseKeepsItsOfficialsAndCatalogThroughAJsonRoundTrip`, `PublishedOfficialsTests.TheFilesHaveSizeCapsSoTheirSizeStaysBounded`.
- The search service does not fetch the two new files. Enforced by `ReleaseFeed`, which fetches the manifest and the record files only. Test: `ReleaseIngestTests.TheOfficialsAndCatalogFilesOfASchemaFiveReleaseAreNeverFetchedSoTheSearchIndexHoldsTheSameRecords`.
- A page in a subfolder links to assets, records, and pager targets through a `../` prefix. Enforced by `PublishedFacetPage`. Test: `ReleaseRendererTests.FacetPageLinksResolveFromItsSubfolderAndPageThroughItsRecordsNewestFirst`.

## Behavior

### Public reader experience

A record explains what happened, who was involved, and when. Where evidence supports it, it explains why the event matters. It states what the evidence can and cannot establish. Readers move from the account into retained passages and exact citations. They do not need to read collection jobs or extraction metadata first.

A document-change record shows both versions, and observation history where needed to explain gaps. A current source link supplements the retained evidence; it does not replace it. Public records show their review and version context and published corrections.

### Release content

- Each document-change record carries the full extracted text of both versions, their source URLs, and their observation times. Changed regions are offsets into those texts.
- A citation holds an extraction ID, UTF-16 offsets, and the quoted text. The contract rejects a quote that does not match its offsets.
- Records show the approval date and the first-publication date. The home and all-records pages show the release date.
- `index.html` is the home page. It shows the latest brief, the 20 newest records, and links to the issue and policy area pages. The latest brief is the one with the newest week. It shows the headline and the paragraphs with their citation links, which lead to the brief page. The home page has no search panel.
- `all.html`, then `all-2.html` and so on, list every record 50 to a page, newest first, with relative previous and next links. They hold no search panel; `search.html` has the search.
- `issues.html` lists each issue and each policy area with its name and record count.
- Each issue has `issues/{id}.html`, then `issues/{id}.page-2.html` and so on. Each policy area has `policy-areas/{id}.html` with the same page suffix. A page lists the manifest entries that hold the ID in `issueIds` or `policyAreaIds`, 50 to a page, newest first. A facet has pages only when its ID is a valid path segment. See Limits. `PublicationProtocol` owns every page path.
- A page outside the root folder builds each link from a `../` prefix, as a record page does.
- Officials, issues, and policy areas appear by their configured name. An ID with no configured name appears as the ID.
- Only the release manifest shows the schema version.
- `officials.json` lists each configured person who has a published record in the release. A record counts when its manifest entry names the person as an official. A record also counts when a vote file of the release holds the person as a member. A vote entry names no official. Publish therefore reads the member person IDs of the vote revisions of the release in one database query. The query takes the record IDs and revision numbers of the manifest, so it covers carried votes and new ones. It sends two array parameters, so the list size does not matter. It reads no vote file. Each profile holds the ID, the configured name, the configured Wikidata ID, and the dated terms. A term holds the office and the party, as the roster gives them. It holds the start and end dates. It holds the state and district when the roster gives them.
- `PublicationOfficials` joins a person to terms. It matches the bioguide ID to the latest member snapshot first. When no term matches, it matches the Wikidata ID to the latest executive snapshot. A person with no match is listed by name with no terms. A Wikidata ID with no executive official is not an error.
- `catalog.json` lists the issues and policy areas that the records of the release use, each as an ID and a name. It uses the names of the facet pages, so an ID with no configured name appears as the ID.

A release holds six kinds of record. Each manifest entry has a `kind`: `documentChange`, `statement`, `action`, `vote`, `brief`, or `relationship`, a lowercase camel string. All kinds share the `records/` folder, the record data path, and the record page path.

| Kind | Record ID |
|---|---|
| `documentChange` | The draft ID: 32 lowercase hex characters |
| `statement` | The candidate ID: 64 characters |
| `action` | The action record ID: 64 lowercase hex characters |
| `vote` | The vote record ID: 64 lowercase hex characters |
| `brief` | The brief record ID: 64 lowercase hex characters; the [briefs](briefs.md#decisions) page defines it |
| `relationship` | The pair key: 64 lowercase hex characters; the [statements](statements.md#decisions) page defines it |

A statement record carries one source version with the full extracted text, the source URL, and the observation time. It also carries:

- speakers by configured name, and other speakers
- issues, policy areas, and bill numbers
- the optional statement date with its evidence
- 1 to 32 quotations, each with its kind: `directQuotation` or `releaseText`

Every quotation must equal the source text at its offsets.

An action record carries:

- the bill identity (congress, type, and number) and the bill title
- the policy area with its citation, the policy area ID stored at draft time, and the tracked issue IDs
- the CRS summary citation, when the revision has one
- 1 to 600 sponsorships. Each has the official by configured name, the role (`sponsor` or `cosponsor`), and the original flag. It also has the sponsored date, the optional withdrawn date, and one or two citations.
- 1 to 8 sources, each with the full extracted text of one cited Congress.gov API page, its URL, and its observation time

The sources are the distinct cited extractions in citation order, so the first one is the page of the first sponsorship. Every citation must name one of the sources and quote its text exactly. A source that no citation names is rejected.

A brief record carries:

- the headline and 1 to 12 paragraphs, each with the citation IDs that it uses
- the week start (a Monday), the cutoff release number, and the coverage counts: considered, sent to the model, and cited
- 1 to 256 citations. Each has its ID, kind, record ID, revision number, and a copy of the cited headline

A relationship record carries:

- the headline, which joins the headline of the statement and the headline of the target
- a citation of the statement and a citation of the target. Each has the kind, the record ID, the revision number, and a copy of the headline
- the type, one of `describesOwnBill`, `statesPositionOn`, `claimsCreditFor`, or `statementAboutVote`, and the reason in one sentence
- the quote of the statement and the text of the fact of the target. Both are text only. The builder takes the quote from the article text. Its span must lie on the extraction of the statement and inside one passage of the statement
- the optional statement date, the speakers by configured name, and the issue and policy area IDs of both sides

The approval time of a record is the latest approval of its current revision, for every kind. One Application rule owns that time.

### Publish

One publish request names 1 to 64 records, each as a kind and an ID. For each kind, publication loads all selected drafts and their verified evidence in one repeatable-read transaction. Each read uses a fixed number of queries for any selection of 1 to 64 drafts. The publisher builds records from this evidence and does not read it again.

1. Application builds the release contract. A page step then renders every page that the publish writes, and Host renders the static HTML. See [related records](#related-records).
2. The owner action builds the release in a staging directory, verifies it, and moves it to a uniquely named directory under `releases/`.
3. Under all six review locks, the commit checks each added record's revision and review-state version again, in the draft table of its kind. For each added brief or relationship it also checks that every citation is current in the records of the new release. It also checks the next release number and the active release it built on. It then requeues the brief of the week of each record that the release changes, drops, or adds again; see [briefs](briefs.md#staleness).
4. In the same transaction, it records a sequentially numbered release and marks it as active. It stamps the release time from the database clock after it holds all review locks. The commit does not take a time from the caller.
5. After the commit, it takes all six review locks again, reads the active release, and atomically replaces the relative `current` symbolic link.

Publish, replay, and activate all end with step 5. An older command therefore cannot move the link back after a newer one.

The review state is checked at commit, so a concurrent blocking decision cannot be ignored. A commit that fails on a conflict or invalid input deletes its directory. If that cleanup fails, or an unknown failure occurs, the directory stays. Only committed releases can be activated.

Each publication builds on the recorded active release, not on the link. A replayed publish request and the activate command both point the link at the recorded active release. This repairs a link that is out of date. Publish requests reuse the review replay receipts.

### Rollback

Rollback records an earlier release as active and then points the link at it. It also requeues the brief of the week of each record that differs between the two releases. The next publication builds on the rolled-back release, so it does not restore the records that were rolled back. A publication built before a rollback fails on commit.

### Owner publish section

The Review home page shows a publish section to the owner only, and the handlers also enforce the owner role. The ready-to-publish read lists approved document changes, statements, actions, votes, relationships, and briefs that the active release does not hold at their current revision. A brief or relationship whose citations are not all current in the active release is not listed. A record is a replacement when the active release holds an older revision. Otherwise it is new.

SQL selects a bounded candidate set for each kind from the review and active-release tables. Application then applies the one publishability rule in `PublishedRecordRules`, which the publish handler also uses. The kinds share the publish limit equally. A kind with fewer ready records gives its unused share to the other kinds.

The owner selects records with checkboxes. A summary step lists each headline, its kind, and the next release number. Only the confirm form calls the publish handler, with one idempotency key for each page render. The page lists recent releases read-only.

### Corrections and withdrawal

Withdrawing approval does not change published artifacts. The UI flags affected published records for an explicit correction or withdrawal release. A correction needs a new revision, an approval, a public correction note, and a new release.

### Vote record

`PublishedVote` is the contract of a vote record. `PublishedVoteBuilder` builds it from an approved `VoteDraftRevision`, the review decisions, and the cited extractions. It maps each member official through `PublishedRecordRules.MapOfficial` and copies each citation through `PublishedRecordRules.Cite`. The vote kind enum mirrors the Core `VoteKind`. `PublishVoteTests` tests the builder through `PublishRelease`, as for the other kinds. The official filter does not find votes until the official pages (R-36) or the search service (R-40) index them. `VoteRecordLoader` owns the vote kind for publish and the ready list. `PostgresVoteReviewStore.GetForPublicationAsync` reads the selected drafts, their review cycles, and the cited extractions. It also reads the IDs of the action records with the same congress, bill type, and bill number. Several bill sources can draft one bill, so there can be more than one ID. The loader passes the first ID whose action record is in the release to `RenderVoteAsync`. The release holds an action record when the base release has it or the same publish adds it. Loaders run in list order and action comes before vote, so a same-release action counts. The page links to it. Otherwise the page shows the bill as text.

### Relationship record

`PublishedRelationship` is the contract of a relationship record. `PublishedRelationshipBuilder` builds it from an approved `RelationshipRevision`, the cited statement revision with its article text, and the cited target. `RelationshipRecordLoader` owns the kind for publish and the ready list, as `BriefRecordLoader` does for briefs. `PostgresRelationshipReviewStore.GetForPublicationAsync` reads the selected drafts and their cited revisions in one repeatable-read transaction. It flags each relationship whose cited revisions are not current in the release that the loader passes. The ready-list read uses the active release.

The review flag "cited records changed" keeps the approved-revision rule of [statements](statements.md#relationship-review). Publication uses the release rule above, as briefs do. The two flags can differ, because a cited record can be approved at a newer revision that the release does not hold yet.

A relationship page names the cited revision number of each side. It links to the current page of each cited record, which can show a newer revision. The page shows the reason, the quote of the statement, and the fact of the target. Its caveat says that the link states no verdict.

### Related records

A statement, action, or vote page lists the relationships of the new release that cite its record. The page step builds the list at render time. `ReleaseLinks` holds the relationships of the new release: the ones that the publish adds, and the carried ones that it reads from the previous release. One database read names the carried relationships that cite a record this publish renders. `PostgresRelationshipReviewStore.FindCitingAsync` does it from the pair rows. The publish then reads only those files, and none when it adds no statement, action, vote, or relationship. `PublishedRecordFiles.MaximumCitedRecordBytes` caps the read of a cited record. It derives from the source limits, so it holds the largest action record. `ReleaseLinks.Citing` orders a list by the statement date, with an undated statement last, and then by record ID.

`ReleasePages` renders every page that the publish writes. A loader gives each added record a page renderer that takes its related list. A record that the publish adds or replaces therefore lists its links, including the carried ones. A statement, action, or vote that an added link cites, and that the release carries, gets its page written again. `ICarriedPageLoader.RenderCarriedAsync` renders it from the carried record file with the related list. The kind loader owns this step, so the vote loader finds the action record of the bill again. `PublishRelease` links the record file of such a record and writes the new page.

A record page that no new link cites, and that the publish does not add or replace, stays a hard link. A later publish that replaces a cited record lists its carried links.

### Rendering

The release builder renders public components to static HTML through `PublicPage`. The pages are the home, all-records, search, facet list, and facet pages, and one record page for each kind. `PublishedHomePage` shows the brief through `PublishedBriefText`. The brief page uses the same component. `PublishedAllRecordsPage`, `PublishedFacetPage`, and `PublishedHomePage` list records through `PublishedRecordTable`. `PublishedSearchPage` renders `search.html`. `PublishedFacetsPage` and `PublishedHomePage` list facets through `PublishedFacetBrowser`. The record pages are `PublishedRecordPage`, `PublishedStatementPage`, `PublishedActionPage`, `PublishedVotePage`, `PublishedBriefPage`, and `PublishedRelationshipPage`.

A statement, action, or vote page shows the "Related records" panel of `PublishedRelatedPanel` when its list is not empty. Each row links to the other record and to the relationship page, with the link type and the statement date.

An action page shows the headline, the summary, the bill, the title, the policy area, and the tracked issues. It has a sponsorship table with each official's configured name, role, original flag, dates, and cited quotes. It shows the policy area and CRS summary citations. Each source shows its URL and observation time as plain text, with no link, and its full text with the quotes marked. Its caveat says that a sponsorship is a proposal, not a law, and that the record lists tracked officials only.

A vote page shows the headline, the summary, the vote day, the kind, the roll call, and the tracked issues. A "Bill" panel shows the bill identity as plain text. It shows a link to `records/{id}.html` instead when the caller passes the ID of an action record in the same release. The "Result" panel lists the day, the kind, and each result fact as a cited quote. The members table shows each official's configured name, cast, and cited member line. Each source shows as on an action page. The caveat says that the record lists tracked officials only. It also says that each cast is the wording of the House Clerk roll call.

A brief page shows the headline and the paragraphs, each with links to its citations. A "Cited records" panel lists each citation. Each row shows the ID, the kind, and the revision number. A link to `records/{id}.html` shows the copied headline. The facts name the week, the cutoff release, and the coverage counts. The caveat is the sample note. The brief cites some of the new records that Civic Lens considered for the week. It is not a full account.

A release copies `assets/css/theme.css`, `assets/css/app.css`, `assets/js/theme.js`, `assets/js/app.js`, and the fonts. Pages also work without JavaScript. Shared components are described in [host](host.md#presentation).

### Search

Every release holds `search.html`, rendered by `PublishedSearchPage`. Every public page links to it. The page fills the kind, official, issue, policy area, and source filters from the manifest and the catalog names. A script on the page calls the [search](search.md) service at `CIVIC_LENS_PUBLIC_API_URL`, which publish reads. The form stays hidden until `app.js` runs, because search needs JavaScript. Without the variable, the page says that search is not available. A method note on the page states the source text limit.

## Storage and contracts

- The generated [publication schema](schema/publication.md) lists every table, column, key, check, index, and trigger.
- Each release row lists its records as kind, record ID, and revision.
- The ready lists read the active row and match by kind, so a statement ID cannot hide a document change.
- Schema version 5 adds the files `officials.json` and `catalog.json` to each release. Schema version 4 gave the action and vote records the required field `textOrigin` (`model` or `person`). Readers accept version 5 only. A release before version 5 is not readable, so do the dev reset before the first version 5 publish; see [operations](../operations.md#publish-a-static-release). The schema flatten at R-23 handles production.
- `PublishedOfficials` and `PublishedCatalog` each have a `Validate` method. `IssueConfiguration` refuses an issue or policy area name over 256 characters, so a catalog entry never fails the publish. Officials are capped at `PublishedOfficials.MaximumOfficials`, each official at `PublishedOfficials.MaximumTerms` terms, the catalog at `PublishedCatalog.MaximumEntries` entries in each list, and every text value at 256 characters. The search service ignores both files.

|---|---|---|---|---|---|---|
| `officials` (ID and configured name) | Officials | Speakers | The sponsor, when tracked | Empty | Empty | The speakers of the statement |

- Each release also holds `release.json.gz` and `release.json.br`, at `PublicationProtocol.ManifestGzipPath` and `ManifestBrotliPath`. They compress the exact manifest bytes, so a static server can send them without compressing on each request.
- A separate static file server serves the release root read-only. It has no access to operational storage.

## Limits and planned work

- A vote record embeds at most `PublishedVote.MaximumSources` sources: the detail, the members, and the bill detail.
- An action record embeds at most `PublishedAction.MaximumSources` sources. The worst case is the detail page, 3 cosponsor pages (250 rows), and the summaries page, which is 5 sources. A record over the cap fails publish loudly.
- No kind can publish a correction or withdrawal release yet. [R-32](../roadmap.md#next) adds them before the first deploy.
- The R2 upload, the CDN, and the local Caddy container are not built yet. They are part of R-24.
- The official profile pages, the vote index files, and the official and issue timelines are planned in [R-36](../roadmap.md#next). The official pages will show dated statements, actions, and reviewed relationships. They will read `officials.json`. The timelines will build on the published relationships.
- A related list orders links by the statement date. On a statement page every link has the same date, so the order there falls back to the link ID. Dates of the target records are not in the relationship file.
- A publish that adds or replaces a statement, action, vote, or relationship reads the carried relationship files that cite those records. It also sends the IDs of all relationships in the release to one database query. The cost of the query grows with the number of published relationships.
- A carried vote page lists a bill action link only when the release holds an action of that bill. A later action does not write the vote page again.
- A relationship flagged "no longer matches" still publishes. Only a person withdraws it. The owner publish list and the summary step show the flag. The `releases publish` command shows no flag, because it names records by ID and prints only the release summary.
- A relationship waits in the owner publish list until both cited records are in the active release. This follows the rule for briefs. The owner publishes the cited records first, and then the relationship.
- Timelines, expandable evidence, and shareable records are planned against published releases.
- Public filter pages are an MVP requirement. The issue and policy area pages are built. The R-36 official pages will complete them.
- A facet page lists the kind, headline, and first publication date of each record. Officials, issues, and event dates are not on it yet.
- Reader reports on a published record go through the R-40 service. The operational application pulls each report into the review queue, and a person handles it. The report names the record ID and the release ID.
- Split the manifest by kind when it grows over 4 MB.
- At 20,000 entries the worst realistic manifest is about 14.6 MB, under three quarters of the 32 MB cap. `PublishRelease` refuses a manifest over the cap.
- A facet ID that the catalog does not name still gets pages, and they show the ID. This keeps a carried record from blocking a later publish after an issue leaves the configuration. `PublicationProtocol.MaximumFacetIdLength` is the one length limit. `IssueConfiguration` applies it to configured issue and policy area IDs, so the configuration fails to load on a longer ID. A carried manifest ID can still be longer or can hold other characters. Such a facet ID gets no pages. The facet list shows its ID with no link.
- The manifest filter fields stay, because the facet pages and the search service use them.
- Each release row stores `records_json`, about 2 MB at 20,000 records. Review queries expand the active one.
- Rolling back the `DropReleaseCountCheck` migration fails while any release holds more than 2000 records.
- A future live public Blazor deployment must read published releases only and stay separate from the operational application.
- Each publish rebuilds the home, all-records, search, and facet pages from the manifest in memory. The measured case has 20,000 records, 100 issues, 20 policy areas, 2 issues and 1 policy area for each record, and a local disk. It writes 1,603 page files, which are 400 all-records pages, 1,200 facet pages, the home page, `issues.html`, and `search.html`. They total 33 MB, and rendering and writing them takes about 1.0 second. The file count is one page for each 50 records of each facet, so it grows with the number of facet memberships, not with releases. A record holds up to 64 issue IDs and 64 policy area IDs, so the facet page count has no fixed cap. Only the configured issues keep it low.
- A future mobile client would read public release contracts through an API, not operational storage.
- Public MCP will expose `search_records`, `get_record`, `get_official_timeline`, and `compare_document_versions`. It returns published data with IDs, citations, dates, review status, coverage caveats, and the release ID.
- Public MCP cannot start collection, inference, or edits. It bounds and pages responses, limits requests, and accepts record IDs, not arbitrary fetch URLs. It treats source passages as untrusted attributed content.
- Public MCP will search through the search service API, over the same entries as the website. The website and public MCP will share one release, and clients can pin it across calls.
- Public MCP needs request compute, but never the local database or AI inference.
- Postgres and capture files need coordinated backups and a tested restore. Production backup rules are in [host](host.md#limits-and-planned-work).
- Retention must keep the evidence that published releases reference. Disposable captures follow an explicit policy, which is not agreed yet.
- Monitoring must cover freshness, skipped and deferred work, source failures, storage, and spend.
