# Executive actions

## Purpose

The executive actions feature records presidential documents from the Federal Register. A record holds the official title and the facts of one document: its type, number, dates, citation, and President. Code approves each record after it checks the citations, because the facts come from the Federal Register. A person can only withdraw a record or approve it again. The record of an original document also has the body text of the document, which a separate text job reads. An AI step then writes a short summary of that text as the next revision. Code checks the summary before it approves it. The step is off until the owner turns it on.

## Decisions

- The source is the Federal Register JSON API. It needs no key. The collector sends the shared User-Agent `CivicLens/0.1 (civic-lens.info)` and no email address.
- The scope is executive orders, proclamations, notices, and memoranda. The list filter `presidential_document_type` selects them. The API gives `presidential_document_type` as a filter only, so the parser reads the `subtype` field of each document.
- One record is one original document. Its identity is the Federal Register document number of the original. The record always keeps the number, the dates, the citation, and the link of the original as its facts.
- A correction document names the original in `correction_of`. It adds one `Correction notice` fact to the record. The fact holds the number, the publication date, and the link of the correction, and it cites the capture of the correction. A correction never replaces a fact of the original. A notice for a recorded original makes a new revision.
- A correction that arrives before its original is stored with its notice and makes no record. It admits a job for the original at once. The original then makes revision 1 with every notice that waited. This holds in either arrival order.
- A correction that names a correction is invalid data. It blocks its job with the reason code `CorrectionOfCorrectionException`. The check holds in either arrival order.
- A list job covers a window of publication dates and admits one document job for each listed document. The window needs no cursor table. It starts 2 days before the newest publication date of any stored document, or at `backfillFrom` when none exists. It ends today.
- A window must fit one API page of 1,000 documents. A longer list is invalid data and blocks the job. About 340 documents appear in a year, so the first window from `backfillFrom` fits.
- A new document job fetches the document with pinned `fields[]`, including `disposition_notes` and `body_html_url`. The pin keeps a changing field such as the page view count out of the capture. The pin also adds `president`, which the API omits otherwise. Jobs with one of the two exact prior pinned field lists stay valid and keep their original URL. Other field orders and query forms are invalid.
- The extraction text has each fixed fact on its own line, so each is a clean citation. `ExecutiveActionFacts` owns the labels and the order. Disposition notes, when present, retain their multiline source text as one appended block.
- Admission writes revision 1 and the code approval in one transaction. This follows the roster admission, which writes a snapshot in one transaction, and `ReviewRecords.AppendCodeApprovedAsync`. The facts need no model.
- The summary is an analysis revision with a run ID, as an action text is. The owner chose this. The step appends it as the next revision under the analysis author. Code approves that revision number after the checks. The precedent is `ActionDraftStep`.
- The summary has 2 or 3 cited sentences at reading grade 12 or below. Each sentence has an exact quote that is a span of the stored text. The step reads the first 60,000 characters and the revision says when the text was cut. The precedent is the bill text summary.
- The prompt asks for what the document does, not what it aims at. A closed list of three phrases backs the rule: `aims to`, `seeks to`, and `intended to`. Code finds only those phrases, as whole words. It does not judge meaning. The repair pass sends back the phrase. The measure counts the answers that held one.
- The summary queue has its own table and its own step, in the shape of the action draft queue. It shares the budget table of the action queue, with its own task name. A new entry comes with the text row. The step is off until `CIVIC_LENS_EXECUTIVE_SUMMARY_DAILY_TOKENS` is set. The owner sets it after a paid measure of 20 documents.
- A correction after the summary copies the summary and has the code author. The run ID stays on the summary revision only.
- The headline is the official title. Public pages say that it is the title from the Federal Register.
- The signer is the configured person whose `President` office covers the signing date. The person ID must equal the President identifier that the Federal Register cites. Both Presidents hold office on 2025-01-20, so the cited identifier picks one. A document with no match is invalid data and blocks the job.
- The body text comes from the HTML body at the `body_html_url` of the detail response. An example is `https://www.federalregister.gov/documents/full_text/html/2025/01/29/2025-01953.html`.
- The document row keeps that URL in `body_html_url`, and the text job fetches it as it is. Code never builds the body URL. The date in its path can differ from the publication date.
- A text job URL must start with the source URL, which ends with a slash. Its last segment must be `{number}.html`. Code checks no date in the path.
- robots.txt of `www.federalregister.gov` was checked on 2026-11-12. It does not disallow `/documents/full_text/html/`. It disallows only `/documents/current`, `/documents/email-a-friend`, the search paths, `/my/`, and `/auth/`.
- Only an original document has text. A correction has none.
- A separate source `federal-register-text` with `apiParser` `federalRegisterText` owns the text jobs. The path of the body is outside `/api/v1/`, and the binding supports one allowed path prefix for each source. The precedent is the source `congress-bill-text`, which owns the second origin of [bill text](bills.md#bill-text). The source keeps the default byte budget of 2,000,000 bytes, so the document source keeps its small budget.
- Admission of an original with a pinned body URL admits its text job in the same transaction. A bill detail admits its text versions job the same way. The key is `federal-register/{text source}/text/{number}`. A known key is a duplicate.
- One text job saves one immutable capture of the body and one extraction. The extraction version is `federal-register-text-v1+html-text-v1`. The extraction keeps the first 60,000 characters, cut at the last whitespace inside the window. `TextWindow` owns that rule for bill text and executive text. `chars_total` keeps the full length.
- The extraction drops the printed page markers of the body, which hold `unprinted-element`. It keeps the end matter: the FR Doc number, the filed date, and the billing code. The bill text extractor also drops no administrative line. A signature image has no text.
- Issue and policy area lists are empty at launch.
- The published kind is `executiveAction`. It adds no manifest version bump.
- A reviewer or the owner can withdraw approval on the review page, as for a vote. The page has the decision panel and, for the owner, Take off site; see [review](review.md#take-off-site). Withdrawing approval alone does not change the public site.

## Behavior

### Source configuration

The text source `federal-register-text` has `apiParser` `federalRegisterText`. Its URL is `https://www.federalregister.gov/documents/full_text/html/` and its allowed path prefix is `/documents/full_text/html/`. The trailing slash keeps a sibling path such as `/documents/full_text/html-x` out. It sets no `maxBytes`, so the default of 2,000,000 bytes holds. It sets no credential, no coverage list, no validator, and no `backfillFrom`. Its admission policy holds exactly one job, like the bill text source. It ships with `enabled: false`. A disabled or missing text source makes no text job. It shares the origin and so the pacing key of the document source.

One `api` source with `apiParser` `federalRegisterDocuments` follows the Federal Register. The source URL is `https://www.federalregister.gov/api/v1/documents.json`. The allowed path prefix is `/api/v1/`, because the list path and the document path need one prefix.

The source sets `backfillFrom` and no credential, no coverage list, no validator, and no Congress option. It covers no people and stays eligible every day. The shipped source `federal-register-documents` sets `backfillFrom` 2024-10-29 and `checkIntervalSeconds` 21600. It ships with `enabled: false`, like the other `api` sources. The admission policy holds 1,000 jobs. [Operations](../operations.md#federal-register-stream) holds the enable steps.

### Window and jobs

The scheduler makes one list job for each due check. Only the schedule makes it. The list URL holds the window, the type filters, the field list, `order=oldest`, and `per_page=1000`. `FederalRegisterUrl` is the one place that builds and reads it. New detail URLs request the exact pinned fields through `body_html_url`. Recovery accepts the two exact previous field sets for queued jobs and keeps their requested URL.

A list job admits one document job for each item. The key is `federal-register/{source}/document/{number}`. A known key is a duplicate. A document job gets the check priority when the document was published in the last 2 days, else the backfill priority.

### Parsing and extraction

| Parser | Version | Reads |
|---|---|---|
| `FederalRegisterListParser` | none, because a list has no extraction | One list with document numbers and publication dates |
| `FederalRegisterDocumentParser` | `federal-register-document-v2` | One document |

A document needs these fields: its number, the type `Presidential Document`, and a subtype of the four kinds. It also needs a title, two dates, a citation, and a President. The link must be on `www.federalregister.gov`. The number of the response must equal the number in the job URL. A line break in a fixed fact becomes a space. When the API includes `disposition_notes`, the parser retains its complete text and line breaks; missing or null notes add no text. The existing document extraction limit bounds the output, and notes are never truncated. A renderer change bumps the extraction version.

```
Federal Register document: 2025-01900
Document type: Executive Order
Presidential document number: 14147
Title: Ending the Weaponization of the Federal Government
Signed: 2025-01-20
Published: 2025-01-28
Citation: 90 FR 8235
President: Donald Trump
Document URL: https://www.federalregister.gov/documents/2025/01/28/2025-01900/ending-the-weaponization-of-the-federal-government
```

A notice or memorandum has no number line. The extraction of a correction document adds the line `Correction notice`, which holds its own number, date, and link. The record cites that line.

### Text

The text job fetches the body HTML at the pinned URL. Preparation reads the number from the last segment of the job URL. It extracts the text with `IDocumentTextExtractor.ExtractAsync` and `FederalRegisterTextParser.Profile`, which drops each element with the class `unprinted-element`. `FederalRegisterRenderer.RenderText` keeps the first window. The extraction has the lines `Federal Register document`, `Characters read: {read} of {total}`, and `Text:`, then the window. Empty text is invalid data.

`AdmitTextAsync` checks that the extraction belongs to an attempt of the text job. It also checks that the document is an original whose pinned body URL equals the job URL. It then adds the `executive_action_texts` row. A repeat adds no row. The same transaction adds the summary queue entry of the record. A replay adds none. The text row and the record do not change, because the text is evidence beside the record. Publication does not read the text yet.

### Admission

Preparation of a document job parses the body, finds the signer, saves the extraction, and calls `AdmitDocumentAsync`. The store takes the job lock. It looks for the document in `executive_action_documents` under that lock, and a known document ends the work as a duplicate. Then the store takes the executive action review lock.

An original creates the draft row and revision 1, with the notices that waited. It also admits its text job, when an enabled text source exists and the document has a pinned body URL. A pinned URL outside the text source fails the job. A correction adds its notice to the current revision and appends the next revision. A correction with no draft waits. Code approves each revision when the rules allow it. The store writes the document row in the same transaction. The extraction must belong to an attempt of the job.

### Disposition targets

`ExecutiveActionDispositionTargets` reads the verbatim disposition notes of a revision. A line that starts with `Amends:` or `Revokes:` holds references that a semicolon separates. A reference becomes a target only when it is exactly `EO n` or `Proc. n`, with an optional `, Month d, yyyy`. These stay in the note only: other lines such as `See:` and `Supersedes:`, and other documents such as memoranda. Joined references such as `EO 1 and EO 2` and ranges also stay. The rule never guesses. Each target keeps its relation, its kind, its number as text, and the start and length of its reference inside the note value. The start and the length count UTF-16 code units, like the other citation spans. The citation of the note then covers it. A repeat of the same relation, kind, and number gives one target.

`ExecutiveActionRevisionRows.FillColumns` writes the target rows with the revision, in the same transaction. A correction revision copies the original notes, so it writes the same targets. The detail API reads the targets through the view `public_api.executive_action_targets`. Each entry has its relation, kind, number, and the cited text of the note. The detail reader extracts each reference with its exact UTF-16 span from the note read once; SQL does not slice the note. It has a record ID only when exactly one other executive action of the active release has the same kind and `presidential_number`. A target with no match, with an older release only, or with two matches has no ID and no link, and stays a cited note. The API never parses the notes. See [search](search.md#api) and [publication](publication.md#public-api-views).

### Review

The review page at `/Review/ExecutiveActions/{id}` shows the facts, their quotes, the history, the banner of an unanswered reader correction, and the decision panel. It has no editor. A reviewer or the owner can withdraw approval or request changes. A record that needs action appears in the review overview with the other fact records.

### Publication

The release holds the record file and a page for each record. The headline is the title. The page says that the title is the title from the Federal Register, that Civic Lens wrote no summary, and that code checked the facts. It links to the Federal Register page. The President page, the all records list, and search list the record. See [publication](publication.md#release-content).

## Storage and contracts

- The generated [executive actions schema](schema/executive-actions.md) lists every table, column, key, and check.
- `executive_action_drafts` has one row for each record. It holds the current revision, the review state, and the listing columns.
- `executive_action_revisions` holds one row for each revision. Typed columns hold the document fields and the code author. The row also keeps the revision JSON as a copy, until a later step drops it. Readers use the columns.
- `executive_action_revision_facts` holds one row for each fact line of a revision: its position and the citation span. It stores no label and no value. A reader builds the lines with `ExecutiveActionFacts.Of` from the columns of the revision.
- `executive_action_revision_summary_sentences` holds one row for each summary sentence of a revision. A row has its position, the sentence, and the span of its quote. The columns `summary_text_origin` and `summary_cut` of the revision hold the origin and the cut flag. Both are null without a summary. The column `run_id` holds the run of the summary revision.
- `exec_summary_analysis` is the summary queue and `exec_summary_analysis_runs` holds its runs. The key is the record ID. Both follow the action queue tables. The budget rows share `action_analysis_budget`, with the task `executive-summary`.
- `executive_action_revision_notices` holds one row for each notice of a revision: its position and the key of the notice document. The document row holds the notice.
- `executive_action_revision_disposition_targets` holds one row for each target of the notes of a revision. A row has its position, relation, kind, and number. It also has the span of the reference inside the note value. It stores no note text. A revision with no notes has no row.
- `executive_action_texts` holds one row for each original document that has its text read: the extraction ID, `chars_read`, and `chars_total`. The key is the document key, and a foreign key to `executive_action_documents` holds it. It stores no text. The extraction holds it. The precedent is `bill_text_versions`.
- `executive_action_review_decisions` holds the decisions, including the code approval.
- `executive_action_documents` has one row for each document. It holds the publication date, which sets the next window. It holds the first revision that has the document. A correction row keeps its notice as `notice_url` and an optional citation span, both null or both set. It has no revision while it waits. A revision never changes a document row that it cites, because the revision reads the notice from that row. `body_html_url` keeps the pinned body URL of the detail response. It is null for a document of an earlier field list. A refetch job has the key `federal-register/{source}/document/{number}/body-url`, and its admission fills that column once.
- `IFederalRegisterAdmissionStore` is the port of list, document, and text admission, and of the body URL fill that admits the text job. `PostgresCollectionJobStore` implements it. `IFederalRegisterTextBackfillStore` is the port of the text backfill and its refetch admission, and the same store implements it. `IExecutiveActionReviewStore` is the review and publication port. `PostgresExecutiveActionReviewStore` implements it.
- `PublishedExecutiveAction` is the published record. It has the kind `executiveAction`.

## Limits and planned work

- Publication does not read the summary yet. The next slice publishes the approved summary with its AI label, and issue tags follow.
- The summary step is off by default. The owner runs a paid measure of 20 documents with `executive-actions text measure`, then sets the daily token limit.
- A prompt change does not redraft a record that has a summary. No stale redraft exists for this task yet.
- Text over 60,000 characters keeps only the first window. A long order is read in part, and `chars_total` says so.
- A document recorded before the text source existed has no text until `executive-actions text backfill` runs. See [operations](../operations.md#executive-action-text-backfill).
- A document recorded before `body_html_url` was pinned has a null URL, about 700 in production. The backfill queues a refetch job for it. A refetch that still returns no URL leaves the row null, and the backfill does not queue it again. The run prints `noUrlWithRefetch`, so such a document stays visible.
- The document row keeps its original `source_job_id`. Only the refetch job key traces where a filled body URL came from. The row has no column for it.
- A President's page lists the record. The talk and action counts do not count it.
- Determinations, presidential orders, and other documents are out of scope. The list filter leaves them out.
- The R-63 pilot has four steps for this kind too; see [roadmap](../roadmap.md). Steps 1 to 3 are done in code. Both write paths write the columns and `revision_json`. The commands `executive-actions revisions backfill` and `executive-actions revisions verify` move and check old revisions. The runbook is in [operations](../operations.md#executive-action-revision-backfill). Step 3 stays open until production runs this code. Step 4 drops the JSON. It needs a migration and a change of `ExecutiveActionRevisionRows.Create`.
- A skipped revision stays legacy, and every run examines it again. Fix the cause first.
- A list longer than one page blocks the job. Move `backfillFrom` forward to fit.
- A document whose President is not a configured President blocks its job. Add the person to the configuration.
- The signing date comes from the Federal Register. Code does not check it against another source.
- Nine or more corrections that arrive before the original make revision 1 fail validation. The original is then not recorded.
- A correction waits with no visible sign when the job of its original fails or blocks for good.
- Disposition notes retain their complete value and exact original-extraction span on each immutable revision. Correction revisions preserve that original note and citation. The revision stores the value and optional source-span columns, leaving fixed fact rows unchanged. Publication includes the notes as one cited fact. Old revisions with no captured notes remain null; no historical notes are inferred. Each immutable revision also stores typed Amends and Revokes targets beside its notes; see [Disposition targets](#disposition-targets). The commands `executive-actions targets backfill` and `executive-actions targets verify` fill old revisions; the runbook is in [operations](../operations.md#executive-action-disposition-target-backfill). The detail API returns the targets, and it gives a record ID only for an exact match in the active release. The server-rendered page does not show the links yet. A planned change renders them from `targets`, and links only an entry that has a `targetRecordId`.
